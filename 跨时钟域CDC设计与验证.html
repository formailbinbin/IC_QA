1. 什么是 CDC

CDC（Clock Domain Crossing，跨时钟域）指一个信号由时钟 A 驱动的触发器产生，却被时钟 B 驱动的触发器采样。只要 A 和 B 之间没有固定的相位关系，接收端采样时刻与发送端数据变化时刻的关系就是随机的，必然存在采样点落在数据跳变窗口内的情况。

clk_a 域 clk_b 域 ┌─────────┐ ┌─────────┐ │ FF_A │──── data_a ────────▶│ FF_B │ └────▲────┘ ↑ └────▲────┘ │ │ │ clk_a 这根线就是 CDC 路径 clk_b (crossing / 异步路径) STA 无法对它做 setup/hold 检查 —— 两个时钟没有共同参考， "采样沿到数据沿"的距离在每个周期都不同。

1.1 异步的三种形态

不是所有「不同时钟」都算异步。判定 CDC 的唯一标准是：两个时钟沿的相对位置能否在 STA 里被静态确定。

关系举例是否 CDC处理方式
同源同步100 MHz 与其 /2 分频 50 MHz，同一 PLL否正常 STA，必要时 MCP
同源但比例非整数同 PLL 出的 300 MHz 与 200 MHz否（但窗口极窄）STA 可算，收敛很难，常退化成异步处理
异源异步SoC 核心时钟 vs 外部 25 MHz 晶振 / USB 48 MHz是必须同步器 + CDC 工具签核
同频不同相且相位未定两个独立 PLL 都出 100 MHz是同上，频率相同不代表同步

最常见的误判：「频率一样所以不用同步」。两个独立 PLL 即使标称同频，也有 ppm 级频差和未知初相，长时间运行必然出现采样点扫过数据跳变沿的情况，是标准 CDC。

1.2 亚稳态与 MTBF

触发器要正确锁存，数据必须在时钟沿前 t_setup 稳定、沿后 t_hold 保持。若数据在这个窗口内跳变，触发器内部的锁存环路可能停在逻辑 0 与 1 之间的亚稳点，经过一段不确定的解析时间后才随机塌陷到 0 或 1。

┌──────┐ data ─────┤ ╱╲ │ 正常：解析时间 < 一个周期，下一级采到稳定值 │╱ ╲ │ clk ──┐ │ ╲ │ 亚稳态：输出在 Vdd/2 附近停留 └──┤ ╲│ ──┐ ┌──── ← 下游可能采到中间电平 └──────┘ └~~~~~~~~┘ ↑ 不确定的解析时间 t_r

亚稳态不可能被消除，只能把它发生并传播出去的概率压到可接受范围。衡量指标是 MTBF（Mean Time Between Failures）：

MTBF = e^(t_r / τ) / (T_w × f_clk × f_data)
符号含义怎么影响 MTBF
t_r留给亚稳态解析的时间（同步器两级之间的可用时间，≈ T_clk − t_setup − t_prop）指数项，最有效的杠杆
τ工艺相关的解析时间常数工艺决定，设计不可控
T_w有效亚稳态窗口宽度FF 单元决定；专用同步器单元更小
f_clk接收端时钟频率越快越差
f_data源数据的跳变率跳变越频繁越差

关键结论：t_r 在指数位置上，所以加一级同步器（把 t_r 从「半个周期」变成「一个完整周期」）通常能把 MTBF 从「天」提高到「上万年」。这就是两级同步器成为业界标配的原因；超高频下才需要三级。

反过来也说明：如果把同步器两级 FF 之间插入组合逻辑、或让它们之间的布线延迟很大，t_r 就被吃掉，MTBF 指数级恶化。这是 §12.2 要用 set_max_delay 而不是单纯 set_false_path 的根本原因。

1.3 为什么 CDC 方案要引入 MTBF

MTBF 不是为了"算出一个好看的数字"，而是因为 CDC 这件事在本质上无法用「对 / 错」来判定，只能用概率来判定。下面分三层说明：为什么必须引入、公式从哪来、以及工程上怎么用。

（1）引入原因：同步路径没有 slack，MTBF 就是它的 slack

原因说明
亚稳态不可消除，只能压概率只要两个时钟异步，源数据跳变就一定有落进 setup/hold 窗口的时刻。没有任何电路能让这个概率变成 0，所以"有没有 bug"这个问法本身就不成立，只能问"多久出一次"
STA 对异步路径失效异步路径被 set_clock_groups -asynchronous 排除后，没有 slack 报告。同步器级间那段路径虽然是同步的，但它的意义不是"满足 setup"，而是"留多少解析时间"。MTBF 就是异步跨越的等效 slack
需要可量化的签核判据"加两级同步器"是经验做法，两级够不够是频率的函数。只有 MTBF 能回答"这颗 2 GHz 的芯片还能不能只用两级"，把设计决策从拍脑袋变成算账
仿真验不到RTL 仿真和注入仿真都抓不到真实概率（见 §15.3）。MTBF 是唯一能在流片前给出定量置信度的手段
对接可靠性指标汽车/工业芯片要报 FIT 率（每 10⁹ 小时失效次数）。FIT = 10⁹ / MTBF(小时)，CDC 必须能折算进整芯片的可靠性预算

（2）公式原理：失效率 = 进入概率 × 未解析完的概率

MTBF 的推导只有两步，都很直观：

第一步，多久进一次亚稳态？源数据跳变只有落在宽度为 T_w 的危险窗口内才会引发亚稳态。两个时钟异步，意味着跳变沿相对于时钟沿的位置在一个周期内均匀分布。于是单位时间内的"危险事件"次数为：

f_danger = T_w × f_clk × f_data

（接收时钟每秒给出 f_clk 次采样机会，数据每秒跳变 f_data 次，每次命中窗口的概率是 T_w / T_clk，相乘即得。）

第二步，进去之后多久还没出来？触发器进入亚稳态后，内部锁存环路的偏离量按时间常数 τ 指数发散，等价于"经过时间 t_r 后仍未判决"的概率为：

P(未解析完 | 等待 t_r) = e^(−t_r / τ)

两者相乘就是失效率，取倒数就是 MTBF：

λ_fail = T_w × f_clk × f_data × e^(−t_r / τ)　　⇒　　MTBF = 1 / λ_fail = e^(t_r / τ) / (T_w × f_clk × f_data)

这个推导解释了公式的全部结构：分母是"多久撞一次"（线性项，全是频率），分子是"撞了之后能不能自己恢复"（指数项，是时间）。这也是为什么所有优化手段都优先去抢 t_r——它是唯一在指数位置上的变量。

（3）数量级直觉：为什么单级不行、两级就够

用一组典型的 0.25 µm 工艺参数代入，可以直观看到两级同步器的意义：

参数取值
τ（解析时间常数）0.31 ns
T_w（亚稳态窗口）9.6 as（阿秒，10⁻¹⁸ s）
f_clk（接收时钟）100 MHz
f_data（数据跳变率）10 MHz
t_r（单级可用解析时间）2.3 ns
方案有效 t_rMTBF结论
单级 FF约 2.3 ns（只有本拍残余时间）≈ 2 天完全不可接受
两级同步器多出一个完整周期（≈ 12.3 ns）≈ 10⁹ 年量级远超产品寿命，可接受

t_r 只增加了一个时钟周期，MTBF 却跨越了十几个数量级——这正是 e^(t_r/τ) 指数项的威力，也是"两级同步器"成为业界默认标配的全部理由。

一个常见的错误算法：有资料把两级同步器的 MTBF 写成"两个单级 MTBF 相乘"。这只是个粗略的类比，并不严谨——两级失效并非独立事件。正确做法是把 t_r 取为第一级 Q 到第二级 D 之间实际可用的解析时间（≈ T_clk − t_setup − t_clk2q − t_wire），代入同一个公式。这也再次说明为什么级间多插一个 buffer 都会伤害 MTBF。

（4）工程上怎么用这个数

用法做法
定同步器级数高频设计中 T_clk 变小 ⇒ t_r 变小 ⇒ MTBF 指数级下降。算一下若两级不够（例如 < 10⁵ 年），就上三级。级数是算出来的，不是抄出来的
系统级累加芯片里有 N 条 crossing，整体失效率是各条相加：MTBF_chip ≈ MTBF_single / N。再乘上出货量：MTBF_fleet ≈ MTBF_chip / N_chip。单条 10⁶ 年，1000 条 crossing、100 万颗芯片，整体就只剩 1 年量级——这就是为什么单条的目标值必须定得极高
选同步器单元库里的专用同步 FF（ASYNC_REG / SYNC_DFF）T_w 和 τ 都更优，常比普通 FF 好几个数量级。§7 的 R1 要求库化封装，本质就是锁定这个参数
反推约束MTBF 对 t_r 极度敏感 ⇒ 必须用 set_max_delay -datapath_only 把级间延迟管住（§12.2），并用 set_size_only 禁止工具改动同步器（§12.3）
降 f_data分母里的 f_data 是线性项，收益不如 t_r，但免费：源端不要让信号无谓地高频翻转（例如先在源域做好去抖/保持，再跨域）

最后强调：MTBF 只描述第 1 类失效（亚稳态传播）。数据丢失、多 bit 不一致、重汇聚这三类（§2）是协议错误，发生概率远高于亚稳态，而且 MTBF 再大也救不了它们。看到"MTBF = 10⁹ 年"就认为 CDC 安全，是最典型的误读。

2. CDC 的四类失效模式

把 CDC 问题拆成四类独立模式，设计时就能逐项确认是否已堵住。注意：加两级同步器只解决第 1 类，另外三类需要协议层面的手段。

2.1 亚稳态传播

接收域第一级 FF 捕获到亚稳态，且在它解析完成前就被下游使用，中间电平沿着组合逻辑扩散，下游不同分支可能解析出不同结果。

解法：两级（或更多级）同步器，第一级的输出只接第二级的 D，给足一个完整周期的解析时间。

2.2 数据丢失（快到慢）

发送域比接收域快时，一个只持续 1 个发送周期的脉冲，可能完全落在接收端两个时钟沿之间，被永久丢失。同步器对此毫无帮助——它只保证采到的值是稳定的，不保证能采到。

clk_fast ─┐_┌─┐_┌─┐_┌─┐_┌─┐_┌─┐_┌─┐_┌─┐_┌─ (200 MHz) pulse ____┌─┐_______________________ 宽度 = 1 × 5 ns clk_slow ────┐______┌──────┐______┌───── (25 MHz, 40 ns) ↑ ↑ 采样点都错过了脉冲 → 丢失

解法：保证源信号在接收域至少宽于 1.5 ~ 2 个接收周期（经验值：≥ 3 个接收周期更保险），或改用 toggle/握手把「脉冲」转成「电平」（§4.2、§4.3）。

2.3 数据不一致（多 bit）

最隐蔽的一类。多个 bit 各自独立过同步器，由于每一位的亚稳态解析结果和布线延迟不同，接收端可能在某个周期采到一个从未在发送端出现过的中间值。

发送端：3'b011 ──▶ 3'b100 (二进制计数器 +1，三位同时翻转) 接收端同步后可能看到： 011 → 111 → 100 ← 出现过 111，源端从未有过 011 → 000 → 100 ← 出现过 000 011 → 101 → 100 ← 出现过 101 如果下游拿这个值去比较"指针相等"判空，会误判。

绝对禁止：多 bit 总线逐位接两级同步器然后直接使用。这是 CDC 工具报的最高频严重错误。唯一例外是能保证任意时刻只有一位变化的编码（格雷码，见 §5.1）。

解法：格雷码、数据冻结 + 单 bit 使能同步（MUX 同步）、握手、异步 FIFO。核心思想都是把 N 个 bit 的同步问题降维成 1 个 bit 的同步问题。

2.4 重汇聚（reconvergence）与毛刺

两个子问题，都和「同步器之外的逻辑」有关。

（a）同步后重汇聚

同一个源信号分两路各自过一套同步器，再在接收域汇合到同一逻辑。两路的同步延迟可能相差 1 个周期，汇合点会出现瞬态非法组合。

┌── sync2 ──┐ src_a ────┤ ├── AND ──▶ 可能出现两路错位 1 拍 └── sync2 ──┘ 产生源端不存在的组合

解法：一个源信号只允许存在一条同步路径，同步后再分发（扇出）。

（b）发送端组合逻辑毛刺

同步器输入端若直接接组合逻辑输出，组合逻辑的毛刺会被接收时钟采样成一个完整的假脉冲——而且采不采到完全随机，仿真极难复现。

解法：同步器输入必须是发送域寄存器输出（FF 的 Q），不允许是组合逻辑。

4.1 两级同步器（慢到快的标准解）

最基础也是最重要的结构：接收域两个背靠背的 FF，中间不插任何逻辑。

    parameter RST_VAL  = 1'b0
)(
    input  wire clk_dst,     // 接收域时钟
    input  wire rst_dst_n,   // 接收域复位（与 clk_dst 同域！）
    input  wire din,         // 来自源域 FF 的 Q，不允许是组合逻辑
    output wire dout
);
    (* ASYNC_REG = "TRUE" *)        // Xilinx/综合工具提示：禁止优化、就近摆放
    reg [STAGES-1:0] sync_q;

    always @(posedge clk_dst or negedge rst_dst_n) begin
        if (!rst_dst_n) sync_q <= {STAGES{RST_VAL}};
        else            sync_q <= {sync_q[STAGES-2:0], din};
    end

    assign dout = sync_q[STAGES-1];
endmodule
要点说明
级数默认 2 级。接收时钟 > 1 GHz、或源跳变率极高时用 3 级
复位必须用接收域的复位。用源域复位就制造了 RDC（§10）
两级之间绝对不能有组合逻辑，否则吃掉 t_r
适用信号只适用于电平型单 bit，且宽度足够（见 §2.2）
物理实现两级 FF 要就近摆放；工艺库有专用 SYNC2 单元时优先用

两级同步器没有解决「数据丢失」。它只保证「采到的值是干净的」。慢→快时宽度天然足够所以没问题；快→慢时必须额外处理，见下面两节。

4.2 快到慢：脉冲展宽与 Toggle 同步

（a）脉冲展宽 stretcher

在源域把 1 拍的脉冲拉长到 N 拍，保证覆盖至少 2 个接收时钟沿。前提是知道频率比，适合频率比固定且已知的场合。

// 源域：把 1 拍脉冲展宽到 N 拍（N 由频率比决定，建议 ≥ 3 × ratio）
reg [N-1:0] stretch;
always @(posedge clk_src or negedge rst_src_n)
    if (!rst_src_n) stretch <= '0;
    else            stretch <= {stretch[N-2:0], pulse_in};

wire wide_level = pulse_in | (|stretch);   // 加宽后的电平送去同步

缺点：频率比写死在 RTL 里。一旦 SoC 支持动态变频（DVFS）或时钟可配置，N 就可能不够，变成偶发丢脉冲的硅上 bug。有变频需求时不要用这个方案。

（b）Toggle 同步（推荐）

把「脉冲」转成「电平翻转」：源域每来一个脉冲就翻转一次 toggle 寄存器，电平信号过同步器（宽度天然足够），接收域做边沿检测还原成脉冲。与频率比无关。

clk_src 域 clk_dst 域 ┌─────────┐ pulse ──▶ toggle│ │ ┌──────┐ ┌──────┐ ┌──────┐ ┌──────┐ │ 异步线 │ │ FF_1 │─▶│ FF_2 │─▶│ FF_3 │ │ T-FF │─┼─────────┼─▶└──────┘ └───┬──┘ └───┬──┘ └──────┘ │ │ │ │ └─────────┘ └── XOR ──┴──▶ pulse_dst 电平每次翻转 = 一个事件；XOR 检测翻转沿 = 还原脉冲
// ---- 源域 ----
reg tog;
always @(posedge clk_src or negedge rst_src_n)
    if (!rst_src_n) tog <= 1'b0;
    else if (pulse_src) tog <= ~tog;      // 每个脉冲翻一次

// ---- 接收域：三级（2 级同步 + 1 级做边沿检测的参考）----
reg [2:0] tog_sync;
always @(posedge clk_dst or negedge rst_dst_n)
    if (!rst_dst_n) tog_sync <= 3'b0;
    else            tog_sync <= {tog_sync[1:0], tog};

wire pulse_dst = tog_sync[2] ^ tog_sync[1];   // 任一方向翻转都出一拍脉冲

Toggle 同步仍有吞吐限制：两个相邻脉冲的间隔必须 > 接收域同步延迟（约 2~3 个 clk_dst 周期）。如果源域脉冲比这更密，toggle 会在同步完成前翻转两次，接收端只看到 0 次或 1 次事件 —— 静默丢事件。这种场景必须用握手（§4.3）或 FIFO（§5.4）。

4.3 快到慢：双向握手（无丢失）

唯一能保证零丢失且与频率比完全无关的单 bit 方案。代价是每次传输需要往返延迟。

src 域 dst 域 ┌─────┐ req ──▶ [sync2] ──▶ ┌─────┐ │ FSM │ │ FSM │ └─────┘ ◀── [sync2] ◀── ack └─────┘ 时序（两相握手）： req ___┌──────────────┐_______ ack _________┌────────────┐___ ↑ ↑ dst 收到并处理 src 看到 ack 后撤 req 往返开销 ≈ 2(同步延迟) ≈ 4~6 拍（取两域中较慢者为主）
// 源域握手 FSM（两相，req 撤销后才能发下一笔）
localparam S_IDLE = 2'd0, S_REQ = 2'd1, S_WAIT_DEASSERT = 2'd2;
reg [1:0] st;
reg       req;
wire      ack_sync;        // ack 经过 cdc_sync_bit 同步到 src 域

always @(posedge clk_src or negedge rst_src_n) begin
    if (!rst_src_n) begin st <= S_IDLE; req <= 1'b0; end
    else case (st)
        S_IDLE : if (start)      begin req <= 1'b1; st <= S_REQ; end
        S_REQ  : if (ack_sync)   begin req <= 1'b0; st <= S_WAIT_DEASSERT; end
        S_WAIT_DEASSERT:
                 if (!ack_sync)  st <= S_IDLE;     // 等 ack 回零，完成一次闭环
        default: st <= S_IDLE;
    endcase
end

握手的真正价值在多 bit 场景：req 有效期间数据总线被冻结，接收端在看到同步后的 req 时直接采总线即可，数据根本不需要过同步器（见 §5.2、§5.3）。

5. 多 bit 同步

核心原则（反复强调）：不要同步多 bit，要把多 bit 降维成单 bit 问题。四种方案分别对应四种降维思路。

5.1 格雷码：从编码上保证只变 1 位

格雷码相邻值只有一位不同。因此逐位同步时，最坏情况只有那一位处于亚稳态，接收端采到的要么是旧值要么是新值，都是合法值。

二进制： 011 ──▶ 100 3 位同时变 → 可能采到 000/111/101（非法） 格雷码： 010 ──▶ 110 只有 1 位变 → 采到 010 或 110（都合法） 3 bit 格雷序列：000 001 011 010 110 111 101 100 (→回到 000)
// 二进制 ⇄ 格雷码转换（组合逻辑，一行）
function automatic [W-1:0] bin2gray(input [W-1:0] b);
    bin2gray = b ^ (b >> 1);
endfunction

function automatic [W-1:0] gray2bin(input [W-1:0] g);
    integer i;
    begin
        gray2bin[W-1] = g[W-1];
        for (i = W-2; i >= 0; i = i - 1)
            gray2bin[i] = gray2bin[i+1] ^ g[i];
    end
endfunction

格雷码的适用条件极其严格：源端数值必须每次只 ±1 单调递变。一旦出现跳变（如计数器被软件写入一个任意值、或清零 ptr <= 0），就会多位同时翻转，格雷码保护完全失效。所以它基本只用在 FIFO 读写指针这一种场合。

5.2 MUX 同步（数据冻结）—— 最常用也最省

思路：数据总线根本不过同步器，只同步一个单 bit 的「数据有效」使能。源端保证使能有效期间数据稳定，接收端用同步后的使能去打拍采数据。

clk_src 域 │ clk_dst 域 │ data_src[31:0] ──────┼───────────────────┐ (异步线，不过同步器) (使能有效期间必须稳定) │ │ ▼ valid_src ──[FF]─────┼─▶[sync2]─▶ valid_dst ─ EN ─▶ ┌──────────┐ │ │ data_dst │ │ └──────────┘ 数据在 valid 之前就已稳定，同步延迟（2 拍）天然成了建立时间余量
// ---- 源域：先摆好数据，再抬 valid；valid 期间不许改数据 ----
always @(posedge clk_src or negedge rst_src_n)
    if (!rst_src_n)       begin data_src <= '0; valid_src <= 1'b0; end
    else if (load && !valid_src) begin
        data_src  <= new_data;    // 数据先于 valid 一拍稳定
        valid_src <= 1'b1;
    end
    else if (done_sync)   valid_src <= 1'b0;

// ---- 接收域：只同步 valid，用它当使能采数据 ----
cdc_sync_bit u_v (.clk_dst(clk_dst), .rst_dst_n(rst_dst_n),
                  .din(valid_src), .dout(valid_dst));

reg valid_dst_d;
always @(posedge clk_dst or negedge rst_dst_n) begin
    if (!rst_dst_n) begin valid_dst_d <= 1'b0; end
    else begin
        valid_dst_d <= valid_dst;
        if (valid_dst && !valid_dst_d)   // 上升沿：此刻 data_src 已稳定 ≥2 拍
            data_dst <= data_src;
    end
end

为什么安全：valid 经过 2 级同步，接收端看到它时，data_src 已经稳定了至少 2 个 clk_dst 周期。同步延迟本身就是数据的建立时间保证。面积开销只有 2 个 FF（而不是 2×32），这也是它被广泛使用的原因。

约束上需要配合 set_max_delay -datapath_only 限制数据线延迟，确保它不会比 valid 路径慢太多（见 §12.2）。

5.3 握手：MUX 同步 + 闭环确认

MUX 同步的升级版，加上 ack 回路，源端确切知道数据已被接收，才能发下一笔。适合低频、必须保证每笔都到的场合（如 APB 配置写入跨域）。

握手类型流程吞吐特点
两相（2-phase）req↑ → ack↑ → req↓ → ack↓每笔 ≈ 4~6 拍信号全回零，状态明确，最常用
四相 / 全回零同上但两边都显式等待对方回零更低最稳健，不依赖任何时序假设
两边沿（2-edge）req/ack 用翻转表示事件，不回零约快 2×省一半延迟，但状态机更易写错

5.4 异步 FIFO：高吞吐的标准答案

需要连续流式传输时唯一可行的方案。原理：双口 RAM + 两个指针，指针用格雷码跨域同步。

┌───────────────────────────┐ wdata ───▶│ Dual-Port RAM (深度 2^N) │───▶ rdata └───────────────────────────┘ wclk 域 rclk 域 ┌──────────┐ ┌──────────┐ │ wptr_bin │──bin2gray──▶ wptr_gray ────┼─▶[sync2]─┼─▶ wptr_g_r │ +1 │ │ │ │ └──────────┘ │ │ ▼ ▲ │ 比较 → empty │ │ full ◀── 比较 ◀── rptr_g_w ◀─[sync2]◀─┼── rptr_gray ◀──bin2gray── rptr_bin │ │ +1 (写域看到的读指针是"偏老"的 → full 判断偏保守 → 安全)
实现要点原因
指针宽度 = log2(DEPTH) + 1多一位用于区分「满」和「空」（指针全等 = 空；最高位不同、其余相同 = 满）
指针必须用格雷码跨域二进制指针多位同时翻转会同步出非法值，导致假空/假满
深度必须是 2 的幂非 2 的幂时格雷码回绕不再保证单 bit 变化
full 在写域算，empty 在读域算各自用「同步过来的偏老的对端指针」，判断天然偏保守——宁可假满/假空，绝不溢出
RAM 输出不需要同步读指针稳定后地址才稳定，数据路径由 set_max_delay 保证
两域复位要协调只复位一侧会导致指针永久错位，必须两域都复位或做 RDC 处理（§10）

「偏保守」是异步 FIFO 安全性的核心。写域看到的 rptr 总是滞后真实值 2~3 拍，意味着写域认为的「剩余空间」比实际更少 → 可能提前报 full（性能损失），但绝不会溢出（功能正确）。读域同理。设计时如果试图"优化"掉这个滞后，就会引入真 bug。

第 三 部 分

设计如何保证 CDC 实现与功能正确

CDC 不是「写对一个模块」的问题，而是「让整个项目不可能写错」的工程问题。核心手段是结构化规则 + 库化封装，把正确性从「靠人细心」转移到「靠流程和工具」。

7. 结构化设计规则

工业界通行的做法：禁止在业务 RTL 里手写同步逻辑，所有跨域必须通过受控的公共单元。

#规则为什么
R1所有同步器封装成项目级公共模块（cdc_sync_bit / cdc_handshake / cdc_async_fifo），业务代码只能实例化，不能自己写 always 做同步把 N 处可能写错收敛成 1 处经过充分验证的实现；CDC 工具也能按模块名批量识别
R2命名规范强制体现时钟域，例如 sig_aclk / sig_pclk，同步器实例统一 u_cdc_*Code review 时肉眼就能发现「两个不同后缀的信号出现在同一个表达式里」
R3跨域只发生在模块边界，内部逻辑严格单时钟每个模块只有一个时钟 → 层次化 STA 和 CDC 分析都简单；跨域集中在一层专门的 *_cdc_wrap
R4一个源信号只允许存在一条同步路径避免重汇聚（§2.4）。需要多处使用时，同步一次后在接收域扇出
R5同步器的输入必须是源域 FF 的 Q，不能是组合逻辑输出组合毛刺会被随机采成假事件，仿真难复现
R6同步器的复位必须用接收域复位用源域复位 = 制造 RDC（§10）
R7多 bit 跨域必须说明采用的降维机制，并在代码注释中声明前提条件（如「valid 有效期间 data 冻结」）前提条件是验证和 CDC 工具 waiver 的依据，不写清楚后人必然破坏它
R8时钟域清单（Clock Domain Spec）作为设计文档的一部分：列出所有时钟、频率范围、域间关系（同步/异步）、所有合法 crossing这是 SDC 的 clock_groups 和 CDC 工具 SGDC 的唯一来源；没有它，约束就是猜的

R1 + R3 是最有价值的两条。做到这两条，CDC 工具的报告量通常能下降一个数量级，剩下的告警才有人力逐条看。反之，如果同步逻辑散落在几百个模块里，工具会报出上万条，团队只能全部 waive，等于没做 CDC 检查。

8. 同步器前后的禁忌

禁忌 1：同步器输入接组合逻辑

// 错误：组合逻辑毛刺会被随机采样
wire req = (state == ST_DONE) && !busy && cnt_zero;
cdc_sync_bit u_bad (.din(req), ...);          // ✗

// 正确：先在源域打一拍
reg req_q;
always @(posedge clk_src or negedge rst_src_n)
    if (!rst_src_n) req_q <= 1'b0;
    else            req_q <= (state == ST_DONE) && !busy && cnt_zero;
cdc_sync_bit u_ok (.din(req_q), ...);         // ✓

禁忌 2：同步器两级之间插逻辑

// 错误：中间插了门，吃掉解析时间 t_r，MTBF 指数恶化
always @(posedge clk_dst) begin
    s1 <= din;
    s2 <= s1 & enable;     // ✗ 这里不能有任何逻辑
end

// 正确：纯移位，要用 enable 就在 s2 之后用
always @(posedge clk_dst) begin
    s1 <= din;
    s2 <= s1;              // ✓
end
wire out = s2 & enable;

禁忌 3：同一源信号走两条同步路径（重汇聚）

// 错误：两套同步器可能错位一拍，AND 出源端不存在的组合
cdc_sync_bit u_s1 (.din(src_flag), .dout(f_a));
cdc_sync_bit u_s2 (.din(src_flag), .dout(f_b));   // ✗
wire use_it = f_a & some_logic(f_b);

// 正确：只同步一次，接收域扇出
cdc_sync_bit u_s  (.din(src_flag), .dout(flag_dst));  // ✓
// flag_dst 在接收域随便用多少次都安全

禁忌 4：对多 bit 总线逐位同步后直接使用

// 错误：经典的多 bit 不一致 bug
genvar i;
for (i = 0; i < 32; i = i + 1)
    cdc_sync_bit u_s (.din(data_src[i]), .dout(data_dst[i]));   // ✗
// data_dst 会出现源端从未存在的中间值

// 正确：用 §5.2 的 MUX 同步，或 §5.4 的异步 FIFO

禁忌 5：对 CDC 路径简单打 set_false_path 就算完

false_path 告诉工具「别管这条路」，于是布线延迟完全失控。单 bit 还勉强（只影响 t_r），多 bit MUX 同步场景会致命：数据线延迟若远大于 valid 线，接收端采 valid 时数据还没到。必须用 set_max_delay -datapath_only（§12.2）。

9. 异步 FIFO 实现要点（逐条核对）

异步 FIFO 是最容易「看起来对、实际有 bug」的模块，建议按下表逐项自检。

// 关键片段：指针与满空判断
localparam AW = 4;                        // 深度 16，必须是 2 的幂
reg [AW:0] wbin, rbin;                    // 宽度 = AW+1，多一位区分满/空

wire [AW:0] wgray = wbin ^ (wbin >> 1);
wire [AW:0] rgray = rbin ^ (rbin >> 1);

// 写域：同步读指针（格雷码，逐位同步是安全的）
reg [AW:0] rgray_s1, rgray_s2;
always @(posedge wclk or negedge wrst_n)
    if (!wrst_n) {rgray_s2, rgray_s1} <= '0;
    else         {rgray_s2, rgray_s1} <= {rgray_s1, rgray};

// 满：最高位不同，次高位不同，其余相同
wire full  = (wgray == {~rgray_s2[AW:AW-1], rgray_s2[AW-2:0]});

// 读域：同步写指针后判空（完全相等即为空）
reg [AW:0] wgray_s1, wgray_s2;
always @(posedge rclk or negedge rrst_n)
    if (!rrst_n) {wgray_s2, wgray_s1} <= '0;
    else         {wgray_s2, wgray_s1} <= {wgray_s1, wgray};

wire empty = (rgray == wgray_s2);
自检项常见错误
指针宽度是否 AW+1用 AW 位 → 满和空都表现为「指针相等」，无法区分
满的判断式是否取反了两位只取反最高位是错的（格雷码的回绕特性决定了要反两位）
深度是否 2 的幂非 2 的幂时格雷码回绕处会多位跳变
full/empty 各自在哪个域算在对方域算会引入新的多 bit 跨域
两域复位是否都做了只复位一侧 → 指针永久错位，FIFO 一开机就是假满或假空
RAM 的写使能是否 wen && !full漏掉 full 保护 → 溢出覆盖未读数据
是否误把 almost_full 等水位线也做成跨域水位线应在本域用本域指针 + 同步过来的对端指针计算

强烈建议：异步 FIFO 不要自己写，用经过硅验证的公共 IP（公司 IP 库 / 代工厂提供 / 成熟开源实现），并配套它自带的 SVA 断言和形式验证脚本。自写异步 FIFO 的 bug 往往只在特定频率比下偶发，仿真跑不出来。

10. 复位域交叉 RDC

CDC 的「孪生问题」。两个 FF 由同一时钟驱动，但复位信号来自不同（异步）复位源：复位撤离时刻不同，发送端已退出复位开始输出，接收端还在复位中（或反之），可能采到不期望的值甚至亚稳态。

rst_a_n ──▶┌──────┐ ┌──────┐◀── rst_b_n (两个独立复位源) │ FF_A │── data ─────▶│ FF_B │ └───▲──┘ └───▲──┘ clk clk ← 同一个时钟！ rst_a_n 已释放、rst_b_n 还在断言中 → FF_B 的 D 口数据在变， 但 FF_B 被异步复位压着；若 rst_b_n 恰在此刻释放 → recovery 违例/亚稳态。 STA 不会报（同时钟同步路径），CDC 工具的 CDC 检查也不一定报， 必须专门跑 RDC 检查。
处理手段说明
复位域合并能合并就合并，最省事。同一功能块尽量只有一个复位
复位撤离排序由复位控制器保证：接收端先退出复位，再放开发送端（或两者同时）
接收端数据隔离在复位期间用同步器/使能把接收端 D 口钉在安全值
同步器复位统一同步器只用接收域复位（规则 R6），从源头减少 RDC
工具检查CDC 工具一般都带 RDC 模式，需要在 SGDC 里声明复位信号与复位域

RDC 极易被漏掉，因为它既不被 STA 覆盖（同时钟路径，STA 认为是普通 setup/hold），也不被默认 CDC 检查覆盖（需要单独开 RDC 分析并正确声明复位）。流程里必须有显式的 RDC 签核项。

约束与 CDC 工具

CDC 的「约束」有两套且不能互相替代：一套给 STA（SDC，决定物理实现质量），一套给 CDC 检查工具（SGDC/TCL，决定能不能查出结构错误）。

12. SDC 侧约束

SDC 对 CDC 做的事有两件：（a）告诉 STA 这些时钟之间不要做跨域 setup/hold 检查；（b）但仍然要限制跨域线的延迟。很多人只做了 (a)，这是 CDC 相关硅上问题的常见来源。

12.1 声明异步关系：set_clock_groups

# 推荐：声明异步时钟组。工具会自动排除组间所有路径的 setup/hold 检查
set_clock_groups -asynchronous \
    -group {clk_core clk_core_div2} \
    -group {clk_usb} \
    -group {clk_rtc}

# 同一组内的时钟仍然互相做正常时序检查（它们同源同步）
命令语义何时用
set_clock_groups -asynchronous组间双向排除检查，且表明"真异步"首选，表达异步关系最准确
set_clock_groups -logically_exclusive逻辑上不会同时活跃（如 MUX 选择的两个时钟）时钟多路选择；注意仍可能需要考虑串扰
set_clock_groups -physically_exclusive物理上不可能同时存在（同一 pin 上的两种模式）多模式分析
set_false_path -from A -to B单向排除指定路径颗粒度更细时用；不如 clock_groups 表达清楚

set_clock_groups 是覆盖式的：同一个时钟出现在多条 set_clock_groups 命令里，后面的可能覆盖前面的（取决于工具版本）。最佳实践是只写一条 set_clock_groups -asynchronous，把所有组一次列全。

12.2 关键：set_max_delay -datapath_only

排除了 setup/hold 检查后，工具对这条线没有任何延迟目标，布线可能绕得很长。后果：

  • 单 bit 同步器：源 FF 到第一级 FF 的线延迟大 → 不直接影响 MTBF，但 第一级到第二级之间若被绕远，t_r 被吃掉，MTBF 指数恶化
  • MUX 同步（多 bit）：数据线延迟 ≫ valid 线延迟 → 接收端按 valid 采样时数据还没稳定，功能直接错
  • 长线还会带来更大的串扰和 skew 不确定性
# 对所有跨域路径给一个延迟上限（典型取接收时钟 1 个周期，或更紧）
set_max_delay 2.0 -datapath_only \
    -from [get_clocks clk_core] -to [get_clocks clk_usb]

set_max_delay 2.0 -datapath_only \
    -from [get_clocks clk_usb]  -to [get_clocks clk_core]

# -datapath_only 的含义：只约束数据路径延迟，忽略时钟路径延迟和时钟不确定性
#   → 正是跨异步域想要的语义（时钟关系本来就无意义）
# 注意：-datapath_only 只能配 set_max_delay，不能配 set_min_delay

标准组合拳：set_clock_groups -asynchronous（去掉无意义的检查）+ set_max_delay -datapath_only（保住物理实现质量）。只写前者是半成品。

12.3 保护同步器不被优化掉

综合和 PnR 工具可能对同步器做出破坏性"优化"：把两级 FF 合并、把第一级替换成扫描链上的共享 FF、或者在两级间插 buffer。

# 允许改驱动强度（修 transition/hold），但不许改结构、不许合并
set_size_only -all_instances [get_cells -hier *u_cdc_sync*/sync_q_reg*]

# 禁止跨同步器做 retiming / 寄存器合并
set_dont_retime  [get_cells -hier *u_cdc_sync*]

# 层次边界保留，便于后续识别与检查
set_dont_touch [get_cells -hier -filter "ref_name =~ cdc_sync_bit*"] false
# ↑ 注意：整体 dont_touch 会导致无法修 transition，MTBF 反而变差，
#   所以优先用 set_size_only，而不是 set_dont_touch
命令效果建议
set_size_only只允许换不同驱动强度的同功能单元推荐。既防结构破坏，又能修 transition
set_dont_touch完全冻结慎用。会导致 transition 超标，MTBF 变差
ASYNC_REG 属性（RTL 中）提示工具这是同步器，就近摆放、禁止优化FPGA 流程必加；ASIC 流程视工具支持情况
专用同步器库单元工艺库提供的 SYNC2，T_w 更小有就用，MTBF 直接改善

物理实现上还要补一条：同步器两级 FF 必须就近摆放。实践中用 create_bound / region 约束，或者直接用库里的双级同步器硬单元。

13. CDC 工具与流程

SDC 解决的是「物理实现别拖后腿」，它完全不检查 CDC 结构对不对。结构正确性必须靠专门的 CDC 工具。

13.1 三类检查引擎

主流工具（Synopsys SpyGlass CDC / VC SpyGlass、Cadence Jasper CDC / Conformal、Siemens Questa CDC、Real Intent Meridian CDC）内部都是这三个引擎的组合：

引擎做什么能发现局限
结构检查
（Structural / Static）		遍历网表，识别所有 crossing，匹配已知同步器模式缺同步器、多 bit 逐位同步、重汇聚、同步器前有组合逻辑、同步器内插逻辑只看结构不看功能，误报多（需要 waiver）；无法判断"协议用得对不对"
形式检查
（Formal / Protocol）		自动生成同步协议断言并用形式方法证明握手协议违例、数据在 valid 期间变化、格雷码多位跳变、FIFO 溢出状态空间爆炸，需要合理切块和假设；需要正确的约束
动态检查
（Dynamic / Metastability Injection）		在仿真中给 CDC 路径注入随机抖动/延迟，模拟亚稳态对亚稳态不鲁棒的功能逻辑、仅在特定频率比下暴露的 bug依赖激励覆盖率；跑得慢

三者不能互相替代。典型流程是：结构检查清零 → 形式检查证明协议 → 动态注入在回归里跑。只做结构检查的项目，仍可能因为"同步器结构对但协议用错"而出问题（例如握手状态机写错、valid 期间数据变化）。

13.2 SGDC / 工具约束

CDC 工具需要一份自己的约束（SpyGlass 叫 SGDC，其他工具是 TCL），内容和 SDC 不同——它关心的是逻辑意图而不是时序数值。

# ---- 时钟与复位声明（最基础，写错则全部分析无效）----
current_design top
clock -name "clk_core" -domain d_core -period 2.0
clock -name "clk_usb"  -domain d_usb  -period 20.83
clock -name "clk_rtc"  -domain d_rtc  -period 30517

reset -name "rst_core_n" -value 0
reset -name "rst_usb_n"  -value 0

# ---- 声明已知的同步器模块，让工具识别而不是报错 ----
sync_cell -name cdc_sync_bit
sync_cell -name cdc_sync_pulse

# ---- 声明数据冻结假设（MUX 同步的前提，§5.2）----
# 告诉工具：data_src 在 valid_src 有效期间是稳定的
qualifier -name valid_src -crossing data_src

# ---- 声明确实无需同步的静态信号 ----
# 只在复位后配置、运行时不变的信号
quasi_static -name cfg_mode[*]

# ---- 不需要分析的时钟组合 ----
cdc_false_path -from clk_scan -to clk_core      # scan 模式不分析
约束作用风险
clock / reset定义时钟域与复位，是一切分析的基础漏声明一个时钟 → 该域所有 crossing 都不被分析，静默漏检
sync_cell注册自定义同步器，工具识别后不报错随便注册未经验证的模块 = 自己给自己开后门
qualifier声明「这个使能保证了那组数据稳定」最危险的约束。声明错了，工具就不报多 bit 错误了，必须用 SVA 独立验证这个假设（§16）
quasi_static声明静态/准静态信号无需同步若该信号运行时其实会变，等于放过一个真 bug
cdc_false_path排除不关心的域间组合同 SDC 的 false_path，容易滥用

qualifier 和 quasi_static 是「用假设换报告干净」的交易。每一条都必须有对应的 SVA 断言在仿真/形式验证中独立证明，否则就是把真 bug 伪装成了合规。Review 时应重点审这两类约束，而不是看报告有多干净。

13.3 Waiver 管理

CDC 项目失败最常见的方式不是"没跑工具"，而是waiver 失控：首次运行报出几千条，团队为了出报告批量 waive，真问题就埋在里面。

规则说明
每条 waiver 必须有署名 + 日期 + 理由「这条是误报」不是理由。要写清为什么结构上安全
禁止通配符批量 waive 整类规则waive -rule Ac_unsync01 等于关掉检查
waiver 文件入版本控制，变更要 review和 RTL 同等对待
每次 RTL 大改后复查 waiver 是否仍成立waiver 基于当时的结构，结构改了假设可能失效
统计并公示 waiver 数量趋势只增不减说明流程在恶化
区分「真误报」和「基于设计假设」后者必须链接到对应的 SVA / 验证项

13.4 签核流程

阶段 1：早期（模块级，RTL 刚成型） ├─ 跑结构检查，按模块逐个清零 ├─ 此时改 RTL 成本最低 └─ 产出：时钟域清单 + 初版 SGDC 阶段 2：集成（子系统/全芯片） ├─ 结构检查（含 RDC）零 error ├─ 形式检查证明所有握手/FIFO 协议 ├─ 所有 qualifier / quasi_static 有对应 SVA └─ waiver 逐条 review 签字 阶段 3：回归（持续） ├─ CDC 检查进 CI，RTL 每次提交自动跑 ├─ 亚稳态注入仿真进夜间回归 └─ 门级网表再跑一次 CDC（确认综合没破坏同步器） 阶段 4：Tapeout 签核 ├─ CDC 报告零 error，warning 全部有结论 ├─ SDC 中 clock_groups 与时钟域清单一致性检查 ├─ report_exceptions -ignored 确认约束未静默失效 └─ RDC 单独签核

阶段 3 的"门级网表再跑一次"经常被省略，但很关键：综合/PnR 可能把同步器优化掉、把两级 FF 合并、或在两级间插了 buffer。只在 RTL 上跑 CDC 无法发现这类问题。对照检查 §12.3 的保护约束是否真的生效。

第 五 部 分

验证：怎么验 CDC

CDC 验证的最大困难：普通 RTL 仿真天然验不出 CDC 问题。因为仿真器用零延迟理想模型，每次采样结果都确定，掩盖了硅上真实存在的随机性。必须用专门手段人为引入这种随机性。

14. 验证的四层防线

层手段能证明什么验不出什么
1静态结构检查（CDC 工具）所有 crossing 都有正确结构的同步器同步协议用得对不对；功能是否正确
2SVA 断言（仿真 + 形式）同步协议的前提条件成立（数据冻结、格雷码单位变化、握手序列）没被激励覆盖到的场景
3亚稳态注入仿真功能逻辑对同步器输出的 ±1 拍不确定性是鲁棒的极低概率事件；依赖随机种子数量（展开分析见 §15.3）
4形式验证在所有可能的时钟相位关系下协议都成立（穷尽）规模受限，通常只能做模块级

为什么只做普通 UVM 仿真不够？

（1）RTL 仿真中 a <= b 是零延迟 NBA 赋值，同步器的第一级永远采到确定值，不会出现亚稳态。

（2）如果 testbench 里两个时钟都是整数倍、固定相位（#5 clk = ~clk 这种），采样关系是周期性固定的，永远只覆盖一种相位组合。硅上会扫过所有相位。

（3）多 bit 不一致问题在 RTL 仿真中完全不出现——所有 bit 同时更新，看不到中间值。

结论：RTL 仿真全绿 ≠ 没有 CDC 问题。必须加第 1、3 层。

15. 仿真层面

15.1 时钟随机化

最低成本、收益最高的改进：让 testbench 的时钟频率和初相在每次仿真中随机，而不是写死整数倍。

// 不好：固定整数比 + 零初相，永远只覆盖一种相位关系
initial forever #5    clk_a = ~clk_a;    // 100 MHz
initial forever #10   clk_b = ~clk_b;    // 50 MHz，固定同相

// 好：周期和初相都随机化，每个 seed 覆盖不同相位关系
class clk_cfg;
    rand real  period_a;
    rand real  period_b;
    rand real  phase_b;
    constraint c_range {
        period_a inside {[4.8:5.2]};      // 含 ppm 级频差
        period_b inside {[9.5:10.5]};
        phase_b  inside {[0:10.0]};       // 随机初相，覆盖整个相位空间
    }
endclass

initial begin
    cfg.randomize();
    fork
        forever #(cfg.period_a/2) clk_a = ~clk_a;
        begin #(cfg.phase_b); forever #(cfg.period_b/2) clk_b = ~clk_b; end
    join_none
end
随机化项目的
周期（含非整数倍、ppm 级频差）覆盖采样点缓慢扫过数据沿的过程
初始相位覆盖所有相对相位关系
复位撤离时刻覆盖 RDC 和复位竞争场景
时钟启停时刻（若有门控）覆盖停钟时的握手卡死场景
极端频率比（如 1000:1 和 1:1000）覆盖快→慢丢失和慢→快的边界

15.2 亚稳态注入（关键）

核心技术：在 CDC 路径上人为注入随机的 0/1 延迟或随机值，模拟亚稳态解析结果的不确定性，验证下游功能逻辑是否鲁棒。

正常仿真： src ──────────▶ sync_q[0] ──▶ sync_q[1] 永远确定 注入后（在源→第一级之间插入随机模型）： src ──▶ [random jitter / random delay] ──▶ sync_q[0] ──▶ sync_q[1] ↑ 采样窗口内跳变时，随机决定本拍采到旧值还是新值 → 同步器输出可能比期望早/晚 1 拍 → 验证下游能否容忍

（a）使用 EDA 工具的内建功能（推荐）

主流 CDC 工具都能基于结构分析自动在所有识别出的 crossing 上插入亚稳态模型，生成一个带注入的仿真模型供回归使用。优点是不用改 testbench、覆盖完整、与 CDC 报告一致。

（b）手工模型（理解原理用）

// 简化的亚稳态注入模型：采样窗口内跳变时随机延迟 1 拍
module cdc_jitter_model (
    input  wire clk_dst,
    input  wire din,
    output wire dout
);
`ifdef CDC_INJECT
    reg din_dly;
    always @(din) begin
        // 随机决定这次变化是"立刻可见"还是"延后一个周期可见"
        if ($urandom_range(0,1))
            din_dly <= din;                    // 立刻
        else
            @(posedge clk_dst) din_dly <= din; // 延后一拍
    end
    assign dout = din_dly;
`else
    assign dout = din;
`endif
endmodule

注入仿真的判定标准：注入后 scoreboard 仍然全过，才说明功能对亚稳态鲁棒。注意 scoreboard 本身必须能容忍延迟的不确定性（用「最终一致性」而不是「第 N 拍必须等于 X」的比对方式），否则注入后会报出大量假失败。这是落地时最常见的工程障碍。

另外两个常用技巧：

  • X 传播（X-prop）仿真：把同步器第一级在采样窗口内的输出置 X，看 X 会不会传到关键控制信号。能发现对亚稳态敏感的逻辑。
  • 门级带 SDF 仿真：用真实延迟，能发现 RTL 仿真掩盖的竞争，但速度极慢，一般只跑关键场景和复位序列。

15.3 注入仿真的能力边界：为什么它"验不出来"

§14 的表格里，第 3 层的"验不出什么"写的是极低概率事件；依赖随机种子数量。这句话值得展开，因为它直接决定了第 4 层形式验证为什么不可省。

一句话：亚稳态注入仿真本质是蒙特卡洛采样，不是穷尽证明。它能证明"我注入了 N 次都没挂"，不能证明"所有情况都不挂"。而真正的 CDC bug 往往要求多个小概率条件同时成立，概率相乘后低到随机种子根本撞不上。

（1）为什么是"极低概率事件"——条件要同时成立

一个 bug 要在注入仿真中暴露，需要下面几件事在同一拍同时发生：

必须同时成立的条件量级估计
注入模型恰好作用在这一条 crossing 上（设计里可能有几百条）~1/100
该拍源信号恰好在跳变（不跳变时注与不注结果相同）1/50 ~ 1/1000（看活动率）
注入方向恰好是致命的那一侧（早 1 拍 / 晚 1 拍，通常只有一侧出错）1/2
设计状态恰好落在敏感窗口（FIFO 将满、FSM 在特定 state、复位刚撤离……）1/100 ~ 1/10000

相乘后单次机会的命中概率大约在 10⁻⁶ ~ 10⁻⁹。一次仿真中有效的注入机会可能只有几千次，一轮回归几千个 seed——期望命中次数远小于 1。

最典型的例子是重汇聚（§2.4）：必须两路同步器在同一拍、一路解析成 0、另一路解析成 1 才会出错。两路独立随机，概率本身就是平方级的。

（2）为什么"依赖种子数量"——收益是对数级的

P(至少命中一次) = 1 − (1 − p)N　　⇒　　要达到 90% 置信度需 N ≈ 2.3 / p
单次命中概率 p达到 90% 置信所需 seed 数 N
10⁻³约 2.3 千
10⁻⁶约 230 万
10⁻⁹约 23 亿（不可行）

而且这只保证"发现一次"，不保证回归可复现。所以"加机器多跑 seed"的性价比很差：seed 翻 10 倍，置信度从 63% 升到 99.99%；但只要换一个 p 小一个量级的 bug，就又回到原点。这就是「依赖随机种子数量」的真实含义——用算力换置信度，且换得很贵。

（3）更根本的盲区：模型本身没建那些失效

比种子数量更麻烦的是，常见注入模型（包括上面 cdc_jitter_model 这种）只建模了"输出早/晚 1 拍"或"随机 0/1"，但真实亚稳态还有这些形态：

真实硅上现象常见注入模型是否建模
第一级输出停在半电平，不同扇出看到不同逻辑值（扇出分裂）几乎都没建
亚稳态穿透到第二级（两级都没稳住）一般只注第一级，没建
clk-to-Q 被拉长，导致下游建立时间违例RTL 层面无法表达
亚稳态期间的瞬时功耗尖峰 / 毛刺传播没建

模型里没有的现象，跑多少 seed 都出不来。这部分盲区与种子数量无关，加算力完全无效。

（4）时间尺度的鸿沟

MTBF 公式（§1.2）给出的真实失效间隔是年量级，而且通常是按"百万颗芯片 × 数年"统计出来的。而一轮仿真跑的是毫秒级虚拟时间，两者差了十几个数量级。所以注入仿真从设计上就不是用来"复现硅上那次失效"的。

（5）正确定位与三个补救手段

定位：注入仿真是证伪工具，不是证明工具。它抓的是"鲁棒性差到一注就挂"的设计——这类问题在实际项目中占多数，所以这一层很有价值，但不能单独作为签核依据。

手段做法解决上面哪个问题
过量注入
over-injection		把注入率从"物理真实概率"拉高到每次跨域跳变都注，人为把 p 提高几个数量级（1）（2）：直接压缩所需 seed 数。代价是会报一些物理上极罕见的场景，但对"功能必须容忍 ±1 拍"这个要求来说是正确的压力测试
注入事件绑定覆盖率对"注入发生时的设计状态"做 cross coverage，例如 注入事件 × FIFO 深度桶 × FSM state × 复位阶段（1）：把盲目随机变成有度量的覆盖，哪个桶没打到就定向补激励，而不是无脑加 seed
关键路径交给形式验证把同步器输出抽象成"任意延迟 0~1 拍的非确定性输入"，再穷尽证明协议成立（见 §17）（1）（2）（4）：用穷尽替代采样，彻底绕开概率问题。这正是第 4 层必须存在的原因

落地建议：注入仿真跑"过量注入 + 覆盖率驱动"，保证公共同步单元和关键 CDC 接口模块各自做一次模块级形式证明，再靠设计规则 R1（只允许使用库化同步单元，见 §7）把模块级的结论推广到全芯片。这是在有限算力下能达到的最高置信度组合。

16. SVA 断言库

每种同步机制都有它的前提条件，这些条件必须用断言显式检查——尤其是那些被用来给 CDC 工具写 qualifier 的假设。

（1）数据冻结：valid 有效期间 data 不许变（MUX 同步的前提）
// 对应 §5.2 和 SGDC 里的 qualifier 声明
property p_data_stable_during_valid;
    @(posedge clk_src) disable iff (!rst_src_n)
        valid_src |-> $stable(data_src);
endproperty
a_data_stable: assert property (p_data_stable_during_valid)
    else $error("CDC: data_src changed while valid_src asserted!");
（2）格雷码：任意跳变只能有 1 位不同
property p_gray_one_bit;
    @(posedge wclk) disable iff (!wrst_n)
        $changed(wptr_gray) |-> ($countones(wptr_gray ^ $past(wptr_gray)) == 1);
endproperty
a_gray: assert property (p_gray_one_bit)
    else $error("CDC: gray pointer changed more than 1 bit!");
（3）握手协议：req 必须等到 ack，且序列合法
// req 抬起后必须保持到 ack 到来（不能中途撤销）
property p_req_hold;
    @(posedge clk_src) disable iff (!rst_src_n)
        $rose(req) |-> req throughout (ack_sync[->1]);
endproperty
a_req_hold: assert property (p_req_hold);

// ack 必须在有限时间内返回（活性检查，防死锁）
property p_ack_bounded;
    @(posedge clk_src) disable iff (!rst_src_n)
        $rose(req) |-> ##[1:MAX_LAT] ack_sync;
endproperty
a_ack_bounded: assert property (p_ack_bounded)
    else $error("CDC: handshake timeout, possible deadlock!");
（4）脉冲宽度：快→慢时源脉冲必须足够宽
// 在接收域检查：源信号抬起后至少维持 MIN_CYC 个接收周期
property p_pulse_wide_enough;
    @(posedge clk_dst) disable iff (!rst_dst_n)
        $rose(src_level) |-> src_level[*MIN_CYC];
endproperty
a_pulse_width: assert property (p_pulse_wide_enough)
    else $error("CDC: source pulse too narrow, may be lost!");
（5）异步 FIFO：不许溢出 / 不许读空
a_no_overflow:  assert property (@(posedge wclk) disable iff(!wrst_n)
                                 !(wen && full));
a_no_underflow: assert property (@(posedge rclk) disable iff(!rrst_n)
                                 !(ren && empty));

// 事务级：写进去的每个数据最终必须按序被读出（用 scoreboard 或 FIFO 模型配合）
（6）Toggle 同步：相邻事件间隔足够
// 保证 toggle 翻转间隔 > 接收域同步延迟，否则会丢事件（§4.2 警告）
property p_toggle_spacing;
    @(posedge clk_src) disable iff (!rst_src_n)
        $changed(tog) |-> ##1 $stable(tog)[*MIN_GAP];
endproperty
a_toggle_gap: assert property (p_toggle_spacing)
    else $error("CDC: toggle events too close, event may be lost!");

断言与 CDC 工具约束要一一对应。写了 qualifier -name valid_src -crossing data_src，就必须有断言 (1)；声明了 quasi_static，就必须有断言证明该信号运行时不变。把这个对应关系做成表格并在签核时逐行核对，是 CDC 验证最有效的管理手段。

17. 形式验证

形式方法在 CDC 上的价值：它穷尽所有时钟相位关系和状态，不依赖激励。这正好弥补仿真的最大弱点。

用法说明
工具自动生成 CDC 断言CDC 工具的 formal 模式会基于识别出的同步结构自动生成协议断言并证明，无需手写
证明同步器模块自身对 cdc_handshake、cdc_async_fifo 这些公共单元做一次彻底的形式证明，之后全项目复用，收益极高
证明 qualifier 假设比仿真更可靠地证明「valid 期间 data 恒定」这类前提
抽象时钟建模形式工具可以把异步时钟建模为完全自由的，涵盖任意频率比和相位——仿真做不到

形式验证的规模限制很实际：全芯片跑不动。正确的用法是把公共同步单元和关键 CDC 接口模块单独做形式证明，然后靠设计规则 R1（只用公共单元）把结论推广到全芯片。这也再次说明 §7 的库化封装为什么重要。
