第 一 部 分

复位架构

从两种复位方式的本质差异出发，推进到工业界标准方案、时序收敛手段、高频物理极限，以及与时钟门控的交互陷阱。

1. 异步复位 vs 同步复位

1.1 两种写法

差别只在复位信号有没有进入 always 的敏感列表。

// 异步复位：rst_n 在敏感列表里，不等时钟
always @(posedge clk or negedge rst_n) begin
    if (!rst_n) q <= 1'b0;
    else        q <= d;
end

// 同步复位：rst_n 只是普通数据，必须等时钟沿
always @(posedge clk) begin
    if (!rst_n) q <= 1'b0;
    else        q <= d;
end

综合结果完全不同：异步复位映射到带 RN 引脚的专用复位触发器（如 DFFRQ），复位走的是触发器内部的异步置位/复位端；同步复位综合成普通 D 触发器，复位逻辑被揉进 D 输入前的组合逻辑（相当于 d & rst_n）。

1.2 对比表

维度异步复位同步复位
生效时机立即，不依赖时钟必须等到有效时钟沿
时钟未起振时仍然有效（上电关键优势）完全失效
面积复位 FF 单元略大，但无额外组合逻辑普通 FF + 每位一个与门，数据路径变长
对时序路径的影响不占用数据路径时序预算插入 D 前，吃掉 setup 余量
毛刺敏感性高。复位线上任何窄脉冲都会误复位低。窄于一个周期的脉冲会被时钟采样滤掉
STA 检查类型recovery / removal普通 setup / hold
亚稳态风险释放沿若落在时钟沿附近会产生亚稳态无（本质是数据，满足 setup 即可）
DFT 可控性需把复位端接到 scan 可控，否则 scan shift 被破坏天然可控，复位走数据路径
仿真与综合一致性复位释放的竞争在 RTL 仿真可能看不出来行为确定，易复现

1.3 各自的致命缺陷

纯异步复位的问题：复位释放时的亚稳态。

复位断言没问题——它本来就是要让电路立刻进入已知状态。危险全在释放瞬间：如果 rst_n 从 0 跳到 1 的时刻恰好落在 clk 上升沿附近的 recovery 窗口内，触发器内部处于"刚被放开又马上被要求采样"的竞争状态，输出可能进入亚稳态，然后在下游随机地解析成 0 或 1。

更糟的是：复位树上不同位置的 FF 看到释放沿的时间不同，有的在这个周期退出复位，有的在下一个周期退出，状态机可能跳进非法状态。

纯同步复位的问题：依赖时钟存在。

上电瞬间 PLL 没锁定、时钟没起振，同步复位根本无法生效，所有 FF 停在随机初值。如果这些随机值驱动了 pad、电源开关、或 PWM 输出，后果可能是硬件损坏。

此外，若时钟被门控关闭，一个短于门控窗口的同步复位脉冲会被永久丢失（详见 第 6 章）。

2. 异步复位、同步释放

既然异步复位怕释放、同步复位怕没时钟，工业界的标准答案就是把两者的优点拼起来：断言走异步路径（立即生效、不依赖时钟），释放走同步路径（对齐时钟沿、消除亚稳态）。英文叫 Asynchronous Assert, Synchronous De-assert。

2.1 复位同步器标准实现

module reset_sync (
    input  wire clk,
    input  wire rst_async_n,   // 来自 PAD / PMU 的原始异步复位
    output wire rst_sync_n     // 送给本时钟域所有 FF
);
    reg r1, r2;

    always @(posedge clk or negedge rst_async_n) begin
        if (!rst_async_n) begin
            r1 <= 1'b0;
            r2 <= 1'b0;
        end else begin
            r1 <= 1'b1;        // 注意：D 端是常量 1，不是数据
            r2 <= r1;
        end
    end

    assign rst_sync_n = r2;
endmodule

2.2 工作过程

clk ─┐_┌─┐_┌─┐_┌─┐_┌─┐_┌─┐_┌─┐_┌─┐_┌─ rst_async_n ───┐ ┌────────────── └─────────────────┘ ↑ 异步断言 ↑ 异步释放（时刻任意） r1 ───┐ └─┐ └───────────────────┘ ← 第 1 个时钟沿后置 1 （可能亚稳态，但不输出） r2 = rst_sync_n ─┐ └─┐ └─────────────────────┘ ← 第 2 个沿后置 1 （干净、对齐时钟）
  • 断言阶段：rst_async_n 一拉低，两个 FF 通过异步复位端立即清零，rst_sync_n 瞬间变 0。不需要时钟，上电无时钟时也有效。
  • 释放阶段：rst_async_n 拉高后，两个 FF 退出异步复位状态，但 D 端的常量 1 需要两个时钟沿才传到 r2。r1 承担了可能的亚稳态，r2 给它一整个周期去稳定。

为什么 D 端接常量 1 很关键？因为这样 r1 的亚稳态只可能解析成 0 或 1，而「解析成 0」只意味着复位晚释放一个周期——功能上无害。如果 D 端接的是真实数据，亚稳态解析错误会直接造成功能错误。这是复位同步器与普通 CDC 同步器的本质区别。

2.3 每个时钟域一个同步器

多时钟域设计中，不能用一个同步器的输出去复位所有域。正确做法是原始异步复位扇出到每个域，各自做同步。

reset_sync u_rst_sync_cpu (.clk(clk_cpu), .rst_async_n(por_n), .rst_sync_n(rst_cpu_n));
reset_sync u_rst_sync_ddr (.clk(clk_ddr), .rst_async_n(por_n), .rst_sync_n(rst_ddr_n));
reset_sync u_rst_sync_pwm (.clk(clk_pwm), .rst_async_n(por_n), .rst_sync_n(rst_pwm_n));

RDC（Reset Domain Crossing）：如果信号从 rst_cpu_n 域的 FF 传到 rst_ddr_n 域的 FF，而两个复位的释放时刻不同步，就存在 RDC 风险——源 FF 已被复位清零，目标 FF 还在正常工作并采到了这个「复位引起的跳变」，可能被误当成有效数据。这类问题普通 CDC 检查抓不到，需要用 Spyglass RDC / Questa CDC 的 RDC 模式专门扫描。

3. 时序收敛：recovery / removal

用了「异步复位、同步释放」之后，rst_sync_n 到各个 FF 复位端的这段路径就成了一条需要被 STA 签核的真实时序路径。它不再是 false path。

3.1 两个检查的定义

检查约束对象含义类比
recovery复位释放沿复位撤销后，必须至少提前 T_recovery 稳定，才能迎接下一个时钟有效沿类似 setup
removal复位释放沿时钟有效沿之后，复位必须继续保持有效至少 T_removal，不能过早撤销类似 hold
┌──────── clk 有效沿 │ ←─ recovery ──→ │ ←─ removal ──→ ─────────────────┐ │ ┌─────────────── rst_n └─┼─┘ │ ↑ 合法释放区在这个窗口之外 （落在窗口内 → 亚稳态）

3.2 关键路径与 slack 公式

需要收敛的路径是：同步器末级 FF 的 Q 端 → 复位分发网络 → 目标 FF 的 RN 端。

slack = T_period − Tck2q(r2) − Treset_tree − Trecovery − uncertainty

其中 T_reset_tree 是复位信号从同步器输出到最远 FF 复位端的组合延迟（含 buffer 树）。这条路径的发起点和捕获点用的是同一个时钟，所以默认按单周期检查——留给复位树的预算只有不到一个时钟周期。

removal 方向则是另一边的约束：

Treset_tree ≥ clk_tree_delay + Tremoval − Tck2q

双边夹击：复位树延迟被两侧同时挤压，必须落在这个窗口内：

clk_tree_delay ≤ T_reset_tree ≤ clk_tree_delay + T − T_recovery

这意味着复位树的延迟必须与时钟树的延迟大致匹配。复位树太快会违反 removal，太慢会违反 recovery。

3.3 SDC 约束要点

（1）原始异步复位的输入端

原始 por_n 从 PAD 进来，与任何时钟都没有相位关系，断言方向无需检查：

set_false_path -from [get_ports por_n] -to [all_registers]
# 或更精确：只放过原始复位到同步器第一级的路径
set_false_path -from [get_ports por_n] \
               -to [get_pins u_rst_sync/r1_reg/RN]

（2）复位同步器的保护

# 禁止综合工具把同步器优化掉 / clone / retime
set_dont_touch [get_cells u_rst_sync/r1_reg]
set_dont_touch [get_cells u_rst_sync/r2_reg]
# 或用 size_only，允许改驱动但不许改结构
set_size_only  [get_cells u_rst_sync/*_reg]

为什么必须 dont_touch？如果同步器输出扇出很大，物理实现工具很可能做 register cloning，复制出 r2_reg_1、r2_reg_2 去分别驱动不同区域。此时：

  • 每个 clone 独立承担亚稳态风险，它们可能在不同周期释放复位；
  • 原本写的 SDC exception 只匹配了 r2_reg/Q，clone 出来的新实例静默未被匹配，约束失效且无报错；
  • 这类失配极难在后期发现，典型的「硅后才暴露」的 bug。

（3）复位树按时钟方式做 CTS

要让 T_reset_tree 与时钟树匹配，关键是让 CTS 把复位网络当作 clock-like net 来处理，做 skew 平衡而不是简单的 buffer 插入。

# ICC2 / Innovus 风格：把复位网设为 clock-like，参与 skew balance
set_clock_sense -stop_propagation [get_pins u_rst_sync/r2_reg/Q]
create_clock_tree ...   # 工具相关

# 把复位网络标为非默认路由规则，减小延迟与变化
set_clock_routing_rule -net [get_nets rst_sync_n] -rule RST_RULE

# 控制复位网最大 transition / skew
set_max_transition 0.10 [get_nets rst_sync_n]

（4）CPPR / CRPR 必须打开

recovery/removal 路径的发起时钟与捕获时钟共享大段时钟树。如果不做公共路径悲观度抵消，这段共享路径的 OCV derate 会被重复计算两次（一次按 max、一次按 min），产生巨大的虚假悲观。

set timing_remove_clock_reconvergence_pessimism true
# 或 PrimeTime
set_app_var timing_remove_clock_reconvergence_pessimism true

4. 高频下同步释放的难点

4.1 核心矛盾：预算被压缩到不可解

再看一次 recovery 的 slack 公式：

slack = T − Tck2q(r2) − Treset_tree − Trecovery − uncertainty

T_ck2q、T_recovery、uncertainty 都是工艺/库决定的固定量，几乎不随频率变化。频率升高时只有 T 在缩小，于是留给 T_reset_tree 的空间被单方面挤压。

频率TTck2q+Trecovery+unc（典型）留给复位树可行性
100 MHz10 ns≈ 0.45 ns≈ 9.5 ns随便做
500 MHz2 ns≈ 0.45 ns≈ 1.55 ns要规划
1 GHz1 ns≈ 0.45 ns≈ 0.55 ns很紧
2 GHz0.5 ns≈ 0.45 ns≈ 0.05 ns基本不可能

在 2 GHz 下，一个全芯片范围的复位网络、跨越几毫米、驱动上万个 FF，物理上不可能把延迟压到 0.05 ns。这时再怎么调 SDC 都没用，必须改架构。
