1. 异步复位 vs 同步复位

1.1 两种写法

差别只在复位信号有没有进入 always 的敏感列表。

// 异步复位：rst_n 在敏感列表里，不等时钟
always @(posedge clk or negedge rst_n) begin
    if (!rst_n) q <= 1'b0;
    else        q <= d;
end

// 同步复位：rst_n 只是普通数据，必须等时钟沿
always @(posedge clk) begin
    if (!rst_n) q <= 1'b0;
    else        q <= d;
end

综合结果完全不同：异步复位映射到带 RN 引脚的专用复位触发器（如 DFFRQ），复位走的是触发器内部的异步置位/复位端；同步复位综合成普通 D 触发器，复位逻辑被揉进 D 输入前的组合逻辑（相当于 d & rst_n）。

1.3 各自的致命缺陷

纯异步复位的问题：复位释放时的亚稳态。

复位断言没问题——它本来就是要让电路立刻进入已知状态。危险全在释放瞬间：如果 rst_n 从 0 跳到 1 的时刻恰好落在 clk 上升沿附近的 recovery 窗口内，触发器内部处于"刚被放开又马上被要求采样"的竞争状态，输出可能进入亚稳态，然后在下游随机地解析成 0 或 1。

更糟的是：复位树上不同位置的 FF 看到释放沿的时间不同，有的在这个周期退出复位，有的在下一个周期退出，状态机可能跳进非法状态。

纯同步复位的问题：依赖时钟存在。

上电瞬间 PLL 没锁定、时钟没起振，同步复位根本无法生效，所有 FF 停在随机初值。如果这些随机值驱动了 pad、电源开关、或 PWM 输出，后果可能是硬件损坏。

此外，若时钟被门控关闭，一个短于门控窗口的同步复位脉冲会被永久丢失（详见 第 6 章）。

1.4 真正的两个维度：断言 × 撤离

前面 1.1–1.3 讲的「异步复位 / 同步复位」其实把两件独立的事绑在了一起。工程上真正要做的选择有两个正交维度：

  • 维度一 · 断言（assert）：复位生效的那一刻，走异步路径还是等时钟沿？
  • 维度二 · 撤离（de-assert / release）：复位解除的那一刻，走异步路径还是等时钟沿？
┌─ 同步断言 ─┐ ┌─ 同步撤离 ─┐ 复位 ────────┤ ├─── × ────────┤ │ └─ 异步断言 ─┘ └─ 异步撤离 ─┘ ↑ ↑ 决定"没有时钟时 决定"有没有 recovery / 能不能复位" removal 要收敛"

两个维度交叉得到四种组合，其中只有两种在工业界真正常用：

组合断言撤离上电无时钟时可用STA 检查工程评价
同步复位需要时钟需要时钟否setup / hold简单，但上电失效
异步断言 + 同步撤离不需要时钟需要时钟是recovery / removal主流方案（见 第 2 章）
异步断言 + 异步撤离不需要时钟不需要时钟是撤离时无时钟 → 无需检查靠流程保证（见 2.5）
同步断言 + 异步撤离需要时钟不需要时钟否—两头缺点都占，几乎不用

把这两个维度拆开看，很多事情就通了：

  • 断言选异步，是为了「不依赖时钟」—— 上电、PLL 失锁、时钟被门控时仍能可靠进入安全态
  • 撤离选同步，是为了「消除亚稳态」—— 让撤离沿与时钟沿的关系变成确定的
  • 撤离也可以选异步，前提是撤离那一刻根本没有时钟沿。没有时钟沿，就不存在 recovery / removal，亚稳态无从谈起

2. 异步复位的两种撤离方式

断言选异步已经没有悬念（1.4），剩下的问题只有一个：撤离怎么做。工业界给出了两条路——同步撤离（2.1–2.4，用复位同步器把撤离沿钉在时钟沿上）和异步撤离（2.5，让撤离发生在没有时钟沿的时刻）。先看前者。

同步撤离的思路是把两者的优点拼起来：断言走异步路径（立即生效、不依赖时钟），撤离走同步路径（对齐时钟沿、消除亚稳态）。英文叫 Asynchronous Assert, Synchronous De-assert。

2.1 复位同步器标准实现

module reset_sync (
    input  wire clk,
    input  wire rst_async_n,   // 来自 PAD / PMU 的原始异步复位
    output wire rst_sync_n     // 送给本时钟域所有 FF
);
    reg r1, r2;

    always @(posedge clk or negedge rst_async_n) begin
        if (!rst_async_n) begin
            r1 <= 1'b0;
            r2 <= 1'b0;
        end else begin
            r1 <= 1'b1;        // 注意：D 端是常量 1，不是数据
            r2 <= r1;
        end
    end

    assign rst_sync_n = r2;
endmodule

2.2 工作过程

clk ─┐_┌─┐_┌─┐_┌─┐_┌─┐_┌─┐_┌─┐_┌─┐_┌─ rst_async_n ───┐ ┌────────────── └─────────────────┘ ↑ 异步断言 ↑ 异步释放（时刻任意） r1 ───┐ └─┐ └───────────────────┘ ← 第 1 个时钟沿后置 1 （可能亚稳态，但不输出） r2 = rst_sync_n ─┐ └─┐ └─────────────────────┘ ← 第 2 个沿后置 1 （干净、对齐时钟）
  • 断言阶段：rst_async_n 一拉低，两个 FF 通过异步复位端立即清零，rst_sync_n 瞬间变 0。不需要时钟，上电无时钟时也有效。
  • 释放阶段：rst_async_n 拉高后，两个 FF 退出异步复位状态，但 D 端的常量 1 需要两个时钟沿才传到 r2。r1 承担了可能的亚稳态，r2 给它一整个周期去稳定。

为什么 D 端接常量 1 很关键？因为这样 r1 的亚稳态只可能解析成 0 或 1，而「解析成 0」只意味着复位晚释放一个周期——功能上无害。如果 D 端接的是真实数据，亚稳态解析错误会直接造成功能错误。这是复位同步器与普通 CDC 同步器的本质区别。

2.3 每个时钟域一个同步器

多时钟域设计中，不能用一个同步器的输出去复位所有域。正确做法是原始异步复位扇出到每个域，各自做同步。

reset_sync u_rst_sync_cpu (.clk(clk_cpu), .rst_async_n(por_n), .rst_sync_n(rst_cpu_n));
reset_sync u_rst_sync_ddr (.clk(clk_ddr), .rst_async_n(por_n), .rst_sync_n(rst_ddr_n));
reset_sync u_rst_sync_pwm (.clk(clk_pwm), .rst_async_n(por_n), .rst_sync_n(rst_pwm_n));

RDC（Reset Domain Crossing）：如果信号从 rst_cpu_n 域的 FF 传到 rst_ddr_n 域的 FF，而两个复位的释放时刻不同步，就存在 RDC 风险——源 FF 已被复位清零，目标 FF 还在正常工作并采到了这个「复位引起的跳变」，可能被误当成有效数据。这类问题普通 CDC 检查抓不到，需要用 Spyglass RDC / Questa CDC 的 RDC 模式专门扫描。

2.4 同步撤离的两种实现：高频撤离 vs 低频撤离

确定了「同步撤离」之后还有一个经常被忽略的选择：同步器用哪个时钟？用功能时钟本身，还是专门引一个慢时钟？这就是高频撤离与低频撤离的分野。

【高频撤离】同步器挂在功能时钟上 ┌──────────┐ por_n ──────────────────────┤ rst_sync ├──→ rst_n ──→ 复位树 ──→ 成千上万个 FF │ (2-FF) │ ▲ clk_core (1 GHz) ───┬───────┤ clk │ │ │ └──────────┘ │ └────────────── clock tree ─────────────────────┘ 撤离预算 = 1 × T_core = 1 ns ← 复位树延迟必须塞进 1 ns，高频下极难 【低频撤离】同步器挂在慢时钟上 ┌──────────┐ por_n ──────────────────────┤ rst_sync ├──→ rst_n ──→ 复位树 ──→ 成千上万个 FF │ (2-FF) │ ▲ clk_slow (10 MHz) ──────────┤ clk │ │ └──────────┘ │ clk_core (1 GHz) ─────────────────────────── clock tree ────────────┘ 撤离预算 = 1 × T_slow = 100 ns ← 复位树随便走，recovery 轻松收敛

低频撤离的隐藏代价：同步器输出 rst_n 是在 clk_slow 域产生的，而它要去复位 clk_core 域的 FF。虽然撤离沿变慢了、预算变大了，但这个撤离沿与 clk_core 之间仍然是异步关系 —— 本质上并没有消除亚稳态，只是把亚稳态窗口相对整个慢周期的占比压到了极小。

所以严格的做法是两级同步：慢时钟域先同步一次（拿到足够的分发时间），再在功能时钟域补一个同步器（消除相对功能时钟的亚稳态）。或者接受这个风险并在 STA 中按 clk_slow → clk_core 的 recovery 路径正常签核。

工程上最常见的折中：低频撤离 + 功能域补一级同步器。慢时钟负责「让复位树有充足时间铺开」，功能域那一级负责「把撤离沿钉在功能时钟沿上」。两者各管一件事，互不冲突。具体实现见 2.4.1。

2.4.1 两级同步器的代码实现

这个折中方案落到 RTL 上就是两级串联的复位同步器。但要注意：两级的「职责分工」主要体现在挂哪个时钟、摆在哪里、怎么约束上，而不在代码结构上 —— 两个模块的 RTL 写法几乎完全一样。

（1）整体拓扑

关键是分清两条复位网络，它们的物理尺度和定时方式完全不同。

)(
    input  wire clk_slow,     // always-on 慢时钟（32 kHz / 晶振 / 分频）
    input  wire por_n,        // 原始异步复位，POR/BOR/WDT/JTAG 聚合后
    output wire rst_glb_n     // 异步断言 + clk_slow 域同步撤离
);
    reg [STAGES-1:0] sync_q;

    always @(posedge clk_slow or negedge por_n) begin
        if (!por_n) sync_q <= {STAGES{1'b0}};
        else        sync_q <= {sync_q[STAGES-2:0], 1'b1};
    end

    assign rst_glb_n = sync_q[STAGES-1];
endmodule
（3）Stage 2：功能域本地同步器（每个时钟域一个）
//==============================================================
// stage 2 : 挂功能时钟，负责「把撤离沿钉在功能时钟沿上」
//           每个时钟域一个实例，物理上贴着它要复位的 FF 群摆放
//==============================================================
module rst_sync_local #(
    parameter STAGES = 2
)(
    input  wire clk,          // 本域功能时钟
    input  wire rst_glb_n,    // 来自 stage 1，相对 clk 是异步的
    input  wire soft_rst_n,   // 本域软复位（可选），1 表示不复位
    output wire rst_n         // 本域复位，驱动本域复位树
);
    // 复位源聚合：必须是干净的 FF 输出相与，不能有组合毛刺
    wire rst_async_n = rst_glb_n & soft_rst_n;

    reg [STAGES-1:0] sync_q;

    always @(posedge clk or negedge rst_async_n) begin
        if (!rst_async_n) sync_q <= {STAGES{1'b0}};
        else              sync_q <= {sync_q[STAGES-2:0], 1'b1};
    end

    assign rst_n = sync_q[STAGES-1];
endmodule

（6）为什么说「两者各管一件事，互不冲突」

这是整个方案的核心，用预算数字说明最清楚。假设 clk_core = 1 GHz（T = 1 ns），clk_slow = 10 MHz（T = 100 ns）：

维度全局网络 rst_glb_n本域复位树 rst_core_n
物理尺度跨整个 die，几毫米单个 partition 内
实际延迟~2.5 ns（长线 + buffer 链）~0.45 ns
可用预算1 × Tslow = 100 ns1 × Tcore = 1 ns
定时方式不做 recovery/removal，只 set_max_delay 封顶真实 recovery/removal 签核
为什么够2.5 ns ≪ 100 ns，随便走0.45 + trec 0.1 + skew 0.2 = 0.75 ns < 1 ns

对比两种单级方案的失败点：

纯高频撤离（只有 stage 2，直接挂 por_n）：那条跨 die 的全局线要在 1 ns 内走完 → 不可能。

纯低频撤离（只有 stage 1）：rst_glb_n 直接去复位 1 GHz 的叶子 FF。预算看似 100 ns，但 recovery 检查的捕获沿是 clk_core 的沿，STA 找最差沿对时仍然只给 1 × Tcore；而且撤离沿相对 clk_core 是异步的，叶子 FF 自己会亚稳态。

两级组合后：长距离那段的撤离沿被声明为「不定时」（因为下游有 stage 2 兜住亚稳态），短距离那段才去跟 1 ns 较劲。两个难点被拆到了两个不同的时间尺度上，所以互不冲突。

（7）SDC 约束：方案真正落地的地方

# 1. 时钟定义
#--------------------------------------------------------------

create_clock -name clk_periph -period 10.000 [get_ports clk_periph]
create_clock -name clk_slow   -period 100.00 [get_ports clk_slow]

# 慢时钟与功能时钟按异步处理。
# 即使 clk_slow 是 clk_core 分频得来的，也刻意声明为异步 ——
# 因为 stage 2 的存在使得 rst_glb_n 的撤离沿无需定时。
set_clock_groups -asynchronous \
    -group {clk_slow} \
    -group {clk_core} \
    -group {clk_periph}

#--------------------------------------------------------------
# 2. 全局网络 rst_glb_n：不定时，但必须卡死绝对延迟与 skew
#--------------------------------------------------------------

set rst_glb_dst [get_pins -hier * -filter \
                 "full_name =~ *u_rst_*/sync_q_reg*/RN"]

# 上面 set_clock_groups 已经把这条路径 false_path 掉了，
# 所以必须用 max_delay 把延迟重新管起来，否则工具会任其疯长
set_max_delay 3.0 -datapath_only -from $rst_glb_src -to $rst_glb_dst
set_min_delay 0.5                -from $rst_glb_src -to $rst_glb_dst

#--------------------------------------------------------------
# 3. 本域复位树：真实 recovery/removal，按 clock-like net 处理
#--------------------------------------------------------------
# 让 CTS 像时钟一样平衡本域复位树

set_clock_routing_rule -net_type reset \
    -rule NDR_2W1S [get_nets u_rst_core/rst_n]

#--------------------------------------------------------------
# 4. 保护同步器不被优化掉
#--------------------------------------------------------------

# 禁止 clone / merge / retime 同步器 FF，只允许改驱动强度
set_size_only -all_instances [get_cells -hier *sync_q_reg*]
# 复位源聚合的那个 AND 门也要锁住，不能被拆成多级或复制
set_dont_touch [get_cells -hier *rst_async_n*]

#--------------------------------------------------------------
# 5. 断言边不是时序问题，别让它污染报告
#--------------------------------------------------------------
# por_n 的断言沿经异步脚传播，正确性由「最小复位脉宽 + 保持足够长」保证，
# 不由 setup/hold 保证
set_false_path -from [get_ports por_n]

#--------------------------------------------------------------
# 6. 实在收不进 1 个周期时，才动 MCP（见第 13 章）
#--------------------------------------------------------------
# set_multicycle_path -setup 2 -from [get_pins u_rst_core/sync_q_reg[2]/Q]
# set_multicycle_path -hold  1 -from [get_pins u_rst_core/sync_q_reg[2]/Q]

第 2、6 条各有一个容易踩的坑：

（a）set_clock_groups -asynchronous 会连带 false_path 掉 rst_glb_n 的所有路径。很多人只写了 clock group 就以为完事，结果这条跨 die 的复位线没有任何延迟约束，布线后实际延迟 15 ns，各域撤离顺序彻底乱掉。必须补 set_max_delay -datapath_only。

（b）本域树上加 MCP 的前提，恰好是由 stage 1 提供的。MCP -setup 2 的含义是「允许叶子 FF 的撤离沿晚到 2 个周期」，即各 FF 出复位的时刻是错开的。这只有在「撤离后有一段静默期、没有功能行为」时才安全（见 4.3）。而 stage 1 让复位保持了几百 ns，天然提供了这个静默期 —— 两级方案和 MCP 是互相成就的。

（8）三个工程细节

软复位寄存器不能放在被它复位的域里。soft_rst_core_n 如果由 clk_core 域、且被 rst_core_n 复位的寄存器产生，那它一旦置位就会把自己复位掉，soft_rst_n 被清回默认值 —— 要么复位永远出不来，要么变成一个不可控的脉冲。正确做法是把软复位寄存器放在 always-on / 慢时钟域，或做成「写 1 自清、带脉冲展宽」的结构。

clk_slow 必须在复位期间真的在跑。rst_glb_n 的撤离依赖 clk_slow 有沿。如果慢时钟来自一个需要软件使能的时钟门控，就构成死锁环路（与 6.4 的波形三同类问题）。clk_slow 必须是 always-on、免门控的。

DFT：scan shift 期间必须能屏蔽异步复位。

// 通常由 DFT 工具自动插入，这里仅作示意
wire rst_async_n = (rst_glb_n & soft_rst_n) | scan_mode;

注意这个 mux/or 加在异步复位脚的路径上，会增加复位网络延迟，而且必须 set_dont_touch。同时 scan_mode 本身要在 shift 前稳定。

2.5 异步复位、异步撤离：靠流程保证

导图中的另一条常用分支。它的思路完全不同：不去解决撤离时的亚稳态，而是让撤离发生在一个根本不存在时钟沿的时刻。

工作流程

时间轴 ─────────────────────────────────────────────────────────→ ① 上电 / 进入复位 por_n ───┐ └────────────────────────────────────────────── clk （关闭 / 未起振 / 被门控） ░░░░░░░░░░░░░░░░░░░░░░░░░░░░ ② 复位期间保持时钟关闭，等 PLL 锁定 pll_lock ───────────────┌────────────────────────────────── ─────────────┘ ③ 异步撤离复位 —— 此刻没有任何时钟沿 por_n ──────────────────────┌─────────────────────────── │ ← 撤离沿落在"无时钟"区间 clk ░░░░░░░░░░░░░░░░░░░░░░░░░ ↑ 此时仍未开时钟 ④ 确认复位已在全芯片铺开（等待 N 个慢周期 / 握手确认）后，才打开时钟 clk_en ─────────────────────────────┌────────────────────── clk ░░░░░░░░░░░░░░░░░░░░░░░░░░┘_┌─┐_┌─┐_┌─┐_┌─┐_┌─ ↑ 第一个时钟沿到来时， rst_n 早已稳定为 1 关键：撤离沿与第一个时钟沿之间有巨大间隔 → recovery 天然满足

为什么它成立

  • recovery / removal 检查的本质是「撤离沿 与 时钟沿 的相对位置」。撤离时没有时钟沿，这个检查就不存在
  • 时钟打开时，rst_n 已经稳定高电平很久了，第一个有效沿看到的是一个完全确定的值
  • 复位树再大也无所谓 —— 它有「从撤离到开时钟」这整段时间去铺开，而这段时间由上层流程控制，可以是任意长

适用场景

  • 上电流程：PMU / PMIC 控制的上电序列天然就是「先复位 → 等电源与 PLL 稳 → 撤复位 → 开时钟」
  • 低功耗唤醒：从 deep sleep 退出时，时钟本来就是关的
  • 带时钟门控的模块级复位：先关门控 → 断言复位 → 撤离复位 → 再开门控
  • 极高频设计：当 第 4 章 说的 recovery 预算在物理上已经不可解时，这是少数可行的出路

它的风险全在「流程」两个字上。

  • 流程由 PMU 状态机 / 固件 / 上电序列控制，一旦某条路径上有人在复位还没撤干净时就打开了时钟，recovery 违例立刻回来，而且这次没有任何 STA 保护
  • 流程正确性无法由 STA 签核。STA 看到的是「撤离路径没有时钟沿要检查」，它不会告诉你流程写错了
  • 验证必须靠 SVA 断言覆盖：在 clk 的第一个有效沿处断言 rst_n 已稳定足够长时间
  • 异常路径最容易出事：看门狗复位、调试器复位、热复位这些可能在时钟正在跑的时候触发 —— 此时撤离沿就落在有时钟的区间里，前提被打破

工程做法：对「时钟一定关闭」的复位源（POR、deep sleep 唤醒）用异步撤离；对「时钟可能在跑」的复位源（看门狗、软复位、调试复位）仍然必须配复位同步器走同步撤离。

两条路径最后用一个与门合并：rst_n = por_n_async & soft_rst_n_sync。

3. 时序收敛：recovery / removal

用了「异步复位、同步释放」之后，rst_sync_n 到各个 FF 复位端的这段路径就成了一条需要被 STA 签核的真实时序路径。它不再是 false path。

3.1 两个检查的定义

检查约束对象含义类比
recovery复位释放沿复位撤销后，必须至少提前 T_recovery 稳定，才能迎接下一个时钟有效沿类似 setup
removal复位释放沿时钟有效沿之后，复位必须继续保持有效至少 T_removal，不能过早撤销类似 hold
┌──────── clk 有效沿 │ ←─ recovery ──→ │ ←─ removal ──→ ─────────────────┐ │ ┌─────────────── rst_n └─┼─┘ │ ↑ 合法释放区在这个窗口之外 （落在窗口内 → 亚稳态）

3.2 关键路径与 slack 公式

需要收敛的路径是：同步器末级 FF 的 Q 端 → 复位分发网络 → 目标 FF 的 RN 端。

slack = T_period − Tck2q(r2) − Treset_tree − Trecovery − uncertainty

其中 T_reset_tree 是复位信号从同步器输出到最远 FF 复位端的组合延迟（含 buffer 树）。这条路径的发起点和捕获点用的是同一个时钟，所以默认按单周期检查——留给复位树的预算只有不到一个时钟周期。

removal 方向则是另一边的约束：

Treset_tree ≥ clk_tree_delay + Tremoval − Tck2q

双边夹击：复位树延迟被两侧同时挤压，必须落在这个窗口内：

clk_tree_delay ≤ T_reset_tree ≤ clk_tree_delay + T − T_recovery

这意味着复位树的延迟必须与时钟树的延迟大致匹配。复位树太快会违反 removal，太慢会违反 recovery。

（1）原始异步复位的输入端

（2）复位同步器的保护

# 或用 size_only，允许改驱动但不许改结构
set_size_only  [get_cells u_rst_sync/*_reg]

为什么必须 dont_touch？如果同步器输出扇出很大，物理实现工具很可能做 register cloning，复制出 r2_reg_1、r2_reg_2 去分别驱动不同区域。此时：

  • 每个 clone 独立承担亚稳态风险，它们可能在不同周期释放复位；
  • 原本写的 SDC exception 只匹配了 r2_reg/Q，clone 出来的新实例静默未被匹配，约束失效且无报错；
  • 这类失配极难在后期发现，典型的「硅后才暴露」的 bug。

（3）复位树按时钟方式做 CTS

要让 T_reset_tree 与时钟树匹配，关键是让 CTS 把复位网络当作 clock-like net 来处理，做 skew 平衡而不是简单的 buffer 插入。

# ICC2 / Innovus 风格：把复位网设为 clock-like，参与 skew balance
set_clock_sense -stop_propagation [get_pins u_rst_sync/r2_reg/Q]
create_clock_tree ...   # 工具相关

# 把复位网络标为非默认路由规则，减小延迟与变化
set_clock_routing_rule -net [get_nets rst_sync_n] -rule RST_RULE

# 控制复位网最大 transition / skew
set_max_transition 0.10 [get_nets rst_sync_n]

（4）CPPR / CRPR 必须打开

recovery/removal 路径的发起时钟与捕获时钟共享大段时钟树。如果不做公共路径悲观度抵消，这段共享路径的 OCV derate 会被重复计算两次（一次按 max、一次按 min），产生巨大的虚假悲观。

set timing_remove_clock_reconvergence_pessimism true
# 或 PrimeTime
set_app_var timing_remove_clock_reconvergence_pessimism true

4. 高频下同步释放的难点

4.1 核心矛盾：预算被压缩到不可解

再看一次 recovery 的 slack 公式：

slack = T − Tck2q(r2) − Treset_tree − Trecovery − uncertainty

T_ck2q、T_recovery、uncertainty 都是工艺/库决定的固定量，几乎不随频率变化。频率升高时只有 T 在缩小，于是留给 T_reset_tree 的空间被单方面挤压。

频率TTck2q+Trecovery+unc（典型）留给复位树可行性
100 MHz10 ns≈ 0.45 ns≈ 9.5 ns随便做
500 MHz2 ns≈ 0.45 ns≈ 1.55 ns要规划
1 GHz1 ns≈ 0.45 ns≈ 0.55 ns很紧
2 GHz0.5 ns≈ 0.45 ns≈ 0.05 ns基本不可能

在 2 GHz 下，一个全芯片范围的复位网络、跨越几毫米、驱动上万个 FF，物理上不可能把延迟压到 0.05 ns。这时再怎么调 SDC 都没用，必须改架构。

4.2 其他高频难点

（1）亚稳态 MTBF 随频率恶化

MTBF ∝ exp(Tsettle / τ) / (fclk × fdata)

两级同步器留给 r1 的 settle 时间就是一个周期减去余量。频率翻倍，T_settle 减半，而指数项是急剧下降的——MTBF 可能恶化几个数量级。高频下两级往往不够，需要三级甚至四级。

（2）复位树 skew 带来的「分批释放」

高频下即使 recovery/removal 都收敛了，复位树上不同 FF 的释放时刻仍可能相差超过一个周期。结果是电路「分批」退出复位：

clk ─┐_┌─┐_┌─┐_┌─┐_┌─┐_┌─ rst_near ──┐ ┌─────────────── 近端 FF 在 cycle 2 退出 └───┘ rst_far ──┐ ┌─────────── 远端 FF 在 cycle 3 才退出 └───────┘ ↑ 此刻近端已开始工作，远端还在复位 → 状态机可能跳进非法状态

（3）OCV / derate 的放大效应

先进工艺下 on-chip variation 的绝对值不随频率降低，但相对于周期的占比急剧上升。1 GHz 下 50 ps 的 derate 就是 5% 的周期预算，recovery 路径本来余量就小，derate 一加就红。

4.3 解法

（1）分级流水复位分发（最常用）

不要让一个同步器的输出直接跨越全芯片。在每个区域/模块入口再打一拍，把长路径切成多段短路径。

module rst_pipe_node (
    input  wire clk,
    input  wire rst_in_n,
    output reg  rst_out_n
);
    always @(posedge clk or negedge rst_in_n) begin
        if (!rst_in_n) rst_out_n <= 1'b0;   // 断言仍然异步、立即
        else           rst_out_n <= 1'b1;   // 释放再同步一拍
    end
endmodule
┌─ rst_pipe_node ─→ 区域 A 的 FF reset_sync ──→ ──┼─ rst_pipe_node ─→ 区域 B 的 FF (root) └─ rst_pipe_node ─→ 区域 C 的 FF 每一跳都是一段短路径，recovery 预算独立计算 代价：各区域退出复位的时刻相差 1 拍

这个结构的好处是：断言方向仍然是纯异步的（rst_in_n 直通每级的异步复位端，断言瞬间全链路同时清零），只有释放方向被流水化。断言的即时性没有牺牲。

（2）架构级静默期（quiet period）

如果从架构上能保证「复位释放后的前 N 个周期内，电路不做任何有意义的事」，那各区域差几拍退出复位就无所谓了。

  • 复位释放后插入固定的等待计数器，等所有区域都确认退出复位再放行数据
  • 这期间所有 valid / enable 信号都强制为 0
  • 有了静默期兜底，才敢放宽 recovery 约束（这就是 第 13 章 里 -setup 9 的架构前提）

（3）反向释放顺序

让下游先退出复位，上游后退出。这样上游开始产生数据时，下游已经准备好接收，不会出现「下游还在复位却收到了数据」的情况。

（4）多周期约束放宽 recovery

如果有静默期兜底，就可以用 set_multicycle_path 把 recovery 检查沿往后推，让复位树有多个周期的预算。这是 第二部分 的主题。

（5）低频复位时钟域

把复位同步器放在一个低频时钟域（如 PMU 的 32 kHz 或分频后的慢时钟），复位树在慢时钟域里做同步，recovery 预算瞬间宽松几十倍。代价是复位释放的响应变慢。详见 2.4 低频撤离。

（6）改用异步撤离，绕开 recovery 检查

前面五条解法都在想办法「把复位树塞进有限的周期预算里」。还有一条根本不同的路：让撤离发生在没有时钟沿的时刻，recovery 检查就不存在了。

先关时钟 → 断言复位 → 异步撤离复位 → 等复位在全芯片铺开 → 再开时钟。复位树的延迟不再受任何周期约束。代价是正确性从 STA 签核转移到了上层流程 + SVA。完整讨论见 2.5。

在 2 GHz 这种 4.1 表里标注「基本不可能」的场景，（2）静默期 + （6）异步撤离往往是仅有的可行组合 —— 前者解决「分批退出复位」，后者解决「recovery 收不了」。

5. 同步复位的适用场景

虽然 SoC 顶层复位架构普遍用「异步复位、同步释放」，但同步复位在下面这些场合是更优甚至唯一的选择。

5.1 FPGA 设计

FPGA 厂商（Xilinx/AMD、Intel/Altera）官方推荐同步复位，原因是架构决定的：

  • FPGA 的 LUT/FF 上电时由 bitstream 自动初始化，不需要异步复位来建立初始状态；
  • FF 的异步复位端（PRE/CLR）是专用布线资源，一个 slice 内的 FF 共享同一个控制集。异步复位信号太多会导致控制集爆炸，严重降低 slice 打包效率和布线资源利用率；
  • 同步复位可以被吸收进 LUT 的逻辑中，几乎不占额外资源；
  • 异步复位会阻止 FF 被用于 SRL（移位寄存器 LUT）或 DSP/BRAM 的内部流水寄存器，浪费硬核资源。

5.2 软复位 / 寄存器写触发的复位

CPU 通过 APB/AHB 写一个配置寄存器来复位某个外设。这个复位本身就是由总线时钟同步产生的，天然同步，没有理由走异步路径。

// 软复位：本身就是同步信号
always @(posedge clk) begin
    if (!rst_sync_n || soft_rst) begin   // soft_rst 来自寄存器
        cnt <= '0;
    end else begin
        cnt <= cnt + 1'b1;
    end
end

5.3 数据通路寄存器 / 深流水线

一条 20 级的乘累加流水线，中间级寄存器的值在复位后反正要被重新填充，不需要立即清零。用同步复位的好处：

  • 省掉几千个异步复位 FF 的面积（复位 FF 比普通 FF 大 10%~20%）
  • 这些 FF 不接入复位树，复位树的扇出大幅减小，recovery 收敛压力骤降
  • 甚至可以进一步完全不复位（no-reset FF），只靠 valid 位来保证数据有效性

实践建议：控制路径（状态机、计数器、配置寄存器）用异步复位同步释放；数据路径（流水线寄存器、FIFO 存储体）用同步复位或不复位 + valid 控制。这是面积与可靠性的最佳折中。

5.4 对毛刺敏感的场合

如果复位信号要经过长距离布线、跨板、或来自噪声环境（比如外部按键、电源监测比较器的输出），异步复位会把线上任何窄脉冲都当成真复位。同步复位天然滤掉短于一个周期的毛刺。

5.5 DFT / scan 友好

同步复位走数据路径，scan chain 天然可控，不需要额外的 reset bypass 逻辑。异步复位则必须在 test mode 下把复位端接到可控源（通常是 scan_rst_n 或固定为无效），否则 scan shift 阶段会被意外复位。

5.6 仿真可复现性要求高的场合

异步复位的释放时刻与时钟沿的相对关系在 RTL 仿真里是确定的，但在门级仿真（带 SDF）里会暴露出 recovery 违例导致的 X 传播。同步复位行为完全确定，不存在这类 RTL/GLS 不一致。

6. 时钟门控场景的行为差异

时钟门控（clock gating）是低功耗设计的基本手段。它与复位的交互是实际项目中最容易出 bug 的地方——因为同步复位的生效前提是「有时钟沿」，而门控恰好把时钟沿拿掉了。

6.1 前提：ICG 单元

// 典型 ICG（Integrated Clock Gating）单元
// CP: 时钟输入   E: 使能   TE: test enable   Q: 门控后时钟
CKLNQD4 u_icg (
    .CP (clk_root),
    .E  (module_req),      // 模块有活干时拉高
    .TE (test_mode),
    .Q  (clk_gated)
);

ICG 内部有一个低电平锁存器，在时钟低电平期间采样 E，保证 Q 上不会出现毛刺。E=0 时 Q 停在低电平，没有任何上升沿。

6.2 波形一：复位在时钟已门控时断言

场景：模块进入休眠（icg_en=0，时钟停了），此时复位断言。

cycle 1 2 3 4 5 6 7 8 9 clk_root ─┐_┌──┐_┌──┐_┌──┐_┌──┐_┌──┐_┌──┐_┌──┐_┌──┐_┌─ icg_en ───────┐ ┌────────── └─────────────────────────────┘ ← 时钟门控窗口（无边沿）→ clk_gated ─┐_┌──┐_┌───────────────────────────┐_┌──┐_┌─ ↑ 从这里开始无上升沿 ↑ 恢复 rst_n ─────────────┐ └─────────────────────────────── ↑ cycle 4 断言 ── 异步复位 FF ── q_async ──X──X──X──┐ └──────────────────────────────── ↑ cycle 4 立即清零（不需要时钟） ── 同步复位 FF ── q_sync ──X──X──X──X──X──X──X──X──┐ └────────────────── ↑ cycle 8 才清零 （等到门控恢复后的第一个沿）

结论：异步复位在 cycle 4 立即生效；同步复位要一直等到 cycle 8 时钟恢复后的第一个上升沿才生效，延迟了 4 个周期。在这 4 个周期内，同步复位 FF 保持着复位前的旧值。如果这个 FF 驱动的是 pad、电源开关或 PWM，这 4 个周期的「旧值残留」可能是致命的。

6.3 波形二：复位脉冲完整落在门控窗口内（最危险）

场景：一个短复位脉冲（比如来自软复位寄存器的自清零脉冲）恰好完整地出现在时钟被门控的窗口里。

cycle 1 2 3 4 5 6 7 8 9 clk_root ─┐_┌──┐_┌──┐_┌──┐_┌──┐_┌──┐_┌──┐_┌──┐_┌──┐_┌─ icg_en ───────┐ ┌──────────────── └───────────────────────┘ clk_gated ─┐_┌──┐_┌─────────────────────┐_┌──┐_┌──┐_┌─ rst_n ─────────────┐ ┌────────────────────────── └─────┘ ↑ cy4 ↑ cy6 ← 脉冲完整落在门控窗口内 ── 异步复位 FF（计数器，初值 1）── q_async 1 2 2 ─→│0│ 0 0 1 2 3 ↑ cycle4 清零，之后门控期保持 0 cycle 7 恢复时钟后从 0 开始计数 最终值 = 2 ── 同步复位 FF（计数器，初值 1）── q_sync 1 2 2 2 2 2 3 4 5 ↑ 复位脉冲完全没被任何时钟沿采到 → 复位被永久丢失！ 最终值 = 5

这是同步复位最危险的失效模式：复位被永久丢失。

门控窗口内没有任何时钟上升沿，同步复位 FF 的 D 端虽然在 cycle 4~6 被复位逻辑拉到 0，但没有任何时钟沿来采样它。等 cycle 7 时钟恢复时，rst_n 已经回到 1，D 端又变回正常数据，复位信息彻底消失。

结果：异步复位 FF 最终值 2，同步复位 FF 最终值 5——两组寄存器状态发散。如果它们本该保持一致（比如一对冗余计数器、或一个状态机的 one-hot 编码分散在两类 FF 里），系统进入不可预测状态。

6.4 波形三：同步器挂门控时钟 → 死锁环路

这是一个常见的设计错误：把复位同步器的时钟接到了门控后的 clk_gated，同时门控使能又依赖复位状态。

// ✗ 错误：同步器用 clk_gated
always @(posedge clk_gated or negedge rst_async_n) begin
    if (!rst_async_n) {r2, r1} <= 2'b00;
    else              {r2, r1} <= {r1, 1'b1};
end
assign rst_sync_n = r2;

// ✗ 错误：门控使能要求模块「不在复位中」
assign icg_en = module_req & rst_sync_n;
rst_async_n ──┐ ┌───────────────────────────── └───────────┘ ↑ 原始复位已释放 rst_sync_n ──┐ └───────────────────────────────────────── ↑ 永远卡在 0！ icg_en = module_req & rst_sync_n ──┐ └───────────────────────────────────────── ↑ 因为 rst_sync_n=0，使能永远为 0 clk_gated ──┐_┌──┐_┌─────────────────────────────────── ↑ 永远没有上升沿 ┌─────────────────────────────────────────┐ │ 死 锁 环 路 │ │ │ │ rst_sync_n = 0 │ │ ↓ │ │ icg_en = 0 │ │ ↓ │ │ clk_gated 无上升沿 │ │ ↓ │ │ 同步器拿不到时钟沿，r1/r2 无法置 1 │ │ ↓ │ │ rst_sync_n 永远 = 0 ──────────────────┘ └─────────────────────────────────────────┘ → 芯片永久卡死在复位状态，只能断电重启

这类 bug 在 RTL 仿真中可能被掩盖（如果 testbench 里 module_req 一直是 1 并且 ICG 被建模为理想的与门，波形看起来可能正常）。但在门级仿真或硅上，一旦进入这个状态就是硬死锁。CDC/结构检查工具通常能报出「reset 依赖 gated clock」的环路，务必重视这类 warning。

6.5 波形四：正确做法

两条铁律：同步器挂未门控的根时钟；复位期间强制打开门控。

// ✓ 同步器用 clk_root（未门控）
always @(posedge clk_root or negedge rst_async_n) begin
    if (!rst_async_n) {r2, r1} <= 2'b00;
    else              {r2, r1} <= {r1, 1'b1};
end
assign rst_sync_n = r2;

// ✓ 复位期间强制开启门控，保证复位能传播到所有 FF
assign icg_en = module_req | ~rst_sync_n;

CKLNQD4 u_icg (.CP(clk_root), .E(icg_en), .TE(test_mode), .Q(clk_gated));
cycle 1 2 3 4 5 6 7 8 clk_root ─┐_┌──┐_┌──┐_┌──┐_┌──┐_┌──┐_┌──┐_┌──┐_┌─ （根时钟永不停，同步器一直有沿） rst_async_n ──────┐ ┌──────────────────────── └───────────┘ ↑ cycle 5 释放 module_req ─────────────────────────────┐ └───────────── （模块此时并不想要时钟） rst_sync_n ──────┐ ┌────────────────── └─────────────────┘ ↑ cycle 5 释放后， 两拍（cy6/cy7）同步完成 icg_en = module_req | ~rst_sync_n ───────┌─────────────────┐ ┌──────────── │ └────┘ ↑ 复位期间被 ~rst_sync_n 强制为 1 ↑ 复位结束后交还给 module_req clk_gated ─┐_┌──┐_┌──┐_┌──┐_┌──┐_┌──┐_┌─────┐_┌── （复位全程有时钟沿 → 复位可靠传播） ↑ 此后才允许门控

要点总结：

  • 复位同步器的时钟必须来自未门控的根时钟（或至少是不受本模块复位影响的时钟）
  • icg_en 中用 | ~rst_sync_n 保证复位期间时钟一定在跑
  • 也可以用库里自带复位端的 ICG（如 CKLNQRSTD*），复位时硬件强制 Q 跟随 CP
  • 只有确认复位已完全退出，才把门控权交还给功能逻辑

6.6 门控场景对比小结

情形异步复位同步复位

如果设计里既有时钟门控、又用了同步复位，那么必须在架构上保证「复位有效期间时钟一定在跑」。否则同步复位就是一个不可靠的机制——它可能生效、可能延迟、也可能完全丢失，而这取决于门控的时序，在验证中极难穷举覆盖。

第 二 部 分

set_multicycle_path 原理

从 STA 的默认检查模型出发，推导 MCP 如何移动检查沿、为什么 hold 必须配对出现、以及 -start/-end 的不对称默认值。

7. STA 的默认检查模型

要理解 MCP，先要理解 STA 默认在检查什么。对一条 reg-to-reg 路径，工具做两件事：

  1. 在发起时钟（launch clock）上找一个有效沿，记作 E0；
  2. 在捕获时钟（capture clock）上找「E0 之后最近的那个有效沿」作为 setup 检查沿，记作 C1；hold 检查沿则取 C0（与 E0 同时刻的那个沿）。
E0 E1 E2 E3 launch clk ─┐__________┌───────────┐__________┌─── ↑ 发起沿 C0 C1 C2 C3 capture clk ─┐__________┌───────────┐__________┌─── ↑ ↑ hold 沿 setup 沿（默认）

于是默认的两个不等式是：

setup: Tck2q + Tdp(max) + Tsetup ≤ TC1 − TE0 = 1 × T
hold: Tck2q + Tdp(min) ≥ TC0 − TE0 + Thold = 0 + Thold

这就是「数据必须在一个周期内到达，且不能快到冲掉上一个周期的数据」的含义。

8. MCP 原理：移动检查沿

set_multicycle_path 做的事情只有一件：改变工具挑选检查沿的规则。它不改延迟、不改时钟定义、不碰任何物理量。

一句话本质：MCP 是一个设计断言——你在告诉工具「这条路径上的数据，功能上允许用 N 个周期传输」。工具相信你，于是把 setup 检查沿往后挪 N−1 个周期。这个断言的正确性由设计保证，工具不验证。

8.1 setup 方向

set_multicycle_path 3 -setup -from FF_A -to FF_B
默认（N=1）： E0 launch ─┐__________┌───────────┐__________┌─── ↑ capture ─┐__________┌───────────┐__________┌─── C0 C1 ← setup 检查沿 ←── 1×T 预算 ──→ MCP N=3： E0 launch ─┐__________┌───────────┐__________┌─── ↑ capture ─┐__________┌───────────┐__________┌─── C0 C1 C2 C3 ↑ setup 检查沿 ←────────── 3×T 预算 ──────────────→

公式变成：

setup: Tck2q + Tdp(max) + Tsetup ≤ N × T

注意 -setup N 中的 N 是「第几个捕获沿」，不是「放宽了几个周期」。-setup 1 就是默认行为，等于没约束；-setup 2 才是放宽一个周期。

9. 为什么 hold 必须配对

9.1 工具的内部公式

这是整个 MCP 机制最关键、也最容易被误解的一点。工具并不是独立地处理 setup 和 hold，而是用下面这个公式从 setup 沿推出 hold 沿：

hold_edge = setup_edge − 1 − hold_mcp_value

其中 hold_mcp_value 默认为 0。代入默认情况 setup_edge = 1：

hold_edge = 1 − 1 − 0 = 0 ✓ 正是默认的 C0

9.2 只写 setup 会发生什么

如果只写 set_multicycle_path 3 -setup，没写 hold：

hold_edge = 3 − 1 − 0 = 2
只写 -setup 3，未写 -hold： E0 launch ─┐__________┌───────────┐__________┌─── ↑ 发起 capture ─┐__________┌───────────┐__________┌─── C0 C1 C2 C3 ↑ ↑ hold 检查沿 setup 检查沿 （跑到 E0 之后 2 个周期了！） ←─ hold 要求数据在这 2×T 内都不许变 ─→ → hold 约束变成：T_dp(min) ≥ 2×T + T_hold → 工具必须插入约 2 个周期的延迟单元才能满足 → 面积爆炸 / 根本无法收敛

后果：hold 检查沿跑到了发起沿之后两个周期。工具会认为「数据发出后必须保持 2 个周期以上不变」，于是疯狂往数据路径里插 buffer。要么面积/功耗爆炸，要么 hold 永远收敛不了。

这是只写 setup 不写 hold 时最典型的症状：hold violation 数量暴增，且违例量级接近一个时钟周期的整数倍。

9.3 正确的配对规则

我们希望 hold 沿保持在默认位置（也就是 0），所以要求：

0 = N − 1 − hold_mcp ⟹ hold_mcp = N − 1

配对铁律：-setup N 必须配 -hold (N−1)。

set_multicycle_path 3 -setup -from FF_A -to FF_B
set_multicycle_path 2 -hold  -from FF_A -to FF_B   # 3 - 1 = 2

# 本文第三部分的两个实例：
# -setup 9 → -hold 8
# -setup 2 → -hold 1
配对后（-setup 3 -hold 2）： E0 launch ─┐__________┌───────────┐__________┌─── ↑ capture ─┐__________┌───────────┐__________┌─── C0 C3 ↑ ↑ hold 沿（回到默认位置） setup 沿 hold_edge = 3 − 1 − 2 = 0 ✓ → setup 放宽到 3 周期，hold 保持原样 → 这才是我们想要的效果

10. -start / -end 基准

MCP 的周期数要乘以「谁的周期」？这由 -start / -end 决定：

选项含义移动的是
-start以发起时钟周期为单位发起沿往前移
-end以捕获时钟周期为单位捕获沿往后移

默认值是不对称的，这是最容易踩的坑：

  • -setup 默认 -end（移动捕获沿）
  • -hold 默认 -start（移动发起沿）

在同频路径上两者等价，所以单时钟域下不用关心。但在跨频路径（如 100 MHz → 400 MHz）上，乘以哪个周期结果完全不同，必须显式指定。

10.1 跨频场景举例

假设 clk_slow = 10 ns，clk_fast = 2.5 ns（4 倍关系），数据从慢域发到快域。快域每 2.5 ns 就有一个沿，默认 setup 预算只有 2.5 ns，但实际上数据有 10 ns 可用。

# 正确：用捕获时钟（快钟）的周期数来放宽
set_multicycle_path 4 -setup -end   -from [get_clocks clk_slow] -to [get_clocks clk_fast]
set_multicycle_path 3 -hold  -end   -from [get_clocks clk_slow] -to [get_clocks clk_fast]
#                                    ↑ hold 也要显式写 -end，否则默认 -start 基准不一致

实践建议：跨频 MCP 一定把 -start/-end 写全，不要依赖默认值。写出来既能避免基准错配，也让 review 的人一眼看懂意图。

11. 与其他 exception 的选择

当一条路径收敛不了时，有多种 exception 可选。选错会掩盖真实问题。

命令作用适用场景风险

set_false_path完全不检查逻辑上永不发生的路径（如互斥的 mux 选择）路径延迟完全失控，毛刺/串扰无约束

12. MCP 的本质代价

set_multicycle_path 看起来只是一行约束，但它改变的不是工具的算法，而是对设计行为的承诺。工具不会去验证这个承诺，它只会相信你。

12.1 它是断言，不是优化

set_false_path 说的是「这条路径永远不会被使用」，set_multicycle_path N 说的是「这条路径被使用时，接收端在第 N 拍才会去采它，前 N−1 拍的值我不在乎」。

如果设计实际上每个周期都在用这条路径，而你写了 -setup 3：

  • STA 报 clean，签核通过
  • P&R 会主动把这条路径上的单元换小、绕远路，去换面积和功耗 —— 因为工具认为你有 3 倍的时间
  • 硅片回来，该路径在第 1 拍采到的是中间态，功能随机失效，且温度/电压越好越不容易复现

这类 bug 无法通过后仿发现（后仿用的是同一份 SDC），只能靠 review SDC 发现。

12.2 必须有架构机制兜底

一条 MCP 要成立，设计里必须存在某种机制，保证「接收端在 N 拍内不会去看这个值」。常见的合法兜底机制：

  • 静默期：复位释放后、或模式切换后，有一段固定周期数内部不做任何有效操作（复位同步器的 MCP 靠这个）
  • valid / ready 握手：数据有效标志自己走的是短路径（1 cycle），数据总线走 N cycle，接收端只在 valid 拉高后的第 N 拍采数据
  • enable 节拍：接收寄存器的 EN 由一个 N 分频的节拍信号控制，物理上每 N 拍才打开一次
  • 慢速配置总线：APB / 寄存器配置路径，软件写入后要等数个周期才读回

Review MCP 的唯一正确提问方式不是「这条约束语法对吗」，而是：

「凭什么允许它用 N 个周期？是哪一段 RTL 保证了接收端在前 N−1 拍不会采它？」

如果写约束的人答不上来，这条 MCP 就是在掩盖时序问题，应当删掉去改物理实现或改架构。

12.3 它会污染周边

MCP 的作用域由 -from / -through / -to 决定，而这三者的匹配是「所有满足条件的路径」，不是「我心里想的那一条」。

  • -through [get_pins X/Q] 会命中这个 Q 端驱动的全部下游路径，包括你没想到的那些
  • 一旦某条真正需要单周期的路径被顺带放宽，它就彻底失去了时序保护，而且在 report 里是 clean 的
  • 综合/布局后网表变化（cloning、buffer 插入、单元改名）可能让 -through 的对象消失，约束静默失效 —— 这时反而是「本该放宽的没放宽」，表现为莫名其妙的 violation

所以 MCP 的作用域应当尽可能窄：能用 -to 指到具体引脚，就不要用 -through 指到驱动端。

第三部分 · 实际 SDC Review

两组来自真实项目的 set_multicycle_path 约束：复位同步器输出的 reg-to-reg 路径，以及 PWM 输出的 reg-to-pad 路径。

13. 复位同步器 MCP（-setup 9）

13.1 原始约束

set_multicycle_path -setup 9 -from [get_clocks clk_asicclk_src_p0] \
  -through [get_pins u_dig_top/u_asic_top/u_asic_cru/u_tdc_rst_sync/rst_ff2_reg/Q] \
  -to [get_clocks clk_asicclk_src_p0]

set_multicycle_path -hold  8 -from [get_clocks clk_asicclk_src_p0] \
  -through [get_pins u_dig_top/u_asic_top/u_asic_cru/u_tdc_rst_sync/rst_ff2_reg/Q] \
  -to [get_clocks clk_asicclk_src_p0]

13.2 它在说什么

  • u_tdc_rst_sync/rst_ff2_reg 是复位同步器的第二级 FF，它的 Q 就是同步释放后的复位信号源
  • -from 和 -to 是同一个时钟 clk_asicclk_src_p0，所以这是一条标准的单时钟域 reg-to-reg（准确说是 reg-to-reg 的异步复位端）路径
  • 意图：给这条复位分发网络 9 个时钟周期的传播预算，把 recovery 检查从 1 cycle 放宽到 9 cycle
setup_slack = 9×T − Tck2q − Treset_tree − Trecovery − unc

对应回 §4 的那个核心矛盾：当频率很高、复位树很大时，1 个周期根本放不下整棵复位树的延迟，于是用 MCP 把预算拉大 9 倍。

13.3 语法层面：正确

  • 配对正确：-hold 8 配 -setup 9，符合 §9 的 N−1 铁律。代入公式 hold_edge = 9 − 1 − 8 = 0，hold 检查回到发起沿本身，即保持默认行为，没有被意外搬到未来 —— 这是对的
  • 无需 -start / -end：发起和捕获是同一个时钟、同一个周期，两个基准等价（§10）
  • 用 get_clocks 做 from/to：覆盖面足够，不会因为网表改名丢失

13.4 风险一：-through 的作用域过宽

-through [get_pins .../rst_ff2_reg/Q] 命中的是这个 Q 端驱动的所有下游路径。而复位同步器的输出通常不只接复位树：

  • 接到各级 FF 的 RN / SN 端 —— 这是本意，需要放宽
  • 接到 ICG 的 E / TE 使能端（见 §6.5 的带复位 ICG 做法）—— 这条是功能路径，如果被放宽到 9 周期，门控开闭时序就失去保护
  • 接到某些模块的「同步复位」输入（作为数据端 D 的一部分，如 d = rst_n ? data : 0）—— 这是纯数据路径，被放宽后直接失去时序保护
  • 接到复位状态上报寄存器、调试寄存器 —— 功能路径

这些被顺带放宽的路径在 report 里全是 clean 的，不会有任何告警。

改进方向：把作用域收窄到真正需要放宽的终点。

# 方案 A：直接指定终点为复位引脚（最精确）
set_multicycle_path -setup 9 \
  -from [get_clocks clk_asicclk_src_p0] \
  -to   [get_pins u_dig_top/u_asic_top/u_tdc_core/*/RN]

# 方案 B：至少把 -through 从 Q 端挪到复位网的某个明确节点
set_multicycle_path -setup 9 \
  -through [get_nets u_dig_top/u_asic_top/u_asic_cru/tdc_rst_n] ...

约束写完后，务必用 report_timing 逐条确认命中了什么（见 §15）。

13.5 风险二：同步器本身没有被保护

这组约束只放宽了时序，但没有阻止工具去动这个同步器。实际工程中必须配套：

set_dont_touch [get_cells u_dig_top/u_asic_top/u_asic_cru/u_tdc_rst_sync/rst_ff*_reg]
# 或者允许改尺寸但不允许改结构
set_size_only  [get_cells .../u_tdc_rst_sync/rst_ff*_reg]

否则综合可能因为负载过大而克隆（clone） rst_ff2_reg，产生 rst_ff2_reg_1、rst_ff2_reg_2…… 这时：

  • MCP 的 -through 只匹配原名，克隆出来的新实例完全没有被放宽，但它们也驱动复位树 → 冒出一堆无法收敛的 recovery violation，且根因极难定位
  • 更糟的是多个克隆实例之间产生了新的 skew，复位释放不再是同一拍

13.6 风险三：9 个周期必须有静默期兜底

按 §12.2，这条 MCP 成立的前提是：复位释放后的 9 个周期内，整个 TDC 模块不做任何有效操作。需要确认：

  • RTL 里是否有一个释放后的等待计数器 / 状态机停留在 IDLE
  • 如果复位释放后第 1 拍就有 FF 开始计数、开始采样 —— 此时有的 FF 已经释放、有的还在复位，模块进入非法状态
  • 这种失效在 RTL 仿真（零延迟）里永远看不到，只会在硅上偶发

结论：这组约束语法无误、意图合理，是高频设计中放宽 recovery 的常规手段。但必须补三件事：①把 -through 收窄到复位引脚；②给同步器加 dont_touch；③确认 RTL 有 ≥9 周期的释放静默期。

14. reg-to-pad MCP（IO_PWM*）

14.1 原始约束

set_multicycle_path -setup 2 -from [get_clocks VCLK_VBD] \
  -through [get_ports IO_PWM*] -to [get_clocks CLK_VBD]

set_multicycle_path -hold  1 -from [get_clocks VCLK_VBD] \
  -through [get_ports IO_PWM*] -to [get_clocks CLK_VBD]

14.2 先认清这是哪一类路径

这是 reg-to-pad（输出）路径，不是 reg-to-reg，也不是输入路径。

看 -through [get_ports IO_PWM*] 就能确定：路径穿过的是顶层 port，而 IO_PWM* 显然是对外输出 PWM 波形的管脚。所以路径形态是：

芯片内部 │ 片外 │ ┌──────────┐ │ │ PWM reg │ │ │ Q ├──逻辑──→ 输出 buf ──→ ◻ IO_PWM ─┼──→ 板上接收器 / 驱动器 │ CK │ │ （用虚拟时钟 CLK_VBD 建模） └────▲─────┘ │ │ │ VCLK_VBD ← 内部真实时钟（launch） │ CLK_VBD ← 虚拟时钟（capture）
  • VCLK_VBD：内部真实的发起时钟，就是 PWM 寄存器 CK 端上的那个时钟 —— 路径的 launch clock
  • CLK_VBD：虚拟时钟（virtual clock），它不驱动芯片内任何寄存器，只是由 set_output_delay -clock CLK_VBD 引用，用来描述「片外那个接收器是按什么时钟去采我的 PWM 输出的」 —— 路径的 capture clock
  • IO_PWM*：路径的终点（endpoint）。它出现在 -through 里只是写法上的习惯，语义上它不是中间节点

配套的约束一定长这样（不写 output_delay，这条 MCP 就没有意义）：

create_clock -name CLK_VBD -period 100 [get_ports ...]   ;# 或 create_clock 无 source = virtual
set_output_delay 85 -clock CLK_VBD [get_ports IO_PWM*] -max
set_output_delay -5 -clock CLK_VBD [get_ports IO_PWM*] -min

14.3 MCP 在输出路径上的真实效果

输出路径的 setup 检查式是：

Tck2q + T内部逻辑+buf+pad + output_delaymax ≤ N × T

默认 N = 1。写了 -setup 2 之后，右边变成 2T，等价于：

output_delaynew = output_delay − (N−1) × T

也就是说，声称片外那个接收器不是在下一个沿采，而是再往后一个沿才采，于是内部多出整整一个周期 T 的输出时序预算。

-hold 1 的作用同 §9：代回 hold_edge = setup_edge − 1 − hold_mcp = 2 − 1 − 1 = 0，hold 检查停在原来的位置，没有被 setup 的放宽顺带拖到未来。配对正确。

14.4 这条约束合不合理：取决于片外是什么

MCP 在这里本质上是在修正「片外时序模型」。合理的情形：

  • PWM 的周期远大于 VCLK_VBD 的周期（典型：PWM 载波几十 kHz ~ 几 MHz，内部时钟几十 ~ 几百 MHz），片外功率器件对单个内部周期的延迟完全不敏感
  • 板上接收这个 PWM 的是门驱动芯片 / 模拟比较器，根本没有「时钟采样」这回事，CLK_VBD 只是为了让 STA 有个参照而虚构出来的
  • 原来的 output_delay 是按最保守值填的，发现收不了，用 MCP 整体让一个周期

在这类场景下，这条约束是常规做法，不必大惊小怪。

14.5 风险一：MCP 管不到 bit 之间的相对关系

IO_PWM* 是一组管脚（通常是 PWM 的上桥 / 下桥、多相输出）。MCP 放宽的是每一条路径各自相对于时钟沿的裕量，它对「这几条路径之间的相对延迟差」毫无约束。

后果：工具拿到一个周期的额外裕量后，会毫不犹豫地把这些路径上的 buffer 换小、绕远路去省面积功耗。各 bit 的延迟差（skew）可能从几十 ps 扩大到几百 ps 甚至上 ns。

对 PWM 来说这是致命的：

  • 死区时间（dead-time）被压缩：上桥关断和下桥开通之间的间隔由 RTL 算好，但如果上桥路径比下桥路径慢了 1 ns，实际死区就少了 1 ns
  • 死区压到 0 以下 → 上下桥同时导通 → shoot-through，直接炸管
  • 多相 PWM 之间的相位关系被破坏，影响电流均衡

必须配套的约束：

# 1. 限制输出路径的绝对延迟上下限，不让工具随意拉长
set_max_delay <x> -to [get_ports IO_PWM*]
set_min_delay <y> -to [get_ports IO_PWM*]

# 2. 或者用 output_delay 的 min/max 窗口把 skew 夹住，
#    并对这组 port 做 skew group / 等长布线
# 3. 更稳的做法：把死区留足余量，不依赖 ps 级精度；
#    或在 pad 前加一级同一个 clock 上的重定时 FF，让 skew 只取决于 clock tree

14.6 风险二：IO_ 前缀 —— 可能是双向口

端口名以 IO_ 开头，很可能是 bidirectional（inout） pad。这会带来两个问题：

  • 双向 pad 上同时存在输出路径（reg → pad，由 output_delay 约束）和输入路径（pad → reg，由 input_delay 约束）。这条 MCP 写的是 -from VCLK_VBD -to CLK_VBD，只能命中输出方向；输入方向（-from 某个虚拟时钟 -to 内部时钟）完全没有被这条约束覆盖
  • 如果实际上这个 pad 只做输出（只是命名习惯带了 IO_），那没问题；如果真的复用成输入（比如读回电平、做故障检测），那输入路径的时序是另一套，需要单独 review

更隐蔽的失配：如果某些 PWM 端口命名不是 IO_PWM* 开头（比如 PWM_OUT_*、IO_PWMH 写成了 IO_PWM_H），get_ports IO_PWM* 会静默漏掉它们，这些路径依然按 1 周期检查 → 报 violation；或者 get_ports 一个也没匹配上，整条 MCP 变成空约束，工具连 warning 都不一定给。

14.7 Review 结论

这组约束语法与配对正确（2 配 1，符合 N−1），路径类型是 reg-to-pad，作用是把输出时序预算从 1 个周期放宽到 2 个周期，等价于把 output_delay 减去一个周期。

需要确认 / 补充：

  1. 确认 CLK_VBD 确实是只用于 set_output_delay 的虚拟时钟，且周期与 VCLK_VBD 的关系清楚（若两者周期不同，还要考虑 §10 的 -start / -end）
  2. 确认片外接收器真的能容忍多一个周期的延迟（PWM 载波周期 ≫ 内部时钟周期）
  3. 必须另加 set_max_delay / set_min_delay 或等长措施，守住 PWM 各 bit 之间的 skew 与死区
  4. 用 report_port -verbose 确认端口方向，用 report_exceptions -ignored 确认这条 MCP 真的匹配上了路径

16. 常见 SDC 约束清单

SDC（Synopsys Design Constraints）是 Tcl 语法的时序约束文件。一份完整 SDC 的书写顺序是有讲究的 —— 后面的命令依赖前面建立的对象，顺序错了会出现「对象不存在」或「约束被覆盖」。

16.1 一份 SDC 的标准骨架

┌─────────────────────────────────────────────────────────┐ │ 0. 单位与环境 set_units / set_operating_conditions│ ├─────────────────────────────────────────────────────────┤ │ 1. 时钟定义 create_clock │ ← 地基 │ create_generated_clock │ │ set_clock_uncertainty / -latency │ │ set_clock_transition │ ├─────────────────────────────────────────────────────────┤ │ 2. 时钟关系 set_clock_groups -asynchronous │ ← 先说清谁和谁 │ set_false_path（跨异步域） │ 不需要定时 ├─────────────────────────────────────────────────────────┤ │ 3. I/O 时序 set_input_delay / set_output_delay │ │ set_driving_cell / set_load │ ├─────────────────────────────────────────────────────────┤ │ 4. 时序例外 set_multicycle_path │ ← 必须放在 │ set_max_delay / set_min_delay │ 时钟之后 │ set_false_path（功能性） │ │ set_case_analysis │ ├─────────────────────────────────────────────────────────┤ │ 5. 设计规则 set_max_transition / set_max_fanout │ │ set_max_capacitance │ ├─────────────────────────────────────────────────────────┤ │ 6. 优化与保护 set_dont_touch / set_size_only │ │ set_ideal_network │ └─────────────────────────────────────────────────────────┘

优先级规则（同一条路径被多条例外命中时，由强到弱）：

set_false_path > set_max_delay / set_min_delay > set_multicycle_path > 默认单周期检查

同一级别内，作用域越具体优先级越高：-from A -to B 胜过 -from A，-from A 胜过 -to B（因为 -from 比 -to 优先）。两条同样具体的命令，后写的覆盖先写的。

16.2 时钟定义类

命令作用典型写法
create_clock定义主时钟，一切时序的起点create_clock -name clk -period 10 [get_ports clk]
create_generated_clock定义分频/倍频/门控后的派生时钟，自动继承源时钟延迟create_generated_clock -name clk_d2 -source [get_ports clk] -divide_by 2 [get_pins div/Q]
create_clock（虚拟）不挂到任何 pin，只作 I/O 时序参考（见 §14）create_clock -name vclk -period 10（无对象列表）
set_clock_uncertainty预留 jitter + skew 余量set_clock_uncertainty -setup 0.15 [get_clocks clk]
set_clock_latency综合阶段估算时钟树延迟（CTS 后用 -source 保留片外部分）set_clock_latency 0.5 [get_clocks clk]
set_clock_transition综合阶段假定时钟沿的转换时间set_clock_transition 0.1 [get_clocks clk]
set_propagated_clockCTS 之后改用真实时钟树延迟set_propagated_clock [all_clocks]
# 典型时钟段：主时钟 + 分频时钟 + 不确定性
create_clock -name clk_core -period 1.000 [get_ports clk_core]
create_clock -name clk_slow -period 100.0 [get_ports clk_slow]

# 2 分频
create_generated_clock -name clk_core_d2 \
    -source [get_ports clk_core] -divide_by 2 \
    [get_pins u_div/clk_out_reg/Q]

# 综合阶段：理想时钟树 + 预留余量
set_clock_latency    0.3 [all_clocks]
set_clock_transition 0.05 [all_clocks]
set_clock_uncertainty -setup 0.08 [all_clocks]
set_clock_uncertainty -hold  0.03 [all_clocks]

# CTS 之后切换（通常在 PnR 脚本里，而非 SDC）
# set_propagated_clock [all_clocks]

门控时钟是否要 create_generated_clock？标准 ICG 单元（§6 的 CKLNQD4）的输出不需要单独定义 —— 工具会自动让源时钟穿过 ICG 传播，并自动做时钟门控检查（clock gating check）。只有分频、倍频、反相、多路选择后的时钟才需要显式定义。

16.3 时钟关系类

这是最容易写错、且后果最严重的一类。三个命令语义完全不同：

命令语义作用范围
set_clock_groups -asynchronous两组时钟之间没有固定相位关系，双向所有路径都不定时双向、全部路径
set_clock_groups -physically_exclusive两个时钟物理上不会同时存在（如 mux 选择的两个时钟源），crosstalk 也不分析双向、全部路径
set_clock_groups -logically_exclusive逻辑上互斥但物理上共存（仍需做信号完整性/crosstalk 分析）双向、全部路径
set_false_path -from A -to B单向、指定路径不定时单向、可精确限定
# 真正异步的时钟域（不同晶振 / PLL）
set_clock_groups -asynchronous \
    -group {clk_core clk_core_d2} \
    -group {clk_ddr} \
    -group {clk_slow}

# 时钟 mux 选择：两者永不同时活动
set_clock_groups -physically_exclusive \
    -group {clk_pll} -group {clk_xtal}

最常见的坑（§2.4.1 已遇到）：set_clock_groups -asynchronous 会把两组之间的所有路径设为 false path，包括那些你其实仍想限制绝对延迟的网络（如跨域复位线、异步 FIFO 的指针）。必须补：

set_max_delay 3.0 -datapath_only -from $src -to $dst

-datapath_only 的作用是只算数据路径延迟，不算时钟路径延迟，这正是跨异步域时想要的。漏掉它会导致约束值被时钟延迟污染。

16.4 I/O 时序类

芯片边界的约束。关键是理解延迟是「片外」的，参考的是虚拟时钟或端口时钟。

命令方向含义
set_input_delay输入数据到达输入端口的时刻（相对参考时钟沿）
set_output_delay输出片外器件要求的 setup 时间（数据必须比时钟沿早这么多到）
set_driving_cell输入假定输入端口由什么单元驱动，决定输入 transition
set_load输出输出端口的片外负载电容
set_input_transition输入直接指定输入沿的转换时间（与 driving_cell 二选一）
# ---- 输入：源同步接口 ----
create_clock -name vclk_in -period 10.0        ;# 虚拟时钟
set_input_delay 2.0 -max -clock vclk_in [get_ports data_in*]
set_input_delay 0.5 -min -clock vclk_in [get_ports data_in*]
set_driving_cell -lib_cell BUFFD4 [get_ports data_in*]

# ---- 输出：reg-to-pad（见 §14）----
create_clock -name CLK_VBD -period 10.0        ;# 虚拟时钟，挂在端口上
set_output_delay 3.0 -max -clock CLK_VBD [get_ports IO_PWM*]
set_output_delay -1.0 -min -clock CLK_VBD [get_ports IO_PWM*]
set_load 5.0 [get_ports IO_PWM*]

# ---- 输出 bit 间 skew 控制（PWM 死区，见 §14.7）----
set_max_delay 2.0 -from [get_pins u_pwm/*_reg/Q] -to [get_ports IO_PWM*]
set_min_delay 1.0 -from [get_pins u_pwm/*_reg/Q] -to [get_ports IO_PWM*]

set_output_delay 的符号容易搞反：它表示片外逻辑需要占用的时间。值越大，留给片内的时间越少，约束越紧。-min 为负值很常见，表示片外器件的 hold 要求是负的（允许数据在时钟沿后一小段才稳定）。

16.5 时序例外类

第二部分（§7~§12）已详述 MCP，这里给出四兄弟的选择决策：

场景该用什么理由
路径功能上永不发生（如测试模式专用逻辑）set_false_path完全不检查，不占优化资源
跨真正异步时钟域，且有同步器set_clock_groups -asynchronous + set_max_delay -datapath_only不定时但限制绝对延迟
同步路径，数据多周期才被采样（有握手/使能保证）set_multicycle_path（setup N + hold N−1）移动检查沿，仍做真实检查
纯组合路径、或需要绝对时间上限set_max_delay / set_min_delay不依赖时钟周期
某信号在当前模式下恒为常量set_case_analysis同时简化时序和功耗分析
路径穿过某个特定点才例外加 -through精确限定作用域
# MCP：setup 与 hold 必须配对（见 §9）
set_multicycle_path -setup 2 -from [get_pins u_src/data_reg*/Q] \
                             -to   [get_pins u_dst/data_reg*/D]
set_multicycle_path -hold  1 -from [get_pins u_src/data_reg*/Q] \
                             -to   [get_pins u_dst/data_reg*/D]

# 模式信号固定：scan_mode 功能态恒为 0
set_case_analysis 0 [get_ports scan_mode]

# 测试逻辑不参与功能时序
set_false_path -from [get_ports test_*]
set_false_path -to   [get_ports debug_out*]

# 异步复位的断言沿不是时序问题（见 §2.4.1）
set_false_path -from [get_ports por_n]

16.7 优化保护类

复位同步器、CDC 同步器、模拟接口都需要防止被工具「优化掉」：

命令禁止的行为允许的行为
set_dont_touch任何修改：删除、复制、合并、改尺寸无
set_size_only删除、复制、合并、retime改驱动强度
set_dont_use库中某个单元被整体禁用—
set_ideal_network缓冲、DRC 修复综合阶段当理想线处理
# 同步器 FF 允许调驱动，但不能被 clone / merge / retime（见 §13.5）
set_size_only -all_instances [get_cells -hier *sync_q_reg*]

# 复位源聚合的组合逻辑不能被拆分或复制
set_dont_touch [get_cells -hier *rst_async_n*]

# 综合阶段把复位网络当理想线，CTS 时再真实处理
set_ideal_network [get_nets u_rst_core/rst_n]

优先用 set_size_only 而非 set_dont_touch。dont_touch 连驱动强度都不让改，结果同步器带大负载时 transition 严重超标，反而恶化亚稳态窗口。size_only 保住结构的同时允许工具修 DRC。
