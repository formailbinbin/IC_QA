0.2 先 Profiling 再优化

任何加速动作之前，先用 VCS 自带的 profiler 量一次。盲猜瓶颈是最大的时间浪费。

# 编译时打开 profiling 支持
vcs -full64 -sverilog -simprofile  <files> -o simv

# 运行：time + mem 双维度
./simv -simprofile time+mem +UVM_TESTNAME=my_test

# 生成报告
profrpt -view simprofile_dir            # 文本报告
# 或用 Verdi Performance Analyzer 图形查看
verdi -simprofile simprofile_dir

报告给出三类关键信息：

报告维度看什么典型结论
Top modules / instances哪个层次消耗时间最多如 DDR PHY、SERDES 模型占 40% → 换行为级模型
Top constructsalways / assign / SVA / DPI 各占多少SVA 占比高 → 回归关 cover
Category 分类Design / Testbench / Dump / Coverage / PLIDump + Coverage 合计 60% → 先砍这两项
Memory 热点哪个数组/MDA 占内存大 memory 的 dump 要单独关掉

经验分布：一个未优化的 UVM 回归，典型开销构成大致是——波形 dump 25~40%、debug_access+all 带来的通用化代码 15~30%、UVM 打印与字符串格式化 10~20%、覆盖率采样 5~15%，真正的 DUT 事件计算往往不到三分之一。这也解释了为什么「先砍无用工作量」比「上多核」性价比高得多。

-simprofile 本身会带来 5~15% 的额外开销，并且会抑制部分优化。它只用于分析，不要留在正式回归里。

第 一 部 分

编译加速

目标是缩短「改一行代码到能跑起来」的周期。核心是三件事：把编译并行化、只重编改动的部分、以及不要为了调试便利付出全程代价。

1. 并行编译 -j

1.1 原理

VCS 编译分为两个阶段：elaboration（分析层次、建立数据结构，基本是串行的）和 C 代码生成 + gcc 编译 + 链接（可以按文件并行）。-j 作用在后半段，把生成的大量 .c 文件分发给多个 gcc 进程。

1.2 操作 Demo

# 编译阶段并行（注意 -j 与数字之间无空格也可，两种写法都接受）
vcs -full64 -sverilog -timescale=1ns/1ps \
    -j8 \
    -f filelist.f -top tb_top -o simv

# 配合 makefile 的 -j 一起用（两层并行互不冲突）
make -j4 compile VCS_J=8

-j 的数字不要无脑拉满。gcc 进程是内存密集型的，8 个并行 gcc 在大设计上可能占 30 GB+，一旦触发 swap 会比串行更慢。LSF 环境下必须和 bsub -n 8 -R "rusage[mem=...]" 申请的资源匹配，否则会被 kill。

1.3 优缺点

优点缺点 / 代价
零风险：不改变仿真语义，结果位级一致只加速编译，对运行时间毫无影响
无需额外 license加速比受 Amdahl 限制：elaboration 串行段不能并行，大设计里这段可能占一半
一行选项，立刻生效内存占用随 N 线性增长，容易 OOM
可与所有其它选项共存N > 8 之后收益明显递减

2. 增量编译

2.1 原理

VCS 默认就是增量编译的。编译产物放在 simv.daidir/（以及 csrc/）里，再次编译时 VCS 比较源文件时间戳与依赖关系，只重新生成受影响模块的代码。

最常见的自毁行为：Makefile 里写了 clean: rm -rf simv* csrc/ *.daidir，然后每次 make 都先 clean。这等于主动关掉增量编译，把 2 分钟的增量编译变成 30 分钟的全量编译。

2.2 操作 Demo

# 正确的做法：日常编译不 clean，直接重跑同一条命令
vcs -full64 -sverilog -j8 -f filelist.f -top tb_top -o simv
# 改了 dut_core.v 之后，仍然执行上面那条命令即可（只重编受影响部分）

# 什么时候必须 clean？
#   - 改了编译选项（-debug_access、timescale、define 等）
#   - 换了 VCS 版本
#   - filelist 增删文件导致层次变化
#   - 出现莫名的 elaboration 错误（怀疑产物损坏）
make clean   # 仅在以上情况执行

Makefile 推荐把 clean 和 compile 彻底分开，避免误触：

COMP_OPT = -full64 -sverilog -j8 -timescale=1ns/1ps

compile:                      ## 增量编译（日常用）
	vcs $(COMP_OPT) -f filelist.f -top tb_top -o simv

rebuild: clean compile        ## 全量重编（显式要求时才用）

clean:
	rm -rf simv simv.daidir csrc ucli.key vc_hdrs.h

2.3 优缺点

优点缺点 / 代价
默认开启，零成本，日常改 RTL/TB 时收益最大（常 5~10x）对「改了全局 define / 顶层参数」的场景无效，依赖链一旦触顶就是全量
与 -j、partcomp 可叠加产物目录会持续增长，占磁盘；多人共用目录时容易冲突
语义完全一致，无风险偶发产物不一致会表现为诡异错误，排查时要记得先 clean 验证

3. 分区编译 partcomp

3.1 原理

把设计按层次切成多个编译分区（partition），每个分区独立 elaborate 和生成代码，然后并行编译。与 -j 的区别是：-j 只并行 gcc，partcomp 把 elaboration 这段串行瓶颈也切开了，因此在超大设计上收益远高于单纯 -j。

普通编译： [ elaborate 全设计 ]───[ codegen ]───[ gcc -j8 ]───[ link ] ↑ 串行，大设计占一半时间 partcomp： [ elab P1 ]┐ [ elab P2 ]├─并行─[ codegen 并行 ]─[ gcc 并行 ]─[ link ] [ elab P3 ]┘

3.2 操作 Demo

# 方式一：全自动分区（最省事）
vcs -full64 -sverilog -fastpartcomp=j8 \
    -f filelist.f -top tb_top -o simv

# 方式二：手工指定分区边界（对关键大模块单独成区，效果更可控）
#   partition.cfg 内容示例：
#     partition -module dut_core
#     partition -module ddr_phy
#     partition -module cpu_cluster
vcs -full64 -sverilog -partcomp -partcomp_cfg_file partition.cfg -j8 \
    -f filelist.f -top tb_top -o simv

分区的粒度原则：每个分区体量尽量均衡，且分区边界选在接口信号少、层次清晰的位置。把一个占 60% 代码量的模块单独划一个区，其它分区很快跑完却要等它，并行度等于白给。

3.3 优缺点

优点缺点 / 代价
大设计（百万门以上 / 全芯片）编译时间常降 40~60%小设计几乎无收益，分区管理反而是净开销
把串行 elaboration 并行化，突破 -j 的加速上限手工分区需要理解设计层次，配置文件要随设计演进维护
增量编译粒度变为「分区级」，改一个分区只重编该区分区边界上的跨界优化会被削弱，运行速度可能略降（几个百分点）
对回归流水线的墙钟时间改善明显某些选项（特定 debug / 特定 PLI）与 partcomp 不兼容，需查版本说明

4. 三步流程与预编译库

4.1 原理：预编译到底省掉了什么

VCS 支持两种使用方式：

  • 一步法：vcs <all files>，每次都重新分析所有源文件。
  • 三步法：vlogan（分析，产物进 library）→ vcs -top（elaborate + 编译）→ simv（运行）。

一次 vcs 编译内部其实有四段工作，预编译的作用是把前面几段的产物缓存下来，让后续编译直接从中间状态开始：

源码 ──① analyze ──→ 语法树/库单元 ──② elaborate ──→ 实例化层次 ──③ codegen ──→ C 代码 ──④ gcc+link ──→ simv ↑ ↑ ↑ └ vlogan 预编译库 └ partcomp 并行（§3） └ -j / -Mlib 缓存 （本章） （本章 4.7）

换句话说：-j 优化的是第 ④ 段，partcomp 优化的是第 ②③ 段，而预编译优化的是第 ① 段，并且是把它彻底消灭掉——稳定不变的代码永远不再被分析第二次。

哪些东西值得预编译，取决于「体量 × 变更频率」：

对象analyze 典型耗时变更频率是否值得预编译
UVM 基类库（uvm_pkg）30s ~ 2min整个项目周期内为零必须（§4.4）
第三方 VIP（PCIe/DDR/AMBA）1 ~ 10min几个月一次必须（§4.5）
标准单元 / IO / memory 库1 ~ 20min（上万 cell）流片周期内基本为零必须（§4.5）
已冻结的子系统 RTL视规模低推荐
DPI-C / PLI 的 C 代码数秒 ~ 数分钟低~中推荐（§4.6，还能免去重编 simv）
正在改的 DUT RTL / TB—每天几十次不需要，交给增量编译

4.2 库机制：synopsys_sim.setup 与 -work / -L

预编译的载体是 library（库目录）。VCS 通过当前目录下的 synopsys_sim.setup 把「逻辑库名」映射到「物理路径」：

# ---- synopsys_sim.setup ----
# 默认库：vlogan 不加 -work 时产物进这里
WORK          > DEFAULT
DEFAULT       : ./work

# 预编译库：指向团队公共只读路径
UVM_LIB       : /proj/common/libs/vcs2023/uvm_lib
VIP_LIB       : /proj/common/libs/vcs2023/vip_lib
CELL_LIB      : /proj/common/libs/vcs2023/tsmc22_cell
RTL_FROZEN    : /proj/chipA/libs/rtl_frozen

两个关键选项：

选项用在哪一步含义
-work <LIB>vlogan把分析产物写入哪个库（写方向）
-L <LIB>vcs / vloganelaborate 时到哪些库里查找未解析的模块（读方向，可多次指定，按顺序搜索）
-liblist / -v / -yvcsVerilog-XL 风格的库搜索，与 -L 并存；门级流程里常见

库是与「VCS 版本 + 关键编译选项」强绑定的。timescale、-sverilog、全局 +define、-full64 不一致时，轻则报错，重则行为诡异。公共库路径里一定要带 VCS 版本号（如 libs/vcs2023.03/），升级工具时整体重建，不要原地覆盖。

4.3 操作 Demo：完整三步流程

# ================= 一次性：建公共预编译库（由 CI 或 flow owner 跑） =================
mkdir -p /proj/common/libs/vcs2023/{vip_lib,tsmc22_cell}

# VIP / 第三方 IP
vlogan -full64 -sverilog -work VIP_LIB  -f vip_filelist.f

# 标准单元库（门级仿真用）
vlogan -full64 -v2005 -work CELL_LIB -f cell_filelist.f

# ================= 日常：项目编译 =================
# ---- Step 1：analyze（只分析自己会改的代码） ----
vlogan -full64 -sverilog -timescale=1ns/1ps \
       -ntb_opts uvm-1.2 \
       -f rtl_filelist.f -f tb_filelist.f        # 产物进 DEFAULT(./work)

# ---- Step 2：elaborate（从多个库里取已编译单元） ----
vcs -full64 -sverilog -ntb_opts uvm-1.2 -j8 \
    -L VIP_LIB -L CELL_LIB \
    -top tb_top -o simv

# ---- Step 3：run ----
./simv +UVM_TESTNAME=my_test +UVM_VERBOSITY=UVM_LOW

注意 Step 1 的 filelist 里只有自己的 RTL 和 TB——VIP 和 cell 库不在里面。这正是预编译的收益来源：日常改一行代码重编时，VCS 完全不会去碰那几万行 VIP 源码。

4.4 UVM 预编译库

UVM 是最典型、也最容易被浪费掉的预编译对象。VCS 安装包里自带已经编译好的 UVM 库，用 -ntb_opts 直接引用即可：

# ✅ 正确：使用 VCS 自带的预编译 UVM 库
vlogan -full64 -sverilog -ntb_opts uvm-1.2 -f tb_filelist.f
vcs    -full64 -sverilog -ntb_opts uvm-1.2 -j8 -top tb_top -o simv

# ❌ 常见错误：手工把 uvm_pkg.sv 塞进 filelist，每次编译都重编一遍 UVM
#   vcs -full64 -sverilog +incdir+$UVM_HOME/src $UVM_HOME/src/uvm_pkg.sv ...

如果因为要打 patch、或要用官方未随包提供的 UVM 版本而必须自己编，那就自己建一个 UVM 库，而不是每次编译都带源码：

# 一次性建库
vlogan -full64 -sverilog -work UVM_LIB \
       +incdir+$UVM_HOME/src $UVM_HOME/src/uvm_pkg.sv

# 之后所有编译只引用
vcs -full64 -sverilog -L UVM_LIB -j8 -top tb_top -o simv

UVM 的 uvm_pkg 是一个巨大的单一 package，analyze 耗时几乎全是固定成本。一个典型 TB 每天编译几十次，省掉这一分钟，一天就是半小时以上的净收益，而代价是零。

4.5 VIP 与标准单元库预编译

这两类是体量最大的「只读代码」，也是预编译收益最高的地方。

# ---- VIP：按供应商 / 协议分库，便于独立更新 ----
vlogan -full64 -sverilog -work VIP_PCIE -f $PCIE_VIP_HOME/filelist.f
vlogan -full64 -sverilog -work VIP_DDR  -f $DDR_VIP_HOME/filelist.f

vcs -full64 -sverilog -j8 -L VIP_PCIE -L VIP_DDR -top tb_top -o simv

# ---- 门级：标准单元 / IO / memory ----
# 传统写法每次编译都要扫描 -v / -y 指定的上万个 cell 文件
#   vcs ... -v /pdk/tsmc22/stdcell.v -y /pdk/tsmc22/io/ +libext+.v
# 改为预编译一次：
vlogan -full64 -v2005 -work CELL_LIB \
       /pdk/tsmc22/stdcell.v /pdk/tsmc22/io/*.v /pdk/tsmc22/mem/*.v

vcs -full64 -j8 -L CELL_LIB +nospecify +notimingcheck \
    -f netlist.f -top tb_top -o simv_gl

门级流程里这一步尤其值得做：一次全芯片网表编译中，扫描和分析 cell 库经常占掉 30~50% 的编译时间，而这些 cell 在整个流片周期内一个字都不会变。注意 cell 库的 -v2005 / -sverilog 模式和 timescale 要与主编译保持一致。

4.6 DPI-C / PLI 的预编译 .so

如果把 .c 文件直接交给 vcs，那么每次编译都会重新 gcc 一遍，而且改一行 C 代码就必须重新 link 整个 simv。更好的做法是预先编成动态库，运行时加载：

# ---- 一次性：把 C 模型编成 .so ----
gcc -fPIC -shared -O2 -I$VCS_HOME/include \
    -o libdpi_model.so  dpi_model.c  ref_model.c

# ---- 编译 simv 时不带任何 .c 文件 ----
vcs -full64 -sverilog -j8 -f filelist.f -top tb_top -o simv

# ---- 运行时动态加载（改 C 代码后只需重编 .so，simv 不用重编！）----
./simv -sv_lib libdpi_model +UVM_TESTNAME=my_test
#   注意：-sv_lib 后面不带 .so 后缀

# ---- 对比：静态链接方式（改 C 就要重 link simv，慢）----
# vcs -full64 -sverilog dpi_model.c ref_model.c -f filelist.f -o simv

这条的价值不只是编译加速，更是调试 C 参考模型时的迭代速度：从「改 C → 重编 simv（几分钟~几十分钟）」变成「改 C → 重编 .so（几秒）→ 直接跑」。对于带 C reference model 的验证环境，这往往是单项收益最大的流程改进。

预编译 .so 的 gcc 版本、-m64、以及是否 -fPIC 必须与 VCS 要求匹配；另外 FGP 多线程 场景下，.so 里的全局变量必须是线程安全的（见 §14.5）。

4.7 -Mdir / -Mlib：共享编译缓存

除了源码层面的库，VCS 还能缓存 codegen + 目标文件 这一层产物，并在多人之间共享：

选项作用典型用法
-Mdir=<dir>指定增量编译产物目录（默认 csrc）多个 TB 配置各用独立 -Mdir，避免互相踩而退化成全量编译
-Mlib=<dir>指定共享的描述符/目标文件库，可跨用户、跨工作区复用已编译模块CI 先编一份公共缓存，个人编译命中缓存直接复用
-Mupdate控制增量编译的更新行为一般不需要显式指定
# 多配置并存：各自独立的增量目录，互不污染
vcs $(OPT) -Mdir=csrc_rtl  -f rtl.f   -top tb_top -o simv_rtl
vcs $(OPT) -Mdir=csrc_gl   -f gl.f    -top tb_top -o simv_gl

# 团队共享编译缓存（CI 维护一份只读公共缓存）
vcs $(OPT) -Mlib=/proj/chipA/shared_mlib -Mdir=csrc -f filelist.f -top tb_top -o simv

-Mlib 的收益与风险都很明显：命中率高时个人全量编译可以大幅缩短，但共享缓存必须保证「同一 VCS 版本 + 同一套编译选项」，否则会出现难以定位的行为差异。实践中建议公共缓存设为只读、由 CI 统一生成，个人只读不写。具体支持情况请以本版本 vcs -help 和 User Guide 为准。

4.8 优缺点

优点缺点 / 代价
稳定代码（UVM / VIP / cell 库 / 冻结 RTL）只分析一次，长期复用流程变复杂：多出 synopsys_sim.setup 和库目录要管理
库可多人 / 多项目共享，是少数能带来团队级收益的手段库与 VCS 版本、编译选项绑定，版本升级必须全部重建
门级流程收益最大（cell 库分析常占编译时间 30~50%）公共库需要 owner 维护，权限与路径规范要先立好
DPI 用 -sv_lib 后，改 C 代码无需重编 simv选项不一致（timescale / define / 语言模式）时报错信息晦涩，排查成本高
与增量编译、partcomp、-j 完全正交，可叠加小项目收益有限，不值得为此改造流程
语义完全一致，零仿真结果风险库损坏/陈旧时会出现「源码已改但行为没变」的幽灵问题

预编译最隐蔽的坑：某人改了已冻结库里的代码，但没重建预编译库，于是所有人跑的还是旧逻辑，而源码看起来是新的。防范办法只有两条——① 公共库目录设为只读，变更只能走 CI；② 库里放一份记录了源码 git commit 的 stamp 文件，编译脚本比对不一致就报错。

5. 调试开关的代价

5.1 原理：为什么 debug_access 这么贵

VCS 默认会做大量优化：合并信号、消除中间变量、把 always 块编译成紧凑的本地代码。一旦打开 -debug_access+all，为了让你能在任意时刻读写任意信号、强制赋值、回溯驱动源，VCS 必须：

  • 保留所有中间信号与局部变量，禁止信号合并与常量传播；
  • 为每个信号生成通用的读写访问接口（value change callback 挂钩）；
  • 保留完整的层次化符号表与行号映射。

结果是编译变慢、可执行文件变大、运行速度明显下降。这是最常见也最容易修正的性能浪费。

5.2 分级使用 Demo

# ---- 回归（不需要交互调试，只要能 dump 波形）----
vcs -full64 -sverilog -j8 -debug_access+pp \
    -f filelist.f -top tb_top -o simv
#   +pp = post-process only：允许 dump FSDB 做事后分析，
#         但不支持交互式 force / 断点，性能损失小得多

# ---- 需要极致性能的长回归（完全不要调试能力）----
vcs -full64 -sverilog -j8 \
    -f filelist.f -top tb_top -o simv
#   连 -debug_access 都不加，FSDB 也不 dump，只看 log 与 coverage

# ---- 本地 debug 单个 case（才用 all）----
vcs -full64 -sverilog -j8 -debug_access+all+reverse \
    -kdb -lca -f filelist.f -top tb_top -o simv_dbg
#   -kdb 生成 Verdi 知识库，+reverse 支持反向调试

最推荐的工程做法：Makefile 里做成两个 target —— make regr 用无 debug 或 +pp，make debug 用 +all+reverse -kdb，输出成两个不同的 simv。失败的 case 用 debug 版本带同一个 seed 重跑复现，而不是让所有 case 都背着调试开销跑。

5.3 各档位对比

档位能做什么相对性能适用场景
不加任何 debug 选项只有 $display / log / coverage基准 1.0x（最快）大规模夜间回归、覆盖率收集
-debug_access+pp可 dump FSDB 事后看波形约 0.8~0.9x需要失败波形的常规回归
-debug_access+r / +w按需开读 / 写访问约 0.6~0.8x只需局部 force 的场景
-debug_access+all全信号读写、force、交互调试约 0.3~0.6x本地单 case 调试
+all+reverse -kdb -lca再加反向调试 / Verdi 全功能约 0.2~0.4x难复现 bug 的深度调试

上表的倍数是量级参考，实际值与设计规模、活动密度强相关。务必在自己的工程上实测一次：用同一个 case、同一个 seed，分别用两档编译跑 CPU time 对比，这个数据是后续说服团队改流程的依据。

第 二 部 分

运行加速（单核）

单核优化的本质只有一句话：让仿真器少做无用功。绝大多数回归的时间不是花在算 DUT 逻辑，而是花在写波形、格式化字符串、采样覆盖率这些「为了调试方便」的附加工作上。

6. 波形 dump 策略

6.1 原理

dump 的代价来自两处：每个被 dump 信号上挂的 value-change callback（每次翻转都要回调、编码、写缓冲），以及 磁盘 I/O。信号数 × 翻转率 共同决定开销，所以全层次全时间 dump 是最昂贵的做法。

6.2 操作 Demo

// ---- 反面教材：全程全层次，最慢 ----
initial begin
    $fsdbDumpfile("wave.fsdb");
    $fsdbDumpvars(0, tb_top);      // 深度 0 = 无限深，整个 TB 全 dump
    $fsdbDumpMDA();                // 所有多维数组/memory 也 dump
end

// ---- 推荐：限层次 + 限范围 + 可控开关 ----
initial begin
    if ($test$plusargs("DUMP_FSDB")) begin
        $fsdbDumpfile("wave.fsdb");
        // 只 dump DUT 的 3 层，不碰 TB（TB 对象多、变化频繁）
        $fsdbDumpvars(3, tb_top.u_dut);
        $fsdbDumpon;
    end
end

// ---- 按时间窗 dump：只抓故障区间 ----
initial begin
    if ($value$plusargs("DUMP_START=%d", t_start)) begin
        $fsdbDumpfile("wave.fsdb");
        $fsdbDumpvars(0, tb_top.u_dut);
        $fsdbDumpoff;                 // 先关
        #(t_start) $fsdbDumpon;       // 到点再开
        #(t_win)   $fsdbDumpoff;      // 窗口结束立刻关
    end
end

运行时的配合用法：

# 回归：完全不 dump
./simv +UVM_TESTNAME=my_test +ntb_random_seed=1234

# 失败后用同一 seed 重跑并只抓关键窗口
./simv +UVM_TESTNAME=my_test +ntb_random_seed=1234 \
       +DUMP_FSDB +DUMP_START=1000000

# 限制 FSDB 体积与压缩行为
./simv +fsdb+autoflush=off       \  # 关掉实时 flush，批量写盘
       +fsdbfile+wave.fsdb

6.3 几个关键取舍

做法效果代价 / 风险
限制层次深度 $fsdbDumpvars(3, dut)信号数锐减，常省 50%+ dump 开销深层信号没波形，debug 时可能要重跑
不 dump TB（只 dump DUT）避开 UVM 对象 / 动态数组的高频变化TB 侧问题看不到，需靠 log 定位
时间窗 dump长 case 上收益最大（如只抓最后 1 ms）必须先知道故障大致时刻，一般靠二次重跑
不 dump memory / MDA大 memory 的 dump 开销极高，关掉收益显著需要看 memory 内容时得改用 backdoor 打印
FSDB 替代 VCD / VPDFSDB 体积小、写入快、Verdi 原生支持需要 Verdi / novas 库 license
关 autoflush减少频繁小 I/O仿真崩溃时末尾波形可能丢失

工程上最省事且有效的组合：回归默认不 dump；CI 跑 +DUMP_FSDB 只对 smoke 用例开；失败 case 自动用相同 seed 重跑一次带 dump 的版本。这样既保证可调试性，又不让 99% 成功的 case 背 dump 开销。

7. UVM 打印与 verbosity

7.1 原理：为什么打印这么贵

uvm_info 的开销并不只是写文件。一条语句的完整代价是：

`uvm_info("TAG", $sformatf("addr=%0h data=%0h", addr, data), UVM_HIGH) ↓ ① $sformatf 字符串格式化 ← 即使最终不打印，参数也已经被求值和格式化！ ② 构造 uvm_report_message 对象（动态内存分配） ③ 查 verbosity 表决定是否输出 ④ 格式化成最终行（加时间戳、层次名） ⑤ 写 stdout / log 文件（I/O）

核心陷阱：`uvm_info 宏虽然会先检查 verbosity，但写成 `uvm_info("T", $sformatf(...), UVM_HIGH) 时，$sformatf 是作为实参在宏展开前就被求值的（取决于宏实现与调用方式）。在数据通路上每拍打一条的场景里，这部分格式化开销可能占到整个仿真的 10~20%。

7.2 操作 Demo

// ---- 反面：热点路径上无保护的格式化 ----
always @(posedge clk) begin
    `uvm_info("MON", $sformatf("beat %0d: data=%0h", cnt, data), UVM_HIGH)
end

// ---- 正面 1：用 uvm_report_enabled 先挡住 ----
always @(posedge clk) begin
    if (uvm_report_enabled(UVM_HIGH, UVM_INFO, "MON"))
        `uvm_info("MON", $sformatf("beat %0d: data=%0h", cnt, data), UVM_HIGH)
end

// ---- 正面 2：高频监控点直接降级或删除 ----
//   每个 transaction 打一条（而不是每拍打一条）
function void write(my_item it);
    `uvm_info("MON", it.convert2string(), UVM_MEDIUM)   // 频率低得多
endfunction
# ---- 运行时控制 ----
# 回归：最低 verbosity
./simv +UVM_TESTNAME=my_test +UVM_VERBOSITY=UVM_LOW

# 极致性能：连 UVM_LOW 也不要（只留 warning/error）
./simv +UVM_TESTNAME=my_test +UVM_VERBOSITY=UVM_NONE

# 只对某个组件开高 verbosity（debug 时精准放大）
./simv +UVM_TESTNAME=my_test +UVM_VERBOSITY=UVM_LOW \
       +uvm_set_verbosity=uvm_test_top.env.agt.mon,_ALL_,UVM_DEBUG,time,0

另一个容易忽略的点：log 文件写到 NFS 网络盘上会极慢。把 log 先写本地 /tmp 或节点本地盘，跑完再拷回，对大 log 的 case 有时能快 20%+。同理，+UVM_VERBOSITY=UVM_DEBUG 跑长 case 会产出几 GB 的 log，本身就是瓶颈。

7.3 优缺点

优点缺点 / 代价
零 license、零风险，纯改代码/选项降 verbosity 后失败现场信息变少，debug 要重跑
对 UVM 环境收益稳定（常 10~25%）加 uvm_report_enabled 保护会让代码变啰嗦
改 plusarg 即可，不需重新编译团队习惯难改，容易有人偷偷加回高频打印

8. 覆盖率与断言开销

8.1 原理

覆盖率的开销按类型差别极大：

类型选项开销说明
Line / Branch-cm line+branch低只在语句执行时置位，代价小
Condition-cm cond中每个条件表达式都要记录各子项取值
FSM-cm fsm中需识别状态机并跟踪跳转
Toggle-cm tgl高每个信号每次翻转都要记录，接近 dump 的开销
Assertion / Cover-cm assert、SVA cover高每个断言每拍都要推进状态机
Functional (covergroup)代码里的 covergroup中~高sample() 调用频率决定，高频 sample 很贵

8.2 操作 Demo

# ---- 功能回归：完全不开覆盖率 ----
vcs -full64 -sverilog -j8 -f filelist.f -top tb_top -o simv_func

# ---- 覆盖率回归：开，但限定范围 ----
#   cm_hier.cfg 内容：
#     +tree tb_top.u_dut          // 只统计 DUT
#     -tree tb_top.u_dut.u_ddr    // 排除第三方 IP
#     -tree tb_top.env            // 排除 TB
vcs -full64 -sverilog -j8 \
    -cm line+cond+fsm+branch \
    -cm_hier cm_hier.cfg \
    -cm_dir ./cov_db \
    -f filelist.f -top tb_top -o simv_cov

# ---- toggle 单独一轮跑（因为最贵）----
vcs ... -cm tgl -cm_hier tgl_only.cfg -o simv_tgl

# ---- 运行时也要指定 ----
./simv_cov -cm line+cond+fsm+branch -cm_name test_${SEED} -cm_dir ./cov_db
// ---- 断言运行时控制 ----
initial begin
    if ($test$plusargs("NO_SVA")) begin
        $assertoff(0, tb_top.u_dut);      // 关掉整个 DUT 的断言
    end
end
# 编译时关 cover property（保留 assert property）
vcs ... -assert disable_cover

# 运行时限制断言失败次数，避免刷屏拖慢
./simv -assert finish_maxfail=10

8.3 优缺点

做法优点缺点
功能回归不开 coverage省 5~20%，最直接需要额外安排覆盖率回归轮次，流程变复杂
-cm_hier 限定范围排除 TB 与第三方 IP，既省时又让覆盖率数据更有意义配置文件要维护，漏配会导致覆盖率统计口径变化
toggle 单独一轮避免最贵的项拖慢所有 case多一轮回归，管理成本上升
-assert disable_cover保留检查能力，去掉 cover 统计开销断言覆盖率缺失，签核时要补跑
$assertoff运行时灵活，无需重编关掉后失去检查能力，绝不能用在签核回归

9. 时序检查与门级优化

9.1 原理

门级（netlist）仿真的时间几乎都消耗在三件事：SDF 反标后的延迟事件调度、specify 块里的 setup/hold/width 时序检查、以及海量小单元带来的事件密度。RTL 仿真里这些开销不存在，所以这一节的选项只对门级有意义。

9.2 操作 Demo

# ---- 门级功能验证（不关心时序，只验连接与功能）----
vcs -full64 +nospecify +notimingcheck \
    +delay_mode_zero \
    -f netlist.f -top tb_top -o simv_zero
#   +nospecify      : 忽略 specify 块（路径延迟 + 时序检查一起关）
#   +notimingcheck  : 只关时序检查，保留路径延迟
#   +delay_mode_zero: 所有延迟当 0，等价于 RTL 速度

# ---- 门级时序验证（必须反标，但做裁剪）----
vcs -full64 -sdf max:tb_top.u_dut:dut.sdf \
    +neg_tchk \
    +sdfverbose \
    -f netlist.f -top tb_top -o simv_sdf

# ---- 只反标关键模块，其余用单位延迟 ----
#   在 SDF 命令文件里限定 scope，或分模块 -sdf 多次指定

四个 delay mode 的关系：+delay_mode_zero（全 0，最快）→ +delay_mode_unit（全部 1 个时间单位）→ +delay_mode_path（只用 specify 路径延迟）→ +delay_mode_distributed（用分布延迟）。越往右越真实也越慢。

9.3 优缺点

选项优点缺点 / 风险
+notimingcheck门级常提速 2~5x不再报 setup/hold violation，时序问题完全漏掉
+nospecify比 notimingcheck 更快（连路径延迟计算也省）路径延迟消失，时序行为与真实硅片差异大
+delay_mode_zero接近 RTL 速度完全失去时序意义，只能做连接性/功能检查
局部 SDF 反标在精度与速度间折中未反标部分的时序问题会漏掉，范围要有依据

绝对不能搞混的一点：这些选项用于加速门级功能验证，不能替代 STA。但反过来，如果你的门级回归目的就是验时序（比如验异步复位 recovery、验 SDF 反标正确性），那么关掉 timing check 就等于这轮回归白跑。先明确这一轮门级跑的是「功能」还是「时序」，再决定开关。

10. +rad 与两态仿真

10.1 Radiant 优化 +rad

VCS 的 Radiant Technology 是一组更激进的编译期优化：更强的表达式合并、调度优化、本地化变量等。对 RTL 与门级都有效。

# 编译时打开（需要 Radiant license）
vcs -full64 -sverilog -j8 +rad \
    -f filelist.f -top tb_top -o simv

# 可配合 radiant 配置文件做细粒度控制
vcs ... +rad +optconfigfile+rad.cfg
优点缺点 / 代价
典型提速 1.3~2x，部分门级场景更高需要单独的 Radiant license
只需加一个编译选项，不改代码编译时间增加（优化本身要花时间）
不改变仿真语义（标准情况下结果一致）与 -debug_access+all 冲突：调试开关会抵消大部分优化
可与 -j、FGP 叠加极少数情况下会暴露出代码里本就存在的竞争问题

10.2 两态仿真

标准 Verilog 是四态的（0/1/X/Z）。两态仿真把 X/Z 全部当作 0/1 处理，省掉每个信号额外的一位编码与 X 传播逻辑。

# 两态仿真（选项名随版本略有差异，以本地 vcs -help 为准）
vcs -full64 -sverilog +twostate -f filelist.f -top tb_top -o simv_2s

# 配合 X-prop 分析：先用四态 + xprop 跑完 X 检查，确认干净后再上两态
vcs -full64 -sverilog -xprop=tmerge -f filelist.f -o simv_xprop

两态仿真的核心风险：复位前的未初始化状态、多驱动冲突、总线浮空，这些本应表现为 X 的问题会被「假装」成确定值，bug 被掩盖而不是被发现。只有在已经用四态 + X-prop 充分验证过复位与初始化之后，才能在后续的大规模性能回归里用两态。绝不能作为默认模式。

优点缺点 / 代价
典型提速 1.2~2x，内存占用也降低X 传播能力丧失，复位 / 初始化 bug 会被掩盖
对 X 敏感度低的成熟模块很划算与四态仿真结果可能不一致，需要单独做一致性确认
可与其它运行期优化叠加部分 IP / VIP 模型假设四态语义，可能直接行为异常

11. TB 代码级优化

11.1 几类典型的 TB 瓶颈

瓶颈表现优化手段
约束求解（constraint solving）profiler 里 solver 占比高；大数组 / 复杂关系约束拆分 randomize 粒度、用 std::randomize 局部随机、避免大 foreach 约束、减少 solve...before
轮询式等待forever #1 if(sig) ... 这类代码产生海量无用事件改成事件驱动：@(posedge sig) / wait(cond)
对象频繁 newGC 压力大，内存抖动复用 transaction 对象，用对象池；避免每拍 new
DPI / C 模型调用每次调用有上下文切换与数据拷贝成本降低调用频率（批量传数据）、避免传大数组按值拷贝
Scoreboard 查找线性遍历队列，O(n²) 行为改用关联数组按 key 索引
无意义的长延时#10000 空等、复位等待过长改为事件握手；复位时间缩短到满足协议的最小值

11.2 操作 Demo

// ---- 反面：轮询，每个时间单位都醒一次 ----
forever begin
    #1;
    if (vif.valid && vif.ready) collect_item();
end

// ---- 正面：事件驱动，只在真正发生时醒 ----
forever begin
    @(posedge vif.clk iff (vif.valid && vif.ready));
    collect_item();
end
// ---- 反面：一次随机化整个大对象 ----
class big_item;
    rand bit [31:0] data[1024];

12. Save / Restore

12.1 原理

SoC 级仿真常有一段冗长且每个 case 都完全相同的开头：上电、PLL 锁定、DDR 初始化训练、bootrom 加载、OS 启动……这段可能占几十分钟。Save/Restore 的思路是：跑一次，把仿真器的完整状态存成快照，后续所有 case 从快照继续跑。

传统： case1: [ boot 30min ][ test 2min ] case2: [ boot 30min ][ test 2min ] case3: [ boot 30min ][ test 2min ] 总计 96 min S/R： 一次: [ boot 30min ]→ save snapshot case1: restore + [ test 2min ] case2: restore + [ test 2min ] case3: restore + [ test 2min ] 总计 36 min

12.2 操作 Demo

# ---- 方式一：UCLI 交互/脚本保存 ----
# save.ucli 内容：
#   run 500us           ;# 跑到 boot 完成的时刻
#   save boot.snapshot  ;# 存快照
#   quit
./simv -ucli -i save.ucli

# ---- 后续 case 从快照恢复 ----
./simv -r boot.snapshot +UVM_TESTNAME=test_a
./simv -r boot.snapshot +UVM_TESTNAME=test_b

# ---- 方式二：命令行直接指定 ----
./simv -save boot.snapshot +boot_only      # 跑到某点自动 save
./simv -restore boot.snapshot +UVM_TESTNAME=test_a
// ---- 更轻量的替代：backdoor 加载，跳过 boot 过程 ----
// 不走真实 flash/DDR 训练流程，直接把 image 写进 memory 模型
initial begin
    if ($test$plusargs("FAST_BOOT")) begin
        $readmemh("boot_image.hex", tb_top.u_dut.u_sram.mem);
        force tb_top.u_dut.u_cpu.boot_done = 1'b1;
        force tb_top.u_dut.u_pll.locked    = 1'b1;
        #1us;
        release tb_top.u_dut.u_cpu.boot_done;
    end
end

手段优点缺点 / 风险
Save / RestoreSoC 级收益巨大（常 2~5x 墙钟）；完全保真，状态与真实跑一致快照文件大（几 GB）；设计/TB 一改就得重建快照；含 DPI/C 模型或打开文件句柄时 restore 可能失败
Backdoor 加载无快照管理成本，灵活；可跳过任意慢流程跳过的流程本身就不再被验证；force/release 使用不当会造成状态不一致
缩短复位 / 等待时间最简单，无副作用可能违反协议规定的最小复位时长，掩盖真实上电问题

第 三 部 分

多核加速

前两部分都是「少做无用功」，这一部分是「同样的工作用更多核去做」。核心是分清编译并行（-j）、细粒度并行（FGP，切分仿真内核本身）及多机回归。历史上 VCS 还提供过应用级并行（ALP）；其旧式 -parallel+... 语法并非所有版本支持，本文单列说明，不能默认套用。

14. FGP 细粒度并行

14.1 原理

传统仿真是单线程的：事件队列里的事件一个一个取出来求值。FGP（Fine-Grained Parallelism）把同一个时间片内彼此独立的事件分发到多个线程并行求值，线程之间在每个时间片边界同步。

单线程： 时间 t: [ e1 ][ e2 ][ e3 ][ e4 ][ e5 ][ e6 ] ──→ 时间 t+1 └──────── 串行执行 6 个事件 ────────┘ FGP(4): 时间 t: T0:[ e1 ][ e5 ] T1:[ e2 ][ e6 ] ← 并行求值 T2:[ e3 ] T3:[ e4 ] └── barrier 同步 ──┘ ──→ 时间 t+1

关键推论：加速比取决于「每个时间片内有多少可并行的独立工作量」。如果每个时间片只有寥寥几个事件（小设计、TB 主导），线程同步的开销会超过并行收益，甚至变慢。

14.2 两种工作模式

模式选项说明
单步（默认）-fgpelaboration 与 FGP 代码生成一起做，流程简单
多步-fgp=multi_steps把 elaborate 与 FGP codegen 分离成两步，对超大设计更稳、内存峰值更低

14.3 操作 Demo

# ---- Step 1：编译时打开 FGP ----
vcs -full64 -sverilog -j8 \
    -fgp \
    -f netlist.f -top tb_top -o simv_fgp

# 超大设计用多步模式
vcs -full64 -sverilog -j8 \
    -fgp=multi_steps \
    -f netlist.f -top tb_top -o simv_fgp

# ---- Step 2：运行时指定线程数 ----
./simv_fgp -fgp=num_threads:4 +UVM_TESTNAME=my_test

# 也可在编译时就固定线程数
vcs ... -fgp=num_threads:4 -o simv_fgp
./simv_fgp +UVM_TESTNAME=my_test

# ---- Step 3：LSF 上必须申请匹配的核数 ----
bsub -n 4 -R "span[hosts=1]" \
     ./simv_fgp -fgp=num_threads:4 +UVM_TESTNAME=my_test

14.5 适用与不适用

判定场景原因
✅ 很适合大规模门级 netlist + SDF 反标仿真（百万门以上）事件密度极高，单个时间片内有大量独立单元可并行求值；常得 2~4x
✅ 适合全芯片多时钟域、高翻转活动的 RTL 回归设计侧工作量大，并行度足够
✅ 适合大型 memory / 多核 CPU cluster 的长时间仿真DUT 计算主导，TB 占比低
⚠️ 收益有限中小规模 RTL（单模块 / 子系统级）每时间片事件少，同步开销占比高
❌ 不适合TB 主导的环境（重随机化、重 UVM 打印、重 scoreboard）TB 是串行的类/线程语义，FGP 无法并行；此时应做 §11 的 TB 优化
❌ 不适合大量 PLI / 非线程安全的 DPI-C 模型C 侧全局状态在多线程下不安全，可能崩溃或结果错乱
❌ 冲突同时开 -debug_access+all 和全量 dump调试开销与 dump 成为新瓶颈，FGP 收益被抵消

14.6 一致性比对流程（必做）

FGP 最需要警惕的风险：并行求值可能改变同一时间片内事件的执行顺序。对于严格遵守 SystemVerilog 调度语义的代码，结果应当一致；但如果代码里本来就存在竞争（race）——比如用阻塞赋值跨模块通信、对同一变量在不同 always 块里读写、依赖 #0 的执行顺序——那么单核与 FGP 的结果可能不同。这不是 FGP 的 bug，而是 FGP 把你代码里本已存在的隐患暴露了出来。

上线 FGP 之前必须做的比对：

# 1. 同一 seed 跑单核与 FGP，比对 log
./simv     +UVM_TESTNAME=my_test +ntb_random_seed=1234 -l base.log
./simv_fgp -fgp=num_threads:4 \
           +UVM_TESTNAME=my_test +ntb_random_seed=1234 -l fgp.log
diff <(grep -v "simulation time\|CPU Time" base.log) \
     <(grep -v "simulation time\|CPU Time" fgp.log)

# 2. 比对波形（关键信号）
#    两边都 dump 同样范围的 FSDB，用 Verdi 的 compare 或 fsdbreport 比
fsdbreport -s base.fsdb -o base.txt  tb_top.u_dut.key_sig*
fsdbreport -s fgp.fsdb  -o fgp.txt   tb_top.u_dut.key_sig*
diff base.txt fgp.txt

# 3. 比对覆盖率数据库（确认激励分布未变）
urg -dir base_cov.vdb fgp_cov.vdb -report cmp_rpt

# 4. 跑一轮完整回归，确认 pass/fail 结果集完全相同

比对发现差异时，正确动作是去查代码里的竞争（用 vcs +race 或 Verdi race 分析），而不是「因为不一致所以放弃 FGP」。修掉竞争对单核仿真的稳定性也是净收益。

15. ALP 应用级并行：历史功能与版本核验

15.1 ALP 是什么

ALP（Application Level Parallelism）是 VCS 历史版本提供的多核机制：不改变仿真内核事件调度，而是将 testbench、断言、覆盖率、debug 等验证应用工作分配到多个核。该概念曾由 Synopsys 对外发布，但具体命令、可并行对象和许可证条件均随发行版本变化。

历史 ALP 概念：仿真内核 ─→ 验证应用（TB / SVA / coverage / debug） └─ 在多个核上并发执行 注意：这是机制说明，不表示任意 VCS 版本均有相同命令或均支持该功能。

15.2 本文已核验版本：R-2020.12-SP2 不支持

本机实际编译日志已确认：VCS R-2020.12-SP2 中 -parallel 已废弃。加入 -parallel+assert 会报 Error-[OBSOLETE_OPTION] 并使编译失败。因此以下旧示例均不能用于该版本：-parallel+assert、-parallel+dump、-parallel+coverage。

# R-2020.12-SP2：不要使用（会编译报 obsolete）
vcs ... -parallel+assert
vcs ... -parallel+dump
vcs ... -parallel+coverage

# 此版本可用的编译并行 / 分区编译
vcs ... -j8 -fastpartcomp=j4 -Mupdate -o simv

该版本的错误提示仅给出一项替换：-parallel+profile 改为 -profiler；但 -profiler 只用于定位性能瓶颈，不提供 ALP 加速。

15.3 其他版本如何核验

不能由版本号推断 ALP 可用性。只有本地帮助或 User Guide 明确列出相应子项，才可以使用；同时还须确认所需 license。先执行：

vcs -help | grep -i -A 8 -B 3 parallel
# 再查本机对应版本 User Guide 的 Multicore / ALP 章节
核验结果动作
明确列出 -parallel+<子项>按该版本手册配置，先以固定 seed 做功能一致性和性能对比
提示 obsolete，或帮助中未列出不要使用；改用减少 dump / 覆盖率范围、-j / -fastpartcomp、FGP（若手册支持）或 LSF case 级并发

R-2020.12-SP2 的实际选择顺序：先不 dump / 限 dump 范围、分级跑覆盖率（§6、§8）→ 编译用 -j、-fastpartcomp、-Mupdate → 单 case 的内核瓶颈才评估 FGP → 多 case 回归由 LSF 并发。不要把历史 ALP 当作当前版本的可执行配置。

16. SmartCompile 与多机回归

16.1 多机回归：吞吐 vs 延迟

必须区分两个目标：

目标含义解法
延迟（latency）单个 case 多快跑完FGP、+rad、减少 dump、Save/Restore
吞吐（throughput）5000 个 case 的回归多久全部跑完LSF/SGE 多机并行分发，每 case 单核

这是最重要的一个判断：如果回归总时间的瓶颈是 case 数量多，那么多机分发（吞吐）的性价比远高于 FGP（延迟）。同样的 license 预算，用来并发跑 100 个单核 case，通常比用来给 25 个 case 各开 4 线程更划算。FGP 的真正价值在于「单个 case 长到无法容忍」的情况，比如一个门级 case 要跑 20 小时。

手段说明适用 / 代价
抽象模型替换把 DDR PHY、SERDES、PLL、ADC 等慢模型换成行为级 / C 模型；flash boot 换 $readmemh backdoor收益极大（有时 5x+），但被替换的部分不再被验证，需单独在 IP 级验收

最后一条特别值得强调：仿真内核是典型的单线程、主频敏感、cache 敏感负载。把 job 调度到主频 3.5 GHz 的机器而不是 2.2 GHz 的机器上，收益可能超过你折腾半天选项的总和。排查性能问题时先确认一下跑在什么机器上。

16ALP（历史功能）运行（多核）仅旧版且手册明确支持时评估版本 / license 相关低低；R-2020.12-SP2 不可用
17LSF 多机回归回归吞吐近线性（受 license 限）sim license无中
18抽象模型替换运行1.5~5x+无中（需 IP 级补验）高
19本地盘 I/O / 高主频机型运行1.1~1.3x无无低
20硬件加速 emulation运行100~10000x专用设备低（但调试能力弱）极高

把表读薄一点：前 10 项（1 ~ 8，含 4b/4c）全部是「零 license、低风险、低成本」，几乎所有工程都应该先做完这些再谈别的。真正需要花钱的是 10、15、16、20，而它们的前提都是「前面这些已经做完，瓶颈确实在内核或辅助任务上」。

19. 分级回归配置模板

把上面的选择固化到流程里。核心思想是不同目的的回归用不同的编译产物和运行选项，不要用一套配置跑所有事。

轮次目的编译选项运行选项覆盖率波形
smoke提交门禁，快速发现明显破坏-j8（增量）+UVM_VERBOSITY=UVM_LOW不开不 dump
功能回归夜间大规模随机，追 bug-j8 -debug_access+pp+UVM_VERBOSITY=UVM_LOW不开失败才重跑 dump
覆盖率回归收集覆盖率做签核-j8 -cm line+cond+fsm+branch -cm_hier cfg-cm ... -cm_name $SEED开（限范围）不 dump
toggle 轮翻转覆盖率（最贵，单独跑）-cm tgl -cm_hier tgl.cfg-cm tgl仅 toggle不 dump
门级功能验 netlist 连接与功能+nospecify +delay_mode_zero—不开按需
门级时序验 SDF 反标后的时序行为-sdf max:... +neg_tchk，可加 -fgp-fgp=num_threads:4不开关键窗口
debug复现并调试单个失败 case-debug_access+all+reverse -kdb -lca同 seed + 全 dump不开全 dump
# ---- Makefile 模板 ----
VCS_BASE  = -full64 -sverilog -timescale=1ns/1ps -j8 -ntb_opts uvm-1.2
LIBS      = -L VIP_LIB -L CELL_LIB          # 预编译库（§4）
FILELIST  = -f filelist.f -top tb_top

# ---- 一次性：预编译库与 C 模型（由 CI 维护，日常不跑）----
libs:
	vlogan -full64 -sverilog -work VIP_LIB  -f vip_filelist.f
	vlogan -full64 -v2005    -work CELL_LIB -f cell_filelist.f

dpi:
	gcc -fPIC -shared -O2 -I$(VCS_HOME)/include -o libdpi_model.so dpi_model.c

# ---- 日常：analyze 只过自己的代码 ----
analyze:
	vlogan $(VCS_BASE) -f rtl_filelist.f -f tb_filelist.f

# 门禁 / 功能回归用：轻量，可事后看波形
simv_regr:
	vcs $(VCS_BASE) $(LIBS) -debug_access+pp -Mdir=csrc_regr $(FILELIST) -o simv_regr

# 覆盖率回归用
simv_cov:
	vcs $(VCS_BASE) $(LIBS) -cm line+cond+fsm+branch -cm_hier cm_hier.cfg \
	    -Mdir=csrc_cov $(FILELIST) -o simv_cov

# 调试用：全开
simv_dbg:
	vcs $(VCS_BASE) $(LIBS) -debug_access+all+reverse -kdb -lca \
	    -Mdir=csrc_dbg $(FILELIST) -o simv_dbg

# 运行目标（-sv_lib 动态加载 C 模型，改 C 不用重编 simv）
run_regr: simv_regr
	./simv_regr -sv_lib libdpi_model \
	            +UVM_TESTNAME=$(TEST) +ntb_random_seed=$(SEED) \
	            +UVM_VERBOSITY=UVM_LOW -l logs/$(TEST)_$(SEED).log

# 失败复现：同 seed + 全波形
rerun_dbg: simv_dbg
	./simv_dbg -sv_lib libdpi_model \
	           +UVM_TESTNAME=$(TEST) +ntb_random_seed=$(SEED) \
	           +UVM_VERBOSITY=UVM_HIGH +DUMP_FSDB \
	           -l logs/$(TEST)_$(SEED)_dbg.log

这个模板有两个关键设计：① 把「跑得快」和「调得动」分到两个可执行文件上，而不是让所有 case 都背着调试开销跑；② 三个 target 各用独立 -Mdir，否则它们会互相覆盖增量产物，每次切换 target 都退化成全量编译（§4.7）。

20. 易错点与风险清单

#错误 / 误解后果正确做法
1没 profiling 就乱加选项在无效选项上浪费时间和 license先 -simprofile time+mem（§0.2）
2每次 make 都先 clean增量编译失效，编译慢 5~10xclean 与 compile 分离（§2）
3混淆「编译加速」和「运行加速」加了 -j64 却抱怨仿真不变快-j/partcomp 只管编译（§13）
4回归也用 -debug_access+all运行慢 2~3x，且抵消 +rad/FGP 收益回归用 +pp 或不加（§5）
5全程全层次 $fsdbDumpvars(0, tb_top)dump 成为最大瓶颈，FSDB 几十 GB限层次 + 限范围 + 时间窗（§6）
6热点路径上无保护的 $sformatf即使不打印也付格式化代价uvm_report_enabled 先挡（§7）
7TB 瓶颈的环境上开 FGP花了多核 license 却几乎无收益，甚至变慢先看 profiler 分类再决定（§18）
8FGP 上线不做一致性比对隐藏的 race 导致结果不一致却没人发现单核 vs FGP 比 log / 波形 / 覆盖率（§14.6）
9FGP 线程数拉到 8 / 16收益饱和，license 浪费扫描找拐点，一般 2~4（§14.4）
10LSF 上开 FGP 不加 span[hosts=1]线程被分到不同机器，启动失败或性能异常bsub -n 4 -R "span[hosts=1]"（§14.3）
11签核回归里留着 $assertoff / +notimingcheck验证能力被阉割，问题漏到硅上加速选项与签核配置严格分离（§19）
12把两态仿真当默认模式复位 / 初始化 X 问题被掩盖先四态 + xprop 过关，再用两态跑性能回归（§10.2）
13所有 case 都 Save/Restore，不再跑完整 bootboot 流程本身的 bug 永远不会被发现保留至少一个完整 boot 用例定期跑（§12）
14把 randomize() 改成 $urandom 没确认分布跑得快但验得少，覆盖率悄悄下降优化前后比对覆盖率数据库（§11.3）
15log / FSDB 直接写 NFSI/O 成为瓶颈，大 log case 慢 20%+写本地盘跑完再拷回（§16.3）
16-j 与 LSF 申请的核数/内存不匹配job 被 kill 或触发 swap 比串行更慢-j 数与 bsub -n 对齐（§1.2）
17case 数多的回归去优化单 case 延迟方向错误，投入产出比极低先判断是吞吐问题还是延迟问题（§16.1）
18假设选项名在所有 VCS 版本一致选项被忽略（有时只给 warning）却以为生效vcs -help | grep 确认 + 查本版本 UG；看 log 里是否有选项被忽略的提示
19把 uvm_pkg.sv 加进 filelist 每次重编每次编译白送几十秒到两分钟用 -ntb_opts uvm-1.2 引用预编译库（§4.4）
20门级编译每次用 -v/-y 扫 cell 库cell 库分析占编译时间 30~50%，且天天重复vlogan -work CELL_LIB 预编译一次（§4.5）
21预编译库与 VCS 版本/选项不匹配报错晦涩，或行为诡异难以定位库路径带版本号，升级时整体重建（§4.2）
22改了冻结库源码但没重建预编译库全组跑的还是旧逻辑，而源码看着是新的公共库只读 + git commit stamp 校验（§4.8）
23多个编译配置共用同一个 -Mdir增量产物互相覆盖，每次切配置都全量重编每个 target 独立 -Mdir（§4.7）
24C 模型 .c 直接交给 vcs 静态链接改一行 C 就要重 link 整个 simv编成 .so 用 -sv_lib 加载（§4.6）

贯穿全文最重要的一条原则：所有加速手段本质上都是在「速度」与「验证完整性 / 可调试性」之间做交换。+notimingcheck 换掉的是时序检查能力，两态换掉的是 X 传播，跳 boot 换掉的是上电流程验证，少 dump 换掉的是失败现场。每一次交换都必须是有意识的、并且在流程上有补偿安排的——否则就不是加速，而是偷偷降低了验证质量。
