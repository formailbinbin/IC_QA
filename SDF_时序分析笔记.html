数字芯片时序笔记

SDF 三元组 · Setup / Hold 原理 · 门级仿真 Corner 搭配

1 · SDF 三元组 (min : typ : max)

SDF 里所有延迟与时序检查值都是三元组，形式 (min:typ:max)，三者对应不同的 PVT corner。

字段含义典型 corner主要用途
min最快路径延迟FF / 高压 / 低温（best case）hold 保持时间检查
typ典型值TT / 标称电压 / 常温功能仿真、参考
max最慢路径延迟SS / 低压 / 高温（worst case）setup 建立时间检查

语法示例

(IOPATH A Y (0.082:0.145:0.263) (0.079:0.141:0.258))
                ↑上升延迟           ↑下降延迟
(SETUP (posedge D) (posedge CK) (0.045:0.071:0.112))
(INTERCONNECT u1/Y u2/A (0.011:0.019:0.034))

每个外层括号先分 (上升) (下降)，每个里面再是 min:typ:max。

字段可以留空

写法含义
(0.1:0.2:0.3)三个值齐全
(0.1::0.3)typ 缺省
(::0.3)只给 max
(::)全缺省，由工具 / 库模型决定
(0.263)单值，三个 corner 同值

工程实践中的坑

多数后端流程不会在一份 SDF 里塞三个 corner PrimeTime write_sdf 通常每个 corner 单独导出一份，文件里三元组三个值相同，例如 (0.263:0.263:0.263)，再靠 -delay_type min/max 或 corner-specific SDF 文件区分。想要真正 min:typ:max 合一，需要多 corner 合并脚本，或用 -delay_type min_max 只填两端。
timing check 的三元组语义和延迟不同 SETUP / HOLD / RECOVERY / REMOVAL / WIDTH 等检查值的 min/max 不代表快慢 corner，而是检查门限的取值范围；工程上通常三个填相同值。
INTERCONNECT 的 min 值要留意 若反标后 min 值异常偏小（接近 0），常是寄生提取 corner 配错（例如用了 cbest 却没配对应的器件 corner），会导致 hold 虚假通过 —— 这是最危险的一类静默错误。

2 · 门级仿真 Corner 搭配原理

经典搭配 功能 / setup 验证 → max SDF + SS corner 库 + +maxdelays
hold 验证 → min SDF + FF corner 库 + +mindelays
两者都要跑，单跑 max 会漏掉全部 hold 违例。

2.1 setup 与 hold 的"受害方向"相反

setup slack = T_period + T_clk_capture - (T_clk_launch + T_datapath_max + T_setup)
hold  slack = T_clk_launch + T_datapath_min - (T_clk_capture + T_hold)
  • setup：数据路径延迟越大越容易违例 → 用最慢延迟去压 → max
  • hold：数据路径延迟越小越容易违例 → 用最快延迟去压 → min

方向相反的两个极端，同一份网表必须跑两遍。

2.2 为什么慢 corner 是 SS / 低压 / 高温

晶体管驱动能力 ∝ 载流子迁移率与过驱动电压 (Vgs − Vth)：

因素慢（max delay）快（min delay）
工艺 PSS：阈值电压高、驱动弱FF：阈值低、驱动强
电压 V低压：过驱动小高压
温度 T高温：迁移率下降低温

所以 SS + Vmin + Tmax 给出最大延迟，FF + Vmax + Tmin 给出最小延迟。

温度反转 (Temperature Inversion) 先进节点（16nm 以下、低压工作）下低温反而更慢。此时 corner 必须按 PDK 实际标定来挑，不能机械套"高温最慢"。

2.3 为什么 SDF 和库必须配对，不能混用

门级仿真的时序由两部分拼出来：

SDF 提供 IOPATH 单元延迟
INTERCONNECT 线延迟
SETUP/HOLD/RECREM/WIDTH 检查门限值
库仿真模型 (.v) 提供 逻辑功能
specify 块骨架
SDF 未覆盖路径的默认值

关键在于 检查门限本身也是 corner 相关的。同一个单元的 $hold 要求在 FF 和 SS 下数值不同（通常 FF 下 hold 要求更苛刻）。

混搭的两种典型错误 ① max SDF 做 hold 验证：拿 SS 下宽松的 hold 门限，去量一条你又故意让它跑慢的路径 —— 双重乐观，等于没验。

② FF 库 + max SDF：SDF 未标注的路径会取库里的 FF 值，与已标注部分不自洽，报出来的违例真假难辨。

2.4 为什么 hold 那一遍绝不能省

setup 违例hold 违例
与频率关系公式含 T_period，有关公式不含 T_period，无关
本质路径太慢，赶不上下一拍纯粹的竞争 race：数据在同一拍内穿过组合逻辑把下级 FF 冲掉
流片后能否抢救能：降主频出货不能：任何频率/电压配置都无法规避 → 直接报废
hold 风险最集中的地方 DFT scan shift 模式：扫描链上相邻 FF 之间几乎没有组合逻辑，T_datapath_min 极小。此外跨异步边界、时钟门控路径也是高危区。FF corner 的 scan shift GLS 是必跑项。

2.5 GLS 的定位：不是替代 STA

GLS 对 clock 和 data 用同一个 corner，而 STA 会做 OCV / AOCV、CRPR（clock reconvergence pessimism removal）、derate 等更精细的处理。

  • 时序是否收敛 → 看 STA，GLS 不负责签核时序
  • GLS 要抓的是 STA 看不见的东西：
    • 复位序列、上电初始化导致的 X 传播
    • SDC 里 set_false_path / set_multicycle_path 用错（STA 被你骗了，仿真骗不了）
    • 异步 FIFO、握手、跨时钟域的真实行为
    • 门控时钟的使能时序、DFT 模式切换
    • 库模型 x_transport、负 setup-hold 窗口带来的实际 X

一句话：corner 的选择决定了你能暴露哪一类竞争，两个极端都跑才覆盖得住。

3 · Setup 时序图：edge N 发出，edge N+1 接收

3.1 电路模型（Setup / Hold 共用）

            ┌────────┐                              ┌────────┐
  D ───────►│D      Q├──►  组合逻辑  ──────────────►│D      Q├──►
            │  FF1   │    T_datapath                │  FF2   │
            │      CK│                              │      CK│
            └────┬───┘                              └────┬───┘
                 ▲                                       ▲
                 │ T_clk_launch                          │ T_clk_capture
                 └──────────── clk 时钟树 ───────────────┘
                                   ▲
                                   │
                              clk 源（t=0 基准）
时间约定 原点 t = 0 取时钟源的某个上升沿，称 edge N；下一沿 edge N+1 在 t = T_period。
T_datapath 已包含 FF1 的 CK→Q、组合逻辑延迟、以及走线延迟。

FF1.CK│________________│‾‾‾│____________________________________________
                       ▲ 发射沿到达 FF1
                       │

      旧数据           │        │ 新数据开始翻转

                                      └───slack───┘

3.3 不等式推导

要求：数据必须在捕获沿之前至少 T_setup 就已稳定。

   T_clk_launch + T_datapath_max + T_setup  ≤  T_period + T_clk_capture
   └──────────── data arrival + setup 要求 ─┘     └─ capture edge 到达时刻 ─┘

移项：

   setup slack = (T_period + T_clk_capture) - (T_clk_launch + T_datapath_max + T_setup)
                 └──── required time ─────┘   └────────── arrival time ──────────┘

3.4 三个直觉

  • 公式含 T_period → setup 与频率有关。降频使 T_period 变大、slack 变大，所以 setup 违例能靠降频抢救。
  • 用 T_datapath_max → 最慢路径最危险 → 对应 max SS / 低压 / 高温 + max SDF。
  • 时钟歪斜 skew = T_clk_capture − T_clk_launch 为正（捕获端更晚到）时，setup slack 变大，是在帮忙。

4 · Hold 时序图：edge N 发出，同一个 edge N 接收

最容易糊的地方 hold 检查里没有 edge N+1。发射沿和捕获沿是同一个时钟沿。这就是为什么 hold 公式里不出现 T_period。

4.1 波形

时间 ─────────────────────────────────────────────────────────────►
      0
      │
clk源 │‾‾‾│_______________________________________________________
      ▲
      │ edge N（launch 和 capture 用的是同一个沿）
      │

FF1.CK│________________│‾‾‾│____________________________________
                       ▲ 发射沿到达 FF1
                       │
                       │◄──── T_datapath_min ────►│
                       │                          │
FF2.D ═══════════════════════════════════════════╗│
      ◄─────── 旧数据必须保持住的区间 ──────────►║┼──── 新数据冲进来
                                                  ▲

                                                  │ = T_clk_launch + T_datapath_min
      │◄─T_clk_capture─►│                         │

                        ▲ 捕获沿到达 FF2 = T_clk_capture
                        │
                        │◄─T_hold─►│              │
                        │          │◄───slack────►│
                                   ▲
                                   数据最早允许变化的时刻
                                   = T_clk_capture + T_hold

4.2 不等式推导

要求：FF2 在它自己的时钟沿之后，还需要 T_hold 这么久把旧数据采稳。所以来自同一沿的新数据不能太早冲到。

   T_clk_launch + T_datapath_min  ≥  T_clk_capture + T_hold
   └──── 新数据到达时刻 ─────────┘     └─ 数据最早可变时刻 ─┘

移项：

   hold slack = (T_clk_launch + T_datapath_min) - (T_clk_capture + T_hold)
                └─────── arrival time ────────┘   └─── required time ───┘

4.3 三个直觉

  • 公式不含 T_period → hold 与频率完全无关。降频、降压、改 PLL 都救不了，流片回来违例就是废片。
  • 用 T_datapath_min → 最快路径最危险 → 对应 min FF / 高压 / 低温 + min SDF。
  • 时钟歪斜 skew = T_clk_capture − T_clk_launch 为正时，hold slack 变小 —— 与 setup 恰好相反。这就是 CTS 要折中、useful skew 要小心的原因。

5 · 数据窗口合图：两者叠在一起看

把 FF2 的 D 端合法数据变化窗口画出来，setup 与 hold 的冲突关系一目了然。

                      ┌─────────── 允许数据翻转的区间 ───────────┐
                      │                                         │
      │               │                                         │        │
FF2.CK│‾‾‾│___________│_________________________________________│____│‾‾‾│
      ▲   edge N      ▲                                         ▲    edge N+1
      │               │                                         │
  T_clk_capture   +T_hold                              −T_setup │
                      │                                         │
                      │◄──── 新数据必须落在这个窗口内变化 ──────►│
                      │                                         │
            太早 → hold 违例                        太晚 → setup 违例
            （由 T_datapath_min 决定）              （由 T_datapath_max 决定）
                      │                                         │
                      └────── 实际数据翻转的抖动范围 ───────┐    │
                            ├══════════════════════════════┤    │
                            ▲                              ▲    │
                   min 路径到达                   max 路径到达   │
                                                                │
                                            留给 setup 的 slack ┘
三条结论 窗口左边界被 T_hold 顶住 → 数据到得越早越危险 → 查 min
窗口右边界被 T_setup 与 T_period 顶住 → 数据到得越晚越危险 → 查 max
数据实际翻转落在 [arrival_min, arrival_max] 区间内，这个区间必须整体落进窗口

5.1 为什么后端修时序这么难

两个方向互相冲突：

  • 把路径加快改善 setup → 同时在恶化 hold
  • 插 buffer 修 hold → 同时在吃掉 setup slack

后端修时序的本质，就是在这张窗口图里把数据区间挤进去。当 arrival_max − arrival_min 的宽度本身就超过窗口宽度时，无论怎么调都修不了，只能回去改设计（减少逻辑级数、重做 pipeline、调整 clock tree）。

5.2 这也解释了必须跑两遍 GLS

一次仿真只能用一个 corner 的延迟值，即只能探测窗口的一侧边界。两个极端都跑，才覆盖得住整个区间。

6 · 对照 PrimeTime 报告

6.1 Setup 报告

  clock clk (rise edge)                   10.00   10.00   ← T_period
  clock network delay (propagated)         0.52   10.52   ← + T_clk_capture
  FF2/CK (DFF)                                    10.52
  library setup time                      -0.09   10.43   ← − T_setup
  data required time                              10.43   ← required
  ------------------------------------------------------
  data arrival time                               -9.86   ← T_clk_launch + T_datapath_max
  slack (MET)                                      0.57

6.2 Hold 报告

  clock clk (rise edge)                    0.00    0.00   ← edge N，注意是 0 不是 T_period
  clock network delay (propagated)         0.48    0.48   ← + T_clk_capture
  library hold time                        0.04    0.52   ← + T_hold
  data required time                               0.52   ← required
  ------------------------------------------------------
  data arrival time                                0.61   ← T_clk_launch + T_datapath_min
  slack (MET)                                      0.09

6.3 两处关键差异

① clock clk (rise edge) 行：10.00 vs 0.00 这一行就是两个公式差一拍的直接证据。setup 的捕获沿在 T_period，hold 的捕获沿在 0（同一沿）。
② clock network delay 数值不同：0.52 vs 0.48 因为两份报告取的是不同的悲观组合：
setup → late capture + early launch（让数据显得更赶不上）
hold → early capture + late launch（让数据显得冲得更早）

这就是 OCV / derate / CRPR 的作用点。
GLS 做不到这一点 门级仿真中 clock 和 data 只能用同一个 corner 的同一个值，无法像 STA 那样对 launch / capture 分别施加不同的悲观度。所以：
时序签核靠 STA，GLS 靠的是发现 STA 约束错误和 X 传播问题。

6.4 读报告的检查清单

  1. 确认 clock clk (rise edge) 的值 → 判断是 setup 还是 hold，以及是否是 multicycle
  2. propagated 还是 ideal → ideal clock 的报告在 CTS 后就没有参考价值
  3. library setup/hold time 符号 → 负 setup / 负 hold 是正常的，别当成异常
  4. 有无 clock reconvergence pessimism 行 → 没有则 CRPR 未开，报告偏悲观
  5. inter-clock uncertainty → 跨时钟域路径是否该被 false path 掉

7.4 常用开关的取舍

开关作用建议
+neg_tchk / -negdelay使能负时序检查必开，保持与 STA 一致，否则负 setup/hold 的单元会误报
+no_notifier违例时不产生 X调试初期可用；签核绝不能关 —— 关掉等于违例"仿过了"
+nospecify忽略全部 specify 块只用于纯功能/零延迟仿真，时序验证下严禁
+notimingcheck保留延迟但关闭所有检查同上，仅用于定位 X 来源时临时使用
+sdfverbose打印 SDF 反标详情首次反标必看，确认 matched / unmatched 数量
-diag timescale检查 timescale 不一致SDF 单位与仿真精度不匹配会导致延迟被截断为 0
反标后第一件事：查 sdf.log 必须确认 unmatched / not annotated 的条目数量。大量未匹配通常意味着：
· 层次路径（scope）给错
· 网表与 SDF 版本不一致
· 单元名在综合后被改名（如加了 _BUFF 后缀）
未匹配的路径会取库默认值（通常接近 0），导致时序验证形同虚设。
