1 · SDF 文件结构与三元组

1.1 SDF 是什么、在流程中的位置

SDF（Standard Delay Format，IEEE 1497）是一种纯文本、工具中立的时序数据交换格式。它把后端提取到的真实延迟，按实例（instance）粒度写出来，供门级仿真反标使用。

综合/布局布线 ──► 寄生提取 (SPEF) ──► STA (PrimeTime)
                                        │
                                        │ write_sdf
                                        ▼
                                     xxx.sdf
                                        │
                                        │ $sdf_annotate / -sdf
                                        ▼
                         门级仿真 GLS (VCS / Xcelium / Questa)
SDF 里有什么、没有什么 有：单元延迟、互连延迟、时序检查门限、脉冲宽度、条件延迟
没有：逻辑功能（在网表 + 库 .v 里）、驱动/负载信息、电压温度的实际计算过程
所以 SDF 必须和同一版网表 + 同 corner 的库仿真模型三者配套使用。

1.2 文件整体骨架

(DELAYFILE                                  ← 文件根节点，整个文件只有一个

  (SDFVERSION "3.0")                        ← SDF 标准版本
  (DESIGN "top")                            ← 顶层模块名
  (DATE "Mon Oct 19 03:15:07 2026")
  (VENDOR "tsmc")
  (PROGRAM "Synopsys PrimeTime")             ← 产生工具
  (VERSION "V-2023.12")
  (DIVIDER /)                               ← 层次分隔符，必须与仿真器一致！
  (VOLTAGE 0.765:0.765:0.765)               ← ★ corner 信息记录在这里
  (PROCESS "ss_g")                          ← ★
  (TEMPERATURE 125.00:125.00:125.00)        ← ★
  (TIMESCALE 1ns)                           ← ★ 所有数值的单位

  (CELL  ... )                              ← 一个实例一个 CELL，可以成千上万
  (CELL  ... )
  (CELL  ... )
)
三个最容易出事的 HEADER 字段 DIVIDER：若 SDF 写的是 / 而网表/仿真器用 .，全部实例匹配失败，延迟全部为 0，仿真照样跑完且"通过"。
TIMESCALE：若 SDF 是 1ns 而仿真 timescale 1ns/1ns（精度只到 1ns），0.018 会被截断为 0。精度至少要 1ps。
VOLTAGE / PROCESS / TEMPERATURE：这是 SDF 自带的 corner 身份证。反标前先看这三行，确认和你挂的库 corner 一致（见第 3 章）。

1.3 CELL 块的结构

(CELL
  (CELLTYPE "MUX2V2_140P7T40L")   ← 单元类型（库里的 module 名）
  (INSTANCE u_core/u_mux_3)       ← 实例路径；(INSTANCE) 空=本层，(INSTANCE *)=通配
  (DELAY                          ← 延迟数据
    (ABSOLUTE                     ← ABSOLUTE=替换 | INCREMENT=累加
      (IOPATH ...)
    )
  )
  (TIMINGCHECK                    ← 时序检查门限（时序单元才有）
    (SETUP ...)
    (HOLD  ...)
  )
)
关键字含义
ABSOLUTE替换库模型里的原值。后端 SDF 几乎都用这个
INCREMENT叠加到库原值上。用于补充 derate、工艺修正等增量
(INSTANCE)空参数 = 应用于当前作用域本身
(INSTANCE *)通配，应用于该 CELLTYPE 的所有实例

1.4 三元组 (min : typ : max)

SDF 里所有延迟与时序检查值都是三元组，形式 (min:typ:max)，三者对应不同的 PVT corner。

字段含义典型 corner主要用途
min最快路径延迟FF / 高压 / 低温（best case）hold 保持时间检查
typ典型值TT / 标称电压 / 常温功能仿真、参考
max最慢路径延迟SS / 低压 / 高温（worst case）setup 建立时间检查
 
(IOPATH A Y (0.082:0.145:0.263) (0.079:0.141:0.258))
            └──── 上升延迟 ────┘ └──── 下降延迟 ────┘
             min : typ : max      min : typ : max

每个外层括号先分 (上升) (下降)，每个里面再是 min:typ:max。

字段可以留空

写法含义
(0.1:0.2:0.3)三个值齐全
(0.018::0.018)typ 缺省（下面实例就是这种）
(::0.3)只给 max
(::)全缺省，由工具 / 库模型决定
(0.263)单值，三个 corner 同值

① CELLTYPE 与端口

MUX2V2_140P7T40L 是一个二选一多路选择器，端口为 I0 / I1（数据）、S（选择）、Z（输出）。

命名段通常含义
MUX22 输入 MUX 功能
V2变体 / 驱动强度档位
7T7-track 单元高度（标准单元行高）
140P / 40LCPP（contacted poly pitch）、Vt 档位等工艺标识
命名规则是 vendor 私有的 上表是常见约定的推测性解读，具体含义必须查对应 PDK 的 standard cell databook 确认。不同 foundry / 不同库供应商规则完全不同。

② INSTANCE：这是一个 Spare Cell

实例名 usr_Smixs_SpareCel_20261019_03H15M07S__MUX2V2_140P7T40L_99 可以拆成：

usr_Smixs _ SpareCel _ 20261019_03H15M07S __ MUX2V2_140P7T40L _ 99
    │          │              │                      │           └ 序号
    │          │              │                      └ 单元类型
    │          │              └ 插入时间戳 2026-10-19 03:15:07
    │          └ Spare Cell 标记
    └ 脚本/模块前缀
Spare Cell（备用单元）是什么 后端在填充空白区域时故意放进去的一批未使用的逻辑单元（MUX、NAND、INV、DFF 等），目的是：万一流片后发现小 bug，可以只改金属层（metal-only ECO），用这些已存在的晶体管搭出补丁逻辑，不用重做基底层掩膜，省掉大量 mask 费用和时间。
带时间戳的自动命名，说明是脚本批量插入的。
Spare Cell 在 GLS 里的影响 · 输入通常 tie 到 VDD/VSS，输出悬空不连接
· 它仍然会出现在 SDF 和网表里，照常占用反标条目
· 若输入没被正确 tie（浮空），仿真时会产生 X，虽不影响功能但会污染波形、增加 debug 噪声
· 对时序无贡献（输出不驱动任何东西），STA 里是 unconstrained path，不要被它的 "no path" 警告干扰

③ 三条无条件 IOPATH

路径上升 (min::max)下降 (min::max)观察
I0 → Z0.018 :: 0.0180.018 :: 0.018上下沿对称，min=max
I1 → Z0.017 :: 0.0170.019 :: 0.019上沿略快于下沿；I0/I1 不对称是 MUX 内部结构决定的
S → Z0.011 :: 0.0210.013 :: 0.015min ≠ max，上沿差近 2 倍
从数据能确定读出的两件事 1. typ 字段全部缺省 → 这是 write_sdf -delay_type min_max 风格的输出，只填两端。仿真时若用 +typdelays，typ 缺省会回退取值（通常取 max 或由工具规则决定），结果不可控，必须显式指定 +mindelays / +maxdelays。

2. min 与 max 来自两次不同的分析 → S→Z 上沿 0.011 vs 0.021 说明 min 侧和 max 侧确实是两套数据（快角/慢角或 early/late 分析），而不是把同一个值复制两遍。
为什么数据路径 min=max、而 S 路径 min≠max？ 这需要结合具体流程才能确认，常见的可能原因：
· S 要经过内部反相器 + 传输门，级数更多，early/late 两次分析的差异被放大
· I0/I1 → Z 只过一级传输门，延迟本身就小、变化空间有限，在 -significant_digits 3 的精度下四舍五入到了同一个值
· 该流程对数据路径与控制路径使用了不同的 derate / OCV 设置
不要凭这一段就下结论，应回去看 write_sdf 的命令参数和 PT 的 report_delay_calculation。

④ 四条 COND 条件延迟

COND 表示状态相关延迟（state-dependent delay）：同一条路径在不同的旁路信号电平下，延迟不同。

(COND I0==1'b0  (IOPATH I1 Z (0.017::0.017) (0.019::0.019)))
      └─ 条件 ─┘ └────────── 该条件成立时才用的延迟 ──────────┘

读法：当 I0 为 0 时，I1 → Z 这条路径的延迟为 ...

本例的四条 COND 覆盖了 I0 和 I1 各为 0/1 的组合，而且数值与无条件 IOPATH 完全相同：

  • COND I0==0 和 COND I0==1 下的 I1→Z 都是 0.017/0.019
  • COND I1==0 和 COND I1==1 下的 I0→Z 都是 0.018/0.018

说明库里虽然定义了状态相关的 timing arc，但在这个 corner / 这个负载下算出来的数值收敛到了同一个值。工具照样把所有 arc 都原样导出，所以看起来冗余。

COND 是 unmatched 的高发区 SDF 的 COND 必须能和库仿真模型 .v 里 specify 块中的 if 条件逐字对应：

if (I0 == 1'b0) (I1 => Z) = (0.017, 0.019);

如果库模型里没有对应的条件 arc，或条件表达式写法不同，这些 COND 条目就会变成 unmatched / not annotated，此时该路径会退回使用无条件值或库默认值。
→ 反标后必须查 sdf.log 的 unmatched 统计。

⑤ 这个 CELL 没有 TIMINGCHECK

MUX 是纯组合逻辑，没有时钟、没有存储节点，因此不存在 setup/hold/width 等检查，CELL 块里只有 DELAY。只有时序单元（DFF、Latch、SRAM）才会有 TIMINGCHECK 段。

1.6 DELAY 段的四种路径类型

关键字作用示例
IOPATH单元内部输入脚到输出脚的延迟(IOPATH I0 Z (0.018::0.018) (0.018::0.018))
INTERCONNECT两个实例脚之间的互连（线）延迟，含 RC(INTERCONNECT u1/Z u2/I0 (0.011::0.034))
PORT到某个输入脚的互连延迟（不指定源端）(PORT u2/I0 (0.011::0.034))

PORT 和 DEVICE 是 INTERCONNECT 的简化形式，精度较低。现代布线后 SDF 基本都用 INTERCONNECT，因为它能区分同一个输出驱动的多个 fanout 各自不同的线延迟。

HOLD数据相对时钟最早变化hold 检查，用 min 路径

① SETUP / HOLD：围住同一个时钟沿的两侧

两者参考同一个时钟沿，一个管左边界、一个管右边界，共同夹出一个禁止数据变化的窗口。

                        ┊
                        ┊ ← 参考沿 (posedge CK)
   CK   ────────────────┨▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔
                   ┌────┊────┐
                   │    ┊    │
        ───────────┤ 禁止变化 ├──────────────
                   │ 窗  ┊ 口 │
                   └────┊────┘
                   │←──→┊←──→│
                   │ Ts  ┊ Th │
                   │     ┊    │
   D    ═══════════╳▒▒▒▒▒▒▒▒▒▒╳══════════════

   (SETUP D (posedge CK) (0.045::0.045))   → Ts = 45 ps  沿之前
   (HOLD  D (posedge CK) (0.012::0.012))   → Th = 12 ps  沿之后
和第 4、5 章公式的对应关系 这里的 Ts 就是 setup slack 公式里的 T_setup， Th 就是 hold slack 公式里的 T_hold。
SDF 的 TIMINGCHECK 只提供门限值（窗口有多宽）， 数据什么时候到达则由 DELAY 段的 IOPATH + INTERCONNECT 累加决定。

② SETUPHOLD：二合一写法

(SETUPHOLD D (posedge CK) (0.045::0.045) (0.012::0.012))
                          └── setup ──┘ └── hold ──┘
                             顺序固定，不可颠倒
为什么库普遍用合并写法 仿真器处理负 setup/hold 时需要同时知道两个值才能正确构造检查窗口 （例如 setup=−8ps、hold=+20ps 时窗口整体右移）。 分开写的 SETUP+HOLD 无法表达这种耦合， 所以绝大多数 PDK 导出的是 SETUPHOLD。

   正常 (Ts>0, Th>0)：窗口跨在沿两侧

④ RECOVERY / REMOVAL：异步信号版的 setup / hold

先理解要防的是什么事 异步复位有效期间，触发器的输出被复位电路直接按住，与时钟无关。
复位释放的那一瞬间，触发器的控制权从"复位电路"交还给"时钟采样电路"。
如果这个交接动作正好和时钟有效沿撞在一起， 触发器就不知道该听谁 —— 内部节点被两边同时拉扯，结果是亚稳态或输出不定值。

RECOVERY 和 REMOVAL 要做的，就是 把"释放沿"和"时钟沿"隔开足够远。
只检查"释放"，不检查"进入有效" 复位进入有效（assert）是异步的，什么时刻都允许 —— 复位压下去就是复位，没有歧义。
只有退出有效（de-assert / release）时才存在"听时钟还是听复位"的争用。
所以 RECOVERY / REMOVAL 的参考事件永远是释放沿。

两者合起来 = 以时钟沿为中心的"禁止释放窗口"

这是理解它们的唯一关键图。结构和 ① 的 SETUP/HOLD 窗口完全一样， 只是被约束的对象从"数据变化"换成了"复位释放"。

一句话区分 · RECOVERY：释放沿在时钟沿之前 → 必须早够 Trec， 让触发器有时间"恢复"到可被时钟正常采样的状态（recovery = 恢复）
· REMOVAL：释放沿在时钟沿之后 → 必须晚够 Trem， 即复位在沿之后还要再"按住"一会儿才能移除（removal = 移除）

SDF 写法与边沿方向

# 低有效异步复位 RN（active-low）：释放是 0→1，即 posedge
(RECOVERY (posedge RN) (posedge CK) (0.060::0.060))              → Trec = 60 ps
(REMOVAL  (posedge RN) (posedge CK) (0.020::0.020))              → Trem = 20 ps
(RECREM   (posedge RN) (posedge CK) (0.060::0.060) (0.020::0.020))  ← 合并写法

# 高有效异步复位 RST（active-high）：释放是 1→0，即 negedge
(RECREM   (negedge RST) (posedge CK) (0.060::0.060) (0.020::0.020))
边沿方向的判定规则 参考事件写的是"释放"那一侧的边沿方向，由复位的有效极性决定：
· 低有效 RN / CDN / RESETB → 释放 = posedge
· 高有效 RST / CLR → 释放 = negedge

判定依据以库 .v 中 $recrem / $recovery 的第一个实参为准。 第 9.5 节的 (RECREM (posedge CDN) (posedge CP) ...) 就是低有效清零脚的典型写法。
违例后果：整个模块的复位值不确定 一条数据路径的 setup 违例只影响一个寄存器的一拍； 但复位释放通常扇出到成百上千个寄存器， recovery/removal 违例会让这些寄存器中的一部分成功复位、一部分没复位 —— 状态机从一个非法状态起步，后果是整个模块行为错乱且难以复现。

这正是异步复位必须做同步释放（reset synchronizer：异步 assert、同步 de-assert）的根本原因。
GLS 中容易被忽略 这类违例集中出现在复位释放后的第一个时钟沿， 和上电初始化的一堆 X 混在一起，常被当成"初始化噪声"直接跳过。
建议：GLS 中把复位释放时刻有意对齐到时钟沿附近跑一轮， 专门验证 reset synchronizer 是否真的起作用。

1.9 工程实践中的坑

多数后端流程不会在一份 SDF 里塞三个 corner PrimeTime write_sdf 通常每个 corner 单独导出一份，文件里三元组三个值相同，例如 (0.263:0.263:0.263)；或者像本章实例那样用 -delay_type min_max 只填两端、typ 留空。想要真正 min:typ:max 合一，需要多 corner 合并脚本。
INTERCONNECT 的 min 值要留意 若反标后 min 值异常偏小（接近 0），常是寄生提取 corner 配错（例如用了 cbest 却没配对应的器件 corner），会导致 hold 虚假通过 —— 这是最危险的一类静默错误。
反标日志必查项 +sdfverbose 打开后，检查 sdf.log 中的：
· unmatched instance —— 层次路径或 DIVIDER 配错、网表与 SDF 版本不一致
· unmatched IOPATH / TIMINGCHECK —— 库模型缺少对应 arc（COND 条件尤其高发）
· not annotated 数量 —— 未匹配的路径会退回库默认值（常接近 0），时序验证形同虚设
一个健康的反标，unmatched 应当是 0 或可解释的极少数。
文件体量 一个中等规模 SoC 的 SDF 可以到几 GB（每个实例一个 CELL 块 + 每根线一条 INTERCONNECT）。常见做法：按模块分别导出、用 gzip 压缩（多数仿真器支持直接读 .sdf.gz）、或只对关键模块反标。

2 · 门级仿真 Corner 搭配原理

经典搭配 功能 / setup 验证 → max SDF + SS corner 库 + +maxdelays
hold 验证 → min SDF + FF corner 库 + +mindelays
两者都要跑，单跑 max 会漏掉全部 hold 违例。

2.1 setup 与 hold 的"受害方向"相反

setup slack = T_period + T_clk_capture - (T_clk_launch + T_datapath_max + T_setup)
hold  slack = T_clk_launch + T_datapath_min - (T_clk_capture + T_hold)
  • setup：数据路径延迟越大越容易违例 → 用最慢延迟去压 → max
  • hold：数据路径延迟越小越容易违例 → 用最快延迟去压 → min

方向相反的两个极端，同一份网表必须跑两遍。

2.2 为什么慢 corner 是 SS / 低压 / 高温

晶体管驱动能力 ∝ 载流子迁移率与过驱动电压 (Vgs − Vth)：

因素慢（max delay）快（min delay）
工艺 PSS：阈值电压高、驱动弱FF：阈值低、驱动强
电压 V低压：过驱动小高压
温度 T高温：迁移率下降低温

所以 SS + Vmin + Tmax 给出最大延迟，FF + Vmax + Tmin 给出最小延迟。

温度反转 (Temperature Inversion) 先进节点（16nm 以下、低压工作）下低温反而更慢。此时 corner 必须按 PDK 实际标定来挑，不能机械套"高温最慢"。

2.3 为什么 SDF 和库必须配对，不能混用

门级仿真的时序由两部分拼出来：

SDF 提供 IOPATH 单元延迟
INTERCONNECT 线延迟
SETUP/HOLD/RECREM/WIDTH 检查门限值
库仿真模型 (.v) 提供 逻辑功能
specify 块骨架
SDF 未覆盖路径的默认值

关键在于 检查门限本身也是 corner 相关的。同一个单元的 $hold 要求在 FF 和 SS 下数值不同（通常 FF 下 hold 要求更苛刻）。

混搭的两种典型错误 ① max SDF 做 hold 验证：拿 SS 下宽松的 hold 门限，去量一条你又故意让它跑慢的路径 —— 双重乐观，等于没验。

② FF 库 + max SDF：SDF 未标注的路径会取库里的 FF 值，与已标注部分不自洽，报出来的违例真假难辨。

2.4 为什么 hold 那一遍绝不能省

setup 违例hold 违例
与频率关系公式含 T_period，有关公式不含 T_period，无关
本质路径太慢，赶不上下一拍纯粹的竞争 race：数据在同一拍内穿过组合逻辑把下级 FF 冲掉
流片后能否抢救能：降主频出货不能：任何频率/电压配置都无法规避 → 直接报废
hold 风险最集中的地方 DFT scan shift 模式：扫描链上相邻 FF 之间几乎没有组合逻辑，T_datapath_min 极小。此外跨异步边界、时钟门控路径也是高危区。FF corner 的 scan shift GLS 是必跑项。

2.5 GLS 的定位：不是替代 STA

GLS 对 clock 和 data 用同一个 corner，而 STA 会做 OCV / AOCV、CRPR（clock reconvergence pessimism removal）、derate 等更精细的处理。

  • 时序是否收敛 → 看 STA，GLS 不负责签核时序
  • GLS 要抓的是 STA 看不见的东西：
    • 复位序列、上电初始化导致的 X 传播
    • SDC 里 set_false_path / set_multicycle_path 用错（STA 被你骗了，仿真骗不了）
    • 异步 FIFO、握手、跨时钟域的真实行为
    • 门控时钟的使能时序、DFT 模式切换
    • 库模型 x_transport、负 setup-hold 窗口带来的实际 X

一句话：corner 的选择决定了你能暴露哪一类竞争，两个极端都跑才覆盖得住。

3 · Corner 体系详解

3.1 什么是 Corner

同一份版图造出来的芯片，性能并不相同。Corner（工艺角） 就是把所有不确定性推到极端，取若干个"最坏组合"作为代表点来验证。只要所有 corner 都过，中间的连续空间就认为安全。

最核心的三个维度 = PVT P (Process) 工艺偏差 —— 不可控，流片后固定，批次间/晶圆内差异
V (Voltage) 供电电压 —— 运行时波动（IR drop、负载跳变、LDO 精度）
T (Temperature) 结温 —— 运行时变化（环境温度 + 自发热）
但"corner"远不止 PVT 三个维度 PVT 只决定晶体管（标准单元库）的快慢。 一条真实时序路径的延迟还取决于连线、工作模式、 片内随机偏差、信号完整性、老化……
签核时任何一个维度漏掉，都可能让其余维度的分析结果整体失效。

· 时钟树两个分支 skew 增大（分支级数不同 → 失配累积不同）

3.4 V：电压维度

场景取值理由
setup（慢）Vnom × (1 − x%)，如 0.81V低压 → 过驱动 Vgs − Vth 小 → 驱动弱 → 延迟大
hold（快）Vnom × (1 + x%)，如 0.99V高压 → 驱动强 → 延迟小
电压 corner 不是拍脑袋定的 低压侧必须覆盖 静态 IR drop + 动态 IR drop + 封装/PCB 压降 + 稳压器精度 的总和。如果 PI（Power Integrity）分析报出的最差压降超过了签核时用的低压 corner，整个 setup 签核结果作废。
这就是为什么 PI 和 STA 必须迭代，以及为什么会有 -pba_mode / voltage-aware STA。

多电压域设计 (Multi-Voltage)

  • 每个 power domain 可以有独立的电压 corner
  • 跨域路径（经过 level shifter）要考虑两侧电压的组合：高压侧低压 + 低压侧高压 等交叉情况
  • DVFS 设计还要为每个工作点（如 0.9V/1GHz、0.7V/400MHz）各建一套 corner

3.5 T：温度维度与温度反转

温度对延迟有两个反向作用：

机制温度升高时对延迟
载流子迁移率 μ 下降驱动电流减小变慢
阈值电压 Vth 下降过驱动增大、亚阈漏电增大变快
温度反转 (Temperature Inversion / Inverted Temperature Dependence) 高电压下：过驱动本来就大，Vth 变化占比小 → 迁移率主导 → 高温最慢（传统认知）
低电压下（接近 Vth，先进节点常态）：Vth 变化占比大 → Vth 主导 → 低温最慢（反转！）

后果：SS + Vmin + T(-40°C) 可能比 SS + Vmin + T(125°C) 更慢。
→ 签核必须同时跑高温和低温两个 setup corner，不能只凭直觉选一个。

3.6 RC Corner：互连寄生参数

延迟 = 单元延迟（器件 corner 决定）+ 互连延迟（RC corner 决定），两者是独立的维度。

RC Corner金属宽度介质厚度R / C 特征主要影响
cworst宽薄C 最大，R 偏小长线、全局互连延迟最大 → setup
cbest窄厚C 最小，R 偏大互连延迟最小 → hold
rcworst窄薄R 与 C 都偏大RC 乘积最大，短/中线最差 → setup
rcbest宽厚R 与 C 都偏小最乐观 → hold
typical标称标称—功能仿真参考
cworst 和 rcworst 哪个更差？取决于线长 长线（全局走线、时钟主干）：容性负载主导 → cworst 更差
短线 / 中等线（局部互连、高层 via 栈多）：电阻影响显著 → rcworst 更差
所以 两个都要跑，不能只挑一个。先进节点还有 cworst_CCworst / cbest_CCbest 等区分耦合电容（coupling）的变体，见下一小节。

耦合电容（Coupling Capacitance）与 CC corner

① 总电容的分解：对地电容 + 耦合电容

一根信号线的负载电容并不是一个整体，提参（extraction）时被拆成两部分：

C_total = C_ground + Σ C_coupling

            ┌──────────────────────────────┐
            │          上层金属 Mn+1        │   ← 也可能是邻层走线
            └──────────────────────────────┘
                   │ C_ground(up)
   ┌─────────┐     ▼      ┌─────────┐      ┌─────────┐
   │ 邻线 A  │◄── Cc1 ───►│ victim  │◄─ Cc2 ─►│ 邻线 B  │   同层左右邻线
   └─────────┘            └─────────┘      └─────────┘
                   │ C_ground(dn)
            ┌──────▼───────────────────────┐
            │          下层金属 Mn-1        │
            └──────────────────────────────┘
                          ⏚ 衬底

  C_ground  = 对上下层 / 衬底的电容  → 恒定负载，只让线"变慢"
  C_coupling= 对同层左右邻线的电容   → 负载随邻线翻转方向而变
为什么先进节点必须单独管 CC 金属线的截面在缩小，但为了控制电阻，厚度不能同比缩小 → 线变得又高又窄，间距也更小。
结果：侧壁（sidewall）面积相对变大，C_coupling 占 C_total 的比例从 0.18µm 时代的 20~30% 上升到 16nm/7nm 的 60~80%。
→ 在先进节点，"互连电容"基本就是"耦合电容"。只管 cworst/cbest 等于只管了小头。
② 米勒效应：耦合电容的等效值不是固定的

耦合电容两端都是动的。victim 线看到的等效电容取决于邻线（aggressor）此刻在做什么：

aggressor 行为等效 Cc（米勒系数 k） victim 延迟受害的检查
静止（不翻转）k = 1 → Cc基准—
反向翻转（victim↑ / aggr↓）k = 2 → 2·Cc变慢数据路径慢 → setup
时钟路径慢 → 另一侧 hold
同向翻转（victim↑ / aggr↑）k = 0 → 0变快数据路径快 → hold
victim 静止、aggr 翻转—（无延迟变化）产生 glitch噪声 / 功能错误
米勒系数 k 的工程取值 理论上 k ∈ [0, 2]，但真实翻转有 slew、有时间错位，极少真的到 0 或 2。
提参工具常用 k = 0 / 1 / 2 做静态近似（对应 CCbest / 无 SI / CCworst）， 而 PT SI 会按实际 slew 和时间窗重叠度动态算出介于两者之间的值。
③ CC corner 与 cworst / rcworst 是正交的两个维度
不要把它们理解成同一条轴上的点 cworst / cbest / rcworst / rcbest：描述工艺偏差（金属宽度、介质厚度的 ±3σ），决定 R 和 C_ground 的大小。
CCworst / CCbest：描述耦合项如何折算（米勒系数取 2 还是 0），决定 C_coupling 的等效大小。

两者相乘才得到完整的 corner 名字，所以才会出现 cworst_CCworst 这种"双段式"命名。
RC corner 全名工艺段耦合段 互连延迟典型用途
cworst_CCworstC 最大k=2最大setup 签核主力（长线主导的设计）
rcworst_CCworstRC 积最大k=2最大setup 签核（短/中线、via 栈多）
cbest_CCbestC 最小k=0最小hold 签核主力
rcbest_CCbestRC 积最小k=0最小hold 签核补充
typical标称k=1标称功能仿真 / 早期评估
为什么没有 cworst_CCbest 这种交叉组合 理论上存在，但签核不用。原因是 corner 的作用是给出单向的悲观边界：
setup 要"全都最慢" → 工艺段和耦合段都取 worst；hold 要"全都最快" → 两段都取 best。
混搭（如 cworst_CCbest）既不是最慢也不是最快，既不保守也不可用，只会浪费一个 view。
例外：某些 PDK 提供它用于诊断，看某条路径的违例到底是 C_ground 还是 C_coupling 贡献的。

写法说明

老节点 / 简化流程通常是把耦合按 k=1 折算进了对地电容（SPEF 里只有 *CAP 的单端项，没有双端耦合项）。
→ 判断依据不是 corner 名，而是看提参输出的 SPEF 里有没有双节点电容项。

一眼看出 SPEF 有没有保留耦合 *CAP 段里每一行有两个节点名的就是耦合电容；只有一个节点名的是对地电容。
如果整份 SPEF 的 *CAP 全是单节点 → 说明做了 coupling-to-ground 折算（grounded SPEF）， 此时无法再做 SI 分析，PT SI 会直接报"no coupling found"。
提参时要显式要求保留：extract -coupling（工具选项名各异），且不要设过大的耦合忽略阈值 （coupling_c_threshold 设太大会把小耦合全部折算掉）。
⑥ CC corner 只给出 Cc 的大小，delta delay 要靠 PT SI 算
两个容易混为一谈的东西 CC corner（提参阶段）：决定 SPEF 里 Cc 这个数值是多少，是静态的工艺/折算假设。
PT SI（分析阶段）：拿着 SPEF 里的 Cc，再结合 ① aggressor 和 victim 的时序窗口是否重叠 ② 翻转方向是否相反 ③ 双方的驱动强度与 slew
才算出真正的 delta delay 和 glitch 高度。

→ 只跑 _CCworst 而不开 SI 分析，等于把所有邻线都当成"永远反向同时翻转"，过度悲观；
只开 SI 但 SPEF 是 grounded 的，则 SI 完全失效。两者必须配套。

时序窗口重叠的意义：只有 aggressor 在 victim 翻转的同一时间窗内翻转，才会产生 delta delay。

                 victim 的翻转窗口
                 ├───────────────┤
  aggr A  ├─────┤                          ← 不重叠，无影响
  aggr B          ├────────┤               ← 重叠 ★ 计入 delta delay
  aggr C                        ├──────┤   ← 不重叠，无影响

  PT SI 会迭代：算延迟 → 更新时序窗口 → 重新判断重叠 → 再算延迟 …
  直到收敛（典型 2~3 轮）。这就是 PT SI 比普通 STA 慢很多的原因。

⑦ 耦合对 setup 和 hold 是双向影响

这是耦合电容区别于普通负载电容的关键：普通电容只会让线变慢，耦合则两个方向都会变。

受影响路径邻线翻转方向 效果对 slack 的影响
数据路径反向变慢T_datapath_max ↑ → setup slack 变小
同向变快T_datapath_min ↓ → hold slack 变小
launch 时钟路径反向变慢T_clk_launch ↑ → setup 变差、hold 变好
同向变快T_clk_launch ↓ → setup 变好、hold 变差
capture 时钟路径反向变慢T_clk_capture ↑ → setup 变好、hold 变差
同向变快T_clk_capture ↓ → setup 变差、hold 变好
时钟网络上的耦合最危险 时钟线上的 delta delay 直接变成 额外的 skew，而且是数据相关、每周期都可能不同的随机 skew。
一条被严重耦合的时钟线可能在某些周期产生几十 ps 的抖动 → hold 违例，且只在特定数据模式下出现，极难在硅后定位。
→ 所以时钟网络通常强制加 shielding（两侧夹地线）、加大间距（NDR）、走专用层， 从物理上把 Cc 压到最小，而不是指望 corner 去 cover。
与其他章节的衔接 SI 作为独立 corner 维度的整体定位见 3.13 节；
crosstalk 的 delta delay 在流到门级仿真时被固化进 SDF INTERCONNECT 数值、 从而丢失动态性这一问题，同样在 3.13 节展开。
本小节只讲提参侧：耦合电容本身怎么被建模、怎么被 corner 命名区分。

· 优化阶段：可以只跑 dominant corner 提速，但必须先用第 3 步的数据 证明被省掉的 corner 确实不主导任何路径集合。
· 判断依据的优先级： PDK 强制清单 > 实测违例路径交集 > 节点经验 > 设计特征直觉

反直觉但极重要：慢 corner 也必须查 hold（第 7 行） hold slack 的分子是 T_clk_launch + T_datapath_min − T_clk_capture − T_hold。
在慢 corner 下，数据路径和时钟路径都变慢，但两者变慢的比例不同。如果 capture 端时钟树比 launch 端更长（或经过更多 ICG / 不同 Vt 单元），慢 corner 会让 T_clk_capture 增加得比 T_datapath_min 更多，hold slack 反而恶化。

结论：hold 不能只跑 FF corner。 实际工程中 hold 的签核 corner 数量通常多于 setup。

GLS 跑几个 corner？ STA 跑全部签核 corner（几十个），GLS 不可能也不需要。GLS 的目标不是时序签核，而是验证 STA 约束的正确性与 X 行为，因此通常只跑两端极值：
· max SDF + SS 库 → 一遍
· min SDF + FF 库 → 一遍
· 必要时补 typ 一遍做功能回归
对关键接口（DDR / SerDes / 跨时钟域）可以再挑 SF/FS 补跑。

3.11 OCV / AOCV / POCV：片内随机偏差

PVT corner 描述的是整颗 die 的平均状态（global / die-to-die）。 但同一颗 die 上，相邻两个单元也不会完全一样 —— 这叫 OCV（On-Chip Variation，片内偏差）。

为什么 PVT corner 不够 SS corner 的含义是"整颗芯片都慢"。可是 setup 检查需要的最坏情况是 数据路径慢、而捕获时钟路径快 —— 这两件事发生在同一颗 die 上。
单靠 PVT corner 无法表达"一颗 die 内部，这边慢那边快"，所以必须额外加 OCV。
方法做法特点
flat derate set_timing_derate -late 1.05 -early 0.95
所有单元统一乘一个系数		 最简单最悲观。路径越长累积越离谱（实际上级数越多，随机偏差越相互抵消）
AOCV
(Advanced)		 derate 系数是 路径深度 (depth) 与 物理距离 (distance) 的查找表 级数多 → derate 变小，符合统计规律。比 flat 省 5~15% 悲观度
POCV / SOCV
(Parametric/Statistical)		 每个单元延迟带一个 σ（标准差），沿路径做平方和开方而非线性累加 先进节点（16nm 以下）主流。需要 LVF (Liberty Variation Format) 库支持 
三种方法下，10 级逻辑路径的悲观度对比（示意）：

  flat derate  ：delay × 1.05 × 10 级  ──► 悲观度线性累加，最大
  AOCV         ：delay × 1.02（查表得 10 级时系数已回落）
  POCV         ：σ_total = √(σ1² + σ2² + ... + σ10²)  ──► 随 √N 增长，最接近真实
OCV 与 SDF / GLS 的关系 write_sdf 导出时，derate 已经被乘进延迟数值里， SDF 本身没有任何字段记录 OCV 设定。
所以：拿到一份 SDF，无法从文件内容判断它含不含 derate —— 必须回去查 PT 脚本里的 set_timing_derate。

更麻烦的是：OCV 对 launch / capture 时钟路径施加的是相反方向的 derate， 而一份 SDF 对同一个时钟 buffer 只能写一个延迟值。 这是 GLS 天然无法完整复现 STA 结果的根本原因之一（见 2.5 节）。

3.12 Aging：老化维度

芯片不是出厂时最慢。随着使用年限增加，晶体管 Vth 会漂移，延迟逐年变大。

机制全称影响
NBTI Negative Bias Temperature Instability PMOS 长期处于导通态 → |Vth| 增大 → 变慢。主要老化机制
PBTI Positive BTI NMOS 版本，high-k 工艺下变得显著
HCI Hot Carrier Injection 高频翻转节点的载流子撞击损伤栅氧
EM Electromigration 金属线逐渐变细 → 电阻增大 → 连线延迟变大（也可能直接断路）
在流程中如何体现 · 车规 / 工业级芯片必须签 aged corner（厂商提供老化后的 .lib，或给一个 aging derate）
· 消费类产品常用简化做法：在 SS corner 上额外加 2~5% derate
· 典型要求：10 年 @ 125°C 后仍满足时序

老化只会让电路变慢，所以主要影响 setup。 但注意：clock tree 也会老化，两条分支老化程度不同 → hold 也会受影响。

3.13 SI：信号完整性（crosstalk）

相邻走线之间存在耦合电容。邻线（aggressor）翻转时，会把受害线（victim）的延迟 推快或拖慢。

   aggressor ─────┐                  耦合电容 Cc
                  │  ╎╎╎╎╎╎╎╎╎╎╎╎╎╎  ← 并行走线段
   victim    ─────┘

   情形 1：同向翻转（0→1 与 0→1）
       → 互相"帮推一把" → victim 变快  → 对 hold 不利

   情形 2：反向翻转（0→1 与 1→0）
       → 互相拖拽         → victim 变慢  → 对 setup 不利

   情形 3：aggressor 不动，victim 翻转
       → Cc 变成纯负载   → victim 变慢（已含在普通 extraction 里）
与 RC corner 的区别与联系 3.5 节提到的 cworst_CCworst 中，后半截 CCworst 指的就是 耦合电容取最坏。
但 RC corner 只决定 Cc 的大小； 真正算出"快了多少 / 慢了多少"（delta delay） 需要 PrimeTime SI 做时序窗口分析 —— 只有当 aggressor 与 victim 的翻转时间窗口真的重叠时才计入。
SDF 无法表达 crosstalk delta delay 依赖"哪些邻线在何时翻转"，是动态、数据相关的。 SDF 只能写一个静态数值。
write_sdf 导出时，PT SI 算出的 delta delay 会被 固化进 INTERCONNECT 数值 —— 等于把"最坏情况的邻线活动" 永久假设成一直发生。这是 SDF 相比 STA 的又一处精度损失。

3.14 时钟不确定性（jitter / duty / uncertainty）

前面所有分析都假设时钟源是理想周期。实际 PLL 输出存在抖动。

来源性质对时序的影响
PLL jitter 周期随机抖动（period jitter） 某一拍周期偶然变短 → 直接从 setup slack 里扣掉
duty cycle 偏差 高低电平不等长 影响半周期路径、DDR 接口、latch 的 time borrowing
电源噪声引起的抖动 供电波动传导到时钟树 与 IR drop 分析耦合
CTS 后残余 skew 工具无法完全消除的确定性偏差 已含在 T_clk_launch / T_clk_capture 的差里 
在 SDC 中统一用 uncertainty 表达：

  set_clock_uncertainty -setup 0.050 [get_clocks clk]
  set_clock_uncertainty -hold  0.020 [get_clocks clk]

它直接从第 4、5 章的 slack 公式里扣除：

  setup slack = T_period + T_clk_capture
              − (T_clk_launch + T_datapath_max + T_setup)
              − T_uncertainty_setup        ← 新增这一项

  hold  slack = T_clk_launch + T_datapath_min
              − (T_clk_capture + T_hold)
              − T_uncertainty_hold         ← 新增这一项
为什么 hold 的 uncertainty 比 setup 小 hold 是同一个沿的检查（第 5 章）， period jitter 对 launch 和 capture 的影响同向、相互抵消， 所以只需覆盖 skew 的随机部分。
setup 跨一拍，必须额外承担整个 period jitter。

4.2 五个量的定义与来源

公式里每一项都有明确的物理含义、明确的 SDF 出处、明确的 corner 取法。 搞不清这张表，公式就只是五个符号。

符号物理含义 在 SDF 中的来源取 min 还是 max
T_clk_launch 时钟从时钟源传到 FF1.CK 所用的时间
（发射端时钟树延迟）		 时钟树上一串 CKBUF/CKINV/ICG 的 IOPATH + 之间的 INTERCONNECT 逐级累加 setup 下取 max（late）
—— 发射越晚越危险
T_clk_capture 时钟从同一个时钟源传到 FF2.CK 所用的时间
（捕获端时钟树延迟）		 同上，但走的是通往 FF2 的那条时钟树分支 setup 下取 min（early）
—— 捕获越早越危险
T_datapath_max FF1.CK 到达后，数据经 CK→Q + 组合逻辑 + 走线，到达 FF2.D 的最长时间 FF1 的 (IOPATH (posedge CK) Q ...)
+ 链路上每个门的 IOPATH
+ 每段 INTERCONNECT		 max
—— 定义即最长路径
T_setup FF2 要求数据在捕获沿之前稳定的最小时间（门限值，不是延迟） FF2 的 (SETUPHOLD D (posedge CK) (Ts) (Th)) 中的第一个值 检查门限，与 corner 无关
通常三元组三值相同
T_period 时钟周期，即 edge N 到 edge N+1 的间隔 不在 SDF 里，来自 SDC 的 create_clock / TB 的时钟激励 —
为什么 launch 取 max 而 capture 取 min 这不是两个独立的选择，而是同一个悲观化策略的两面：
· 发射端慢（T_clk_launch 大）→ 数据出发得晚 → arrival time 变大
· 捕获端快（T_clk_capture 小）→ 截止时刻提前 → required time 变小

两者同时朝最坏方向取，slack 被压到最小。这叫 late launch / early capture， 是 setup 检查的标准悲观组合（第 7 章 PT 报告里 0.52 vs 0.48 就是这个）。
T_setup 与前四项性质不同 T_clk_launch / T_clk_capture / T_datapath_max 都是 延迟（signal 走了多久，来自 SDF 的 DELAY 段）；
T_setup 是门限（单元要求多久，来自 SDF 的 TIMINGCHECK 段）。
这正是 1.7 节 ⑨ 后面那段"DELAY 产生 arrival time、TIMINGCHECK 产生 required time"的分工。

共用时钟树的部分不参与竞争

clk 源 ──► [共用段 BUF] ──┬──► [分支 A] ──► FF1.CK
                          │
                          └──► [分支 B] ──► FF2.CK

  T_clk_launch  = 共用段 + 分支 A
  T_clk_capture = 共用段 + 分支 B

  skew = T_clk_capture − T_clk_launch = 分支 B − 分支 A
         └─ 共用段被抵消，不影响 skew ─┘

所以 CTS 的目标不是把时钟树做短，而是把两个分支做得一样长。 共用段再长，对 setup/hold 的 slack 也不产生净影响（只影响 latency 与 I/O 时序）。

4.4 不等式推导

要求：数据必须在捕获沿之前至少 T_setup 就已稳定。

   T_clk_launch + T_datapath_max + T_setup  ≤  T_period + T_clk_capture
   └──────────── data arrival + setup 要求 ─┘     └─ capture edge 到达时刻 ─┘

移项：

   setup slack = (T_period + T_clk_capture) - (T_clk_launch + T_datapath_max + T_setup)
                 └──── required time ─────┘   └────────── arrival time ──────────┘

为什么捕获沿到达时刻是 T_period + T_clk_capture

一切的前提：公共时间原点 STA 把时钟源发出 edge N 的那一刻定义为 t = 0。 之后所有事件的时刻，都是从这个同一个原点量出来的绝对时间。
只有统一了原点，arrival 和 required 才能直接相减 —— 这是公式能成立的基础。

于是捕获沿的时刻可以分两步推出来：

第 1 步：捕获沿在时钟源上何时发出？

   edge N   在时钟源发出 ──► t = 0
   edge N+1 在时钟源发出 ──► t = T_period        ← 周期的定义

   setup 检查用的是 edge N+1，所以源端时刻 = T_period


第 2 步：它从时钟源走到 FF2.CK 要多久？

   走的是通往 FF2 的那条时钟树分支 ──► T_clk_capture


两步相加：

   捕获沿到达 FF2.CK 的时刻 = T_period + T_clk_capture
                              └──┬──┘   └──────┬──────┘
                          源端发出时刻      树上传播时间
同理看 arrival 侧，结构完全对称 
发射沿在源端发出     ──► t = 0
发射沿到达 FF1.CK    ──► t = 0 + T_clk_launch
数据到达 FF2.D       ──► t = T_clk_launch + T_datapath_max
两侧都是"源端发出时刻 + 传播时间"。 唯一的差别只是：arrival 侧用的是 edge N（源端 t=0），required 侧用的是 edge N+1（源端 t=T_period）。

T_period 从哪来：因为 setup 是"跨一拍"的检查

时钟源：
          edge N                      edge N+1
   t=0 ─────┬──────── T_period ──────────┬────────────────►
            │                            │
            │ 用来发射数据             │ 用来捕获数据
            │ (launch)                   │ (capture)
            ▼                            ▼
       +T_clk_launch                +T_clk_capture
            │                            │
            ▼                            ▼
       FF1.CK 收到沿                 FF2.CK 收到沿
       = T_clk_launch               = T_period + T_clk_capture

   ◄════════ 数据有整整一个周期的时间可以跑 ════════►
这就是 setup 与 hold 唯一的结构性差别 两个公式的 required time 都是"源端发出时刻 + T_clk_capture"， 区别只在捕获用的是哪一个沿：

· setup：launch 用 edge N，capture 用 edge N+1
  → capture 沿源端时刻 = T_period → 到达 FF2.CK = T_period + T_clk_capture

· hold：launch 用 edge N，capture 用同一个 edge N
  → capture 沿源端时刻 = 0 → 到达 FF2.CK = 0 + T_clk_capture = T_clk_capture

hold 公式里没有 T_period，就是因为那个 0。 把 setup 公式中的 T_period 换成 0、把 max 换成 min、 把 T_setup 换成 −T_hold，就得到了 hold 公式（详见第 5 章）。
推论：为什么降频能救 setup，但救不了 hold T_period 只出现在 setup 的 required time 里。 周期加大 → 捕获沿整体往后挪 → 数据多了喘息时间 → setup slack 线性变好。

hold 的两端都挂在同一个沿上，T_period 根本不出现 —— 时钟放慢多少倍，hold slack 一点都不变。
这就是 hold 违例流片后无法用降频抢救的数学原因。
两个常见误解 ✗ "T_period + T_clk_capture 是因为数据要走一个周期再加时钟树延迟"
→ 错。T_period 和 T_clk_capture 都在时钟侧， 和数据路径没有任何关系。数据路径只贡献 T_datapath_max。

✗ "多周期路径就把 T_clk_capture 乘 N"
→ 错。set_multicycle_path N 改的是捕获沿的选取， required time 变成 N × T_period + T_clk_capture； 时钟树延迟 T_clk_capture 始终只算一次。

4.5 代入数值走一遍

假设 1 GHz 时钟（T_period = 1.000 ns），SDF 中查到：

T_clk_launch   = 0.520 ns   ← 时钟树到 FF1.CK，取 late
T_clk_capture  = 0.480 ns   ← 时钟树到 FF2.CK，取 early
T_datapath_max = 0.420 ns   ← FF1 CK→Q (0.085) + 组合逻辑 + 走线
T_setup        = 0.045 ns   ← FF2 的 SETUPHOLD 第一个值
T_period       = 1.000 ns   ← 来自 SDC

arrival  = 0.520 + 0.420          = 0.940 ns   ← 数据到达 FF2.D 的时刻
required = 1.000 + 0.480 − 0.045  = 1.435 ns   ← 最晚允许到达的时刻

slack    = 1.435 − 0.940          = +0.495 ns  ✓ 满足
两种等价的写法 把 T_setup 放在左边（加进 arrival）还是放在右边（从 required 里减去）， 结果完全一样 —— 它只是把"截止线"往前挪了 T_setup。
PrimeTime 报告采用的是右边的形式：先算出 capture edge 时刻， 再在 library setup time 一行减去 T_setup，得到 data required time。
slack 对各项的敏感度 从公式可直接读出每一项变化 1 ps 对 slack 的影响：
· T_period ↑ → slack ↑（降频能救 setup）
· T_clk_capture ↑ → slack ↑（捕获端更晚到，等于多给时间）
· T_clk_launch ↑ → slack ↓（发射端更晚到，数据出发就迟了）
· T_datapath_max ↑ → slack ↓（逻辑级数越多越危险）
· T_setup ↑ → slack ↓（换驱动更大但 setup 更大的 FF 不一定划算）

4.6 三个直觉

  • 公式含 T_period → setup 与频率有关。降频使 T_period 变大、slack 变大，所以 setup 违例能靠降频抢救。
  • 用 T_datapath_max → 最慢路径最危险 → 对应 max SS / 低压 / 高温 + max SDF。
  • 时钟歪斜 skew = T_clk_capture − T_clk_launch 为正（捕获端更晚到）时，setup slack 变大，是在帮忙。

5 · Hold 时序图：edge N 发出，同一个 edge N 接收

最容易糊的地方 hold 检查里没有 edge N+1。发射沿和捕获沿是同一个时钟沿。这就是为什么 hold 公式里不出现 T_period。

5.2 不等式推导

要求：FF2 在它自己的时钟沿之后，还需要 T_hold 这么久把旧数据采稳。所以来自同一沿的新数据不能太早冲到。

   T_clk_launch + T_datapath_min  ≥  T_clk_capture + T_hold
   └──── 新数据到达时刻 ─────────┘     └─ 数据最早可变时刻 ─┘

移项：

   hold slack = (T_clk_launch + T_datapath_min) - (T_clk_capture + T_hold)
                └─────── arrival time ────────┘   └─── required time ───┘

5.3 三个直觉

  • 公式不含 T_period → hold 与频率完全无关。降频、降压、改 PLL 都救不了，流片回来违例就是废片。
  • 用 T_datapath_min → 最快路径最危险 → 对应 min FF / 高压 / 低温 + min SDF。
  • 时钟歪斜 skew = T_clk_capture − T_clk_launch 为正时，hold slack 变小 —— 与 setup 恰好相反。这就是 CTS 要折中、useful skew 要小心的原因。

6 · 数据窗口合图：两者叠在一起看

把 FF2 的 D 端合法数据变化窗口画出来，setup 与 hold 的冲突关系一目了然。

                      ┌─────────── 允许数据翻转的区间 ───────────┐
                      │                                         │
      │               │                                         │        │
FF2.CK│‾‾‾│___________│_________________________________________│____│‾‾‾│
      ▲   edge N      ▲                                         ▲    edge N+1
      │               │                                         │
  T_clk_capture   +T_hold                              −T_setup │
                      │                                         │
                      │◄──── 新数据必须落在这个窗口内变化 ──────►│
                      │                                         │
            太早 → hold 违例                        太晚 → setup 违例
            （由 T_datapath_min 决定）              （由 T_datapath_max 决定）
                      │                                         │
                      └────── 实际数据翻转的抖动范围 ───────┐    │
                            ├══════════════════════════════┤    │
                            ▲                              ▲    │
                   min 路径到达                   max 路径到达   │
                                                                │
                                            留给 setup 的 slack ┘
三条结论 窗口左边界被 T_hold 顶住 → 数据到得越早越危险 → 查 min
窗口右边界被 T_setup 与 T_period 顶住 → 数据到得越晚越危险 → 查 max
数据实际翻转落在 [arrival_min, arrival_max] 区间内，这个区间必须整体落进窗口

6.1 为什么后端修时序这么难

两个方向互相冲突：

  • 把路径加快改善 setup → 同时在恶化 hold
  • 插 buffer 修 hold → 同时在吃掉 setup slack

后端修时序的本质，就是在这张窗口图里把数据区间挤进去。当 arrival_max − arrival_min 的宽度本身就超过窗口宽度时，无论怎么调都修不了，只能回去改设计（减少逻辑级数、重做 pipeline、调整 clock tree）。

6.2 这也解释了必须跑两遍 GLS

一次仿真只能用一个 corner 的延迟值，即只能探测窗口的一侧边界。两个极端都跑，才覆盖得住整个区间。

7 · 对照 PrimeTime 报告

7.1 Setup 报告

  clock clk (rise edge)                   10.00   10.00   ← T_period
  clock network delay (propagated)         0.52   10.52   ← + T_clk_capture
  FF2/CK (DFF)                                    10.52
  library setup time                      -0.09   10.43   ← − T_setup
  data required time                              10.43   ← required
  ------------------------------------------------------
  data arrival time                               -9.86   ← T_clk_launch + T_datapath_max
  slack (MET)                                      0.57

7.2 Hold 报告

  clock clk (rise edge)                    0.00    0.00   ← edge N，注意是 0 不是 T_period
  clock network delay (propagated)         0.48    0.48   ← + T_clk_capture
  library hold time                        0.04    0.52   ← + T_hold
  data required time                               0.52   ← required
  ------------------------------------------------------
  data arrival time                                0.61   ← T_clk_launch + T_datapath_min
  slack (MET)                                      0.09

7.3 两处关键差异

① clock clk (rise edge) 行：10.00 vs 0.00 这一行就是两个公式差一拍的直接证据。setup 的捕获沿在 T_period，hold 的捕获沿在 0（同一沿）。
② clock network delay 数值不同：0.52 vs 0.48 因为两份报告取的是不同的悲观组合：
setup → late capture + early launch（让数据显得更赶不上）
hold → early capture + late launch（让数据显得冲得更早）

这就是 OCV / derate / CRPR 的作用点。
GLS 做不到这一点 门级仿真中 clock 和 data 只能用同一个 corner 的同一个值，无法像 STA 那样对 launch / capture 分别施加不同的悲观度。所以：
时序签核靠 STA，GLS 靠的是发现 STA 约束错误和 X 传播问题。

7.4 读报告的检查清单

  1. 确认 clock clk (rise edge) 的值 → 判断是 setup 还是 hold，以及是否是 multicycle
  2. propagated 还是 ideal → ideal clock 的报告在 CTS 后就没有参考价值
  3. library setup/hold time 符号 → 负 setup / 负 hold 是正常的，别当成异常
  4. 有无 clock reconvergence pessimism 行 → 没有则 CRPR 未开，报告偏悲观
  5. inter-clock uncertainty → 跨时钟域路径是否该被 false path 掉

9 · 常见 Cell 在 SDF 中的格式解读

同一份 SDF 里，不同类型的单元写出来的 CELL 块形态差别很大。 只要先判断"这是哪一类单元"，就能预判它应该有哪些 IOPATH、哪些 TIMINGCHECK， 反过来也能用来发现反标缺失或库/网表不匹配。

9.1 先按"有无 TIMINGCHECK"分两大类

类别典型单元SDF 块特征
纯组合逻辑INV / BUF / NAND / AOI / MUX / XOR / FA 只有 DELAY (ABSOLUTE ...)，没有 TIMINGCHECK
时序 / 状态单元DFF / DFFR / SDFF / LATCH / ICG / RAM / IO DELAY + TIMINGCHECK（SETUPHOLD / WIDTH / PERIOD / RECREM）
一条快速自查 网表里有 N 个触发器，SDF 里 TIMINGCHECK 块的数量应与之同量级。 如果一个 DFF 只有 DELAY 却没有 TIMINGCHECK， 说明 write_sdf 时丢了时序检查，GLS 将完全检查不出 setup/hold 违例。

9.2 反相器 / 缓冲器（INV, BUF, DEL）

(CELL (CELLTYPE "INVD2BWP7T40")
  (INSTANCE u_core/U1234)
  (DELAY (ABSOLUTE
    (IOPATH A ZN (0.015::0.015) (0.012::0.012))
  ))
)
  • 只有一条 IOPATH，一个输入到一个输出
  • 两组括号 = 01（上升）与 10（下降）两个转换延迟
  • 反相器输出端常命名 ZN；缓冲器为 Z —— 名字本身不含反相信息，反相关系由库模型决定
  • DEL 系列（延时单元）格式完全相同，只是数值明显偏大（几百 ps 量级）
时钟树上的 BUF / INV 数量最多 CTS 后 SDF 里占比最大的往往是 CKBUF / CKINV 系列。 它们的 IOPATH 直接决定第 4、5 章里的 T_clk_launch 与 T_clk_capture， 也是 skew 的来源。查 clock network delay 异常时第一个看这类单元。

9.3 多输入组合门（NAND / NOR / AOI / OAI）

(CELL (CELLTYPE "ND2D1BWP7T40")
  (INSTANCE u_alu/U88)
  (DELAY (ABSOLUTE
    (IOPATH A1 ZN (0.021::0.021) (0.018::0.018))
    (IOPATH A2 ZN (0.023::0.023) (0.019::0.019))
  ))
)
  • 每个输入脚各一条 IOPATH，条目数 = 输入数
  • 各脚延迟不同，源于版图上晶体管的串/并联位置（靠近输出的管子更快）
  • AOI / OAI 这类复合门脚位更多（A1 A2 B…），IOPATH 会有 3~5 条
STA 工具只会挑一条 SDF 把所有输入脚都标上，但具体某条路径走哪一脚，由网表连接决定。 一个单元出现多条 IOPATH 不代表延迟相加。

9.4 MUX（含第 1 章的实例）

(CELL (CELLTYPE "MUX2V2_140P7T40L")
  (INSTANCE ..._MUX2V2_140P7T40L_99)
  (DELAY (ABSOLUTE
    (IOPATH I0 Z (0.018::0.018) (0.018::0.018))
    (IOPATH I1 Z (0.017::0.017) (0.019::0.019))
    (IOPATH S  Z (0.011::0.021) (0.013::0.015))
    (COND I0==1'b0 (IOPATH I1 Z ...))
    (COND I1==1'b0 (IOPATH I0 Z ...))
  ))
)
  • 数据脚 I0 / I1 各一条，选择脚 S 单独一条 —— S 也是时序路径，常被忽略
  • COND 行是状态相关延迟：另一路数据脚固定为 0/1 时，本路的延迟不同
  • MUX 是 glitch 的常见来源，S 路径与数据路径的延迟差会被 PATHPULSE 影响
COND 行必须与库 .v 的 specify 块逐字对应 若库里写 if (I0 === 1'b0) 而 SDF 写 I0==1'b0 之外的形式（如写成 !I0）， 该条会 unmatched，静默退回库默认值。查 sdf.log 时要专门 grep COND。

9.5 D 触发器（最重要的一类）

(CELL (CELLTYPE "DFCNQD1BWP7T40")
  (INSTANCE u_core/state_reg_3)
  (DELAY (ABSOLUTE
    (IOPATH (posedge CP) Q (0.095::0.095) (0.088::0.088))
    (IOPATH (negedge CDN) Q ()(0.070::0.070))
  ))
  (TIMINGCHECK
    (SETUPHOLD (posedge D) (posedge CP) (0.045::0.045) (-0.012::-0.012))
    (SETUPHOLD (negedge D) (posedge CP) (0.052::0.052) (-0.008::-0.008))
    (WIDTH (posedge CP) (0.120::0.120))
    (WIDTH (negedge CP) (0.110::0.110))
    (RECREM (posedge CDN) (posedge CP) (0.060::0.060) (0.030::0.030))
    (WIDTH (negedge CDN) (0.090::0.090))
  )
)
条目含义对应公式中的量
IOPATH (posedge CP) Q时钟到输出的传播延迟T_datapath 的起点部分（CK→Q）
IOPATH (negedge CDN) Q异步清零到输出复位释放路径
SETUPHOLD D CP建立与保持时间合并写T_setup / T_hold
WIDTH CP时钟高/低电平最小宽度占空比检查
RECREM CDN CPrecovery / removal异步复位相对时钟的约束
三个必须注意的点 ① SETUPHOLD 的第一个值是 setup、第二个是 hold，顺序固定；
② hold 出现负值（-0.012）是正常的，必须用 +neg_tchk -negdelay 才能正确仿真；
③ 上升沿 D 与下降沿 D 的 setup 不同（0.045 vs 0.052），所以写成两条。

9.6 带扫描的触发器（SDFF / Scan FF）

(CELL (CELLTYPE "SDFCNQD1BWP7T40")
  (INSTANCE u_core/cnt_reg_0)
  (DELAY (ABSOLUTE
    (IOPATH (posedge CP) Q (0.098::0.098) (0.090::0.090))
  ))
  (TIMINGCHECK
    (SETUPHOLD (posedge D)  (posedge CP) (0.045::0.045) (-0.012::-0.012))
    (SETUPHOLD (posedge SI) (posedge CP) (0.060::0.060) (0.005::0.005))
    (SETUPHOLD (posedge SE) (posedge CP) (0.150::0.150) (0.020::0.020))
    (WIDTH (posedge CP) (0.120::0.120))
  )
)
  • 比普通 DFF 多出 SI（scan in）与 SE（scan enable）两组 SETUPHOLD
  • SE 的 setup 通常远大于 D —— 它要在时钟沿前稳定足够久以切换数据通路
  • 功能仿真时 SE=0，SI 路径不激活；但 scan shift 模式的 GLS 必须单独跑（对应第 3.9 节的 Mode 维度）

9.7 锁存器（LATCH）

(CELL (CELLTYPE "LHQD1BWP7T40")
  (INSTANCE u_ctrl/lat_0)
  (DELAY (ABSOLUTE
    (IOPATH (posedge E) Q (0.080::0.080) (0.075::0.075))
    (IOPATH D Q           (0.060::0.060) (0.058::0.058))
  ))
  (TIMINGCHECK
    (SETUPHOLD (posedge D) (negedge E) (0.030::0.030) (0.015::0.015))
    (WIDTH (posedge E) (0.100::0.100))
  )
)
锁存器与触发器的关键区别 多了一条 IOPATH D Q（无边沿限定）—— 使能打开期间数据直通。 这条路径是 time borrowing 的物理来源，也是 latch 时序难分析的根本原因。 SETUPHOLD 参考的是使能的关闭沿（此处 negedge E），不是打开沿。

9.8 集成时钟门控（ICG / Clock Gating Cell）

(CELL (CELLTYPE "CKLNQD4BWP7T40")
  (INSTANCE u_core/clk_gate_bank0)
  (DELAY (ABSOLUTE
    (IOPATH (posedge CP) Q (0.055::0.055) (0.050::0.050))
  ))
  (TIMINGCHECK
    (SETUPHOLD (posedge E)  (negedge CP) (0.090::0.090) (0.010::0.010))
    (SETUPHOLD (posedge TE) (negedge CP) (0.085::0.085) (0.010::0.010))
    (WIDTH (posedge CP) (0.120::0.120))
  )
)
  • 内部是 latch + AND，所以 E 的 SETUPHOLD 参考 negedge CP（时钟低电平期间采样 enable）
  • TE 是 test enable，DFT 时强制开门
  • ICG 的 CP→Q 延迟直接叠加到整条下游时钟树上
ICG 是 GLS 最容易暴雷的单元 enable 信号的 setup 违例会导致门控时钟出现毛刺或丢沿， 后果是整组寄存器漏采一拍 —— 这类问题在 RTL 仿真中完全看不到， 只有带 SDF 的 GLS 才能抓住（对应第 2.5 节 GLS 的定位）。

9.9 Memory / IP 黑盒（RAM / ROM / PHY）

(CELL (CELLTYPE "SRAM_1024X32_M4")
  (INSTANCE u_mem/u_sram0)
  (DELAY (ABSOLUTE
    (IOPATH (posedge CLK) Q[0]  (1.250::1.250) (1.180::1.180))
    (IOPATH (posedge CLK) Q[31] (1.270::1.270) (1.200::1.200))
  ))
  (TIMINGCHECK
    (SETUPHOLD (posedge A[0]) (posedge CLK) (0.300::0.300) (0.120::0.120))
    (SETUPHOLD (posedge WEN)  (posedge CLK) (0.280::0.280) (0.110::0.110))
    (SETUPHOLD (posedge D[0]) (posedge CLK) (0.260::0.260) (0.100::0.100))
    (WIDTH  (posedge CLK) (0.800::0.800))
    (PERIOD (posedge CLK) (2.000::2.000))
  )
)
  • 条目数量极多：每一位 地址 / 数据 / 输出都单独写一条
  • 延迟量级比标准单元大 1~2 个数量级（ns 级 vs ps 级）
  • 常见 PERIOD 检查 —— 存储器有最高工作频率限制
  • 这类 CELL 的时序来自 memory compiler 生成的 .lib，不随标准单元 corner 自动缩放，必须确认用了对应 corner 的 memory 库

9.10 IO / PAD 单元

(CELL (CELLTYPE "PDDW0204SCDG")
  (INSTANCE u_io/pad_gpio_5)
  (DELAY (ABSOLUTE
    (IOPATH I  PAD (2.400::2.400) (2.350::2.350))
    (IOPATH PAD C   (1.800::1.800) (1.750::1.750))

  • I→PAD 输出方向、PAD→C 输入方向、OEN→PAD 三态控制
  • 延迟是 ns 级（驱动大负载 + ESD 结构）
  • IO 单元跨两个电压域（core 1.8V / IO 3.3V），SDF 头部的 VOLTAGE 只写了一个，IO 的时序实际由 IO 库单独决定 —— 见第 3.4 节多电压域

9.11 互连延迟（INTERCONNECT，不属于任何 CELL）

(CELL (CELLTYPE "top")
  (INSTANCE)
  (DELAY (ABSOLUTE
    (INTERCONNECT u_a/U1/ZN u_b/U2/A (0.008::0.008) (0.009::0.009))
    (INTERCONNECT u_a/U1/ZN u_c/U3/A (0.015::0.015) (0.017::0.017))
  ))
)
为什么它挂在顶层 CELL 下 INTERCONNECT 描述的是两个 pin 之间的连线延迟，不属于某个单元内部， 所以统一写在 (CELLTYPE "top") (INSTANCE) 这个空实例块里。 同一驱动点到不同负载的值不同（0.008 vs 0.015）—— 这就是 RC corner（第 3.6 节）影响最大的地方。

9.12 Spare Cell / Tie Cell / Filler 等"不参与功能"的单元

Tie High/Low (TIEH/TIEL)通常无 IOPATH（没有输入脚）无
Filler / Decap完全不出现在 SDF 中无
Antenna Diode不出现无

10 · VCS 反标验证与排查

"仿真跑完了、没报错、PASS"不等于反标生效。SDF 反标失败在绝大多数情况下是 静默的：未匹配的路径会退回库模型的默认延迟（通常接近 0），仿真照样跑完， 时序验证形同虚设。必须按下面三层主动检查。

三层检查，缺一层就可能"以为反标了其实没反标" ① 读进去了吗 —— elaborate 阶段的 log 诊断
② 三元组是空的吗 —— SDF 文件静态文本检查
③ 延迟真的进仿真了吗 —— 运行时波形/违例验证
前两层只是"看 log"，只有第三层能真正证明反标生效。

10.1 第一层：确认 SDF 被读进去且匹配上

必须指定 log 文件并开 verbose

# 方式 A：TB 内 $sdf_annotate，第 4 个参数就是 log 文件
initial $sdf_annotate("top_max.sdf", tb.dut, , "sdf_annotate.log", "MAXIMUM");

# 方式 B：命令行
vcs ... -sdf max:tb.dut:top_max.sdf +sdfverbose
+sdfverbose 是关键 不开它，VCS 默认只报前若干条警告就静默了。你会看到一个"干净"的 log 而误以为没问题 —— 这是最常见的误判来源。

grep 诊断信息

# VCS 所有 SDF 相关诊断都以 SDFCOM_ 为前缀
grep -c "SDFCOM" vcs.log

# 按类型归类统计
grep "SDFCOM" vcs.log | sed 's/.*\(SDFCOM_[A-Z]*\).*/\1/' | sort | uniq -c
诊断类型含义处理
无法解析层次 / 实例名SDF 里的 INSTANCE 在网表中找不到 必须清零 —— scope 给错或网表版本不对
IOPATH / 端口找不到库模型的 specify 块里没这条路径 必须清零 —— 库版本与 SDF 不匹配
TIMINGCHECK 找不到库 .v 没有对应的 $setuphold 必须清零 —— 否则该 FF 完全不检查时序
COND 不匹配SDF 条件表达式与库 specify 的 if 不一致 高发区，需单独 grep 确认
 
# COND 要专门看 —— 它是静默退回库默认值的
grep -i "cond" sdf_annotate.log | head -50

数量对账（最容易被跳过，但最有效）

# SDF 里有多少个 CELL
grep -c "^\s*(CELL" top_max.sdf

# 网表里有多少个实例（粗略估计）
grep -cE "^\s+[A-Z0-9_]+ +[A-Za-z_][A-Za-z0-9_]* *\(" netlist.v
对账时要扣除/加回的部分 · 扣掉 filler / decap / well tap / antenna diode —— 这些不出现在 SDF 中（见 9.12）
· 注意 spare cell —— 这些出现在 SDF 中但对时序无贡献

如果 annotated 数远小于 CELL 数 → 大面积没反标上。 这种情况仿真会跑完、会 PASS，但时序验证完全是假的。

两个容易漏的开关

开关作用何时必须开
+multisource_int_delays支持多源互连延迟 SDF 含多源 INTERCONNECT 时，不开会只取一条

10.2 第二层：确认三元组本身不是空的

这一步在跑仿真之前做，纯文本检查，成本极低。

先摸清这份 SDF 是什么导出风格

# 统计各种三元组形态出现次数
grep -oE "\([0-9.:+-]*\)" top.sdf | sort | uniq -c | sort -rn | head -20
形态含义+typdelays 下的后果
(0.018:0.018:0.018)三值齐全（单 corner 导出）正常
(0.018::0.018)typ 为空 —— -delay_type min_max 导出 危险 静默退回库默认值
(::0.300)只有 max —— -delay_type max 导出min / typ 都取不到
(0.018)单值，三者相同正常
(::) / ()全空该条完全不生效

针对性地数空字段

# typ 位为空的条目数（min::max 风格）
grep -oE "\([0-9.+-]+::[0-9.+-]+\)" top.sdf | wc -l

# min 位为空（只有 max）
grep -oE "\(::[0-9.+-]+\)" top.sdf | wc -l

# 彻底全空
grep -oE "\(::\)|\(\)" top.sdf | wc -l
第 1.5 节那份 SDF 正是这个问题 片段中的 (0.018::0.018) —— typ 位是空的。

按 IEEE 1497，三元组中缺省的字段表示"未指定"，反标工具应当 保留目标对象的原有值（即库模型里的默认延迟）。所以：

vcs +typdelays -sdf typ:tb.dut:your.sdf  ← 对这份 SDF 是错的

这条命令不会报错、不会 unmatched，但大量路径会悄悄退回库默认值。 
# 正确做法：只用 min 和 max 两端
vcs +maxdelays -sdf max:tb.dut:your.sdf    # setup 验证
vcs +mindelays -sdf min:tb.dut:your.sdf    # hold  验证
两处选择必须一致 +mindelays/+typdelays/+maxdelays 与 -sdf min|typ|max:... 两处必须一致。
写成 -sdf max:... 却加 +mindelays 是常见的自相矛盾配置。
若用 $sdf_annotate 的 "TOOL_CONTROL"，则完全交由命令行开关决定。

确认 TIMESCALE 对得上

grep -i "TIMESCALE" top.sdf      # 例如 (TIMESCALE 1ns)
grep -i "timescale" netlist.v    # 例如 `timescale 1ns/1ps

vcs -diag timescale ...          # 让 VCS 主动报出不一致
单位不匹配 → 延迟被舍入成 0 SDF 的 0.018 ns = 18 ps。如果仿真精度只到 1ns， 这个值会被舍入成 0 —— 反标"成功"（log 干净），但延迟全是 0。 这是最隐蔽的一类失败。

10.3 第三层：确认延迟真的进入仿真

前两层都是"看 log"，这一层是"看结果"。只有这一层能真正证明反标生效。

① 波形量延迟 ← 首选

抓一个 FF，在波形上量 CK 上升沿到 Q 变化的时间， 和 SDF 里那条 IOPATH (posedge CP) Q 的数值对比。

grep -A3 "INSTANCE u_core/state_reg_3" top_max.sdf
对得上                    → 反标生效
Q 与 CK 同时刻跳变（零延迟） → 没反标上

② 极端值注入法 ← 最可靠的端到端验证

复制一份 SDF，把某个关键单元的延迟改成荒谬的大值：

(IOPATH (posedge CP) Q (5.000:5.000:5.000) (5.000:5.000:5.000))

重跑，看波形上该 FF 的 Q 是否真的延后 5ns。

这招能排除所有"log 干净但其实没生效"的情况 · 波形变了 → 反标链路（文件 → scope → 实例 → 路径）完全通畅
· 波形没变 → 反标在某一环断了

因为它验证的是端到端结果，不依赖任何 log 的可信度。

③ 故意制造违例，验证 TIMINGCHECK 生效

把时钟周期压到明显不够（比如砍一半），重跑，应该看到大量 Timing violation 报告。如果一条都没有，按下表排查：

可能原因检查方式
加了 +notimingcheck去掉 —— 它保留延迟但关闭所有检查
加了 +nospecify去掉 —— 它把延迟和检查一起关了
加了 +no_notifier违例不产生 X，但仍应打印报告；签核绝不能开
SDF 里本来就没有 TIMINGCHECK 段grep -c TIMINGCHECK top.sdf
库 .v 的 specify 块被编译选项屏蔽检查 -v / -y 与 +nospecify 的组合

④ 负时序检查必须开

vcs +neg_tchk -negdelay ...
不开会产生 STA 里不存在的假违例 SDF 里的负 hold（如 9.5 节的 (-0.012::-0.012)）会被钳到 0， 导致 hold 检查比 STA 更严格，报出一堆 STA 中并不存在的违例， 浪费大量时间去 debug 不存在的问题。

10.5 最常见的四个"假反标"

现象根因
log 干净、仿真 PASS，但波形上组合逻辑零延迟 scope 给错（tb.dut vs tb.dut.u_core），整块没匹配
反标数量很大，但时序验证查不出任何问题 大量 spare cell 撑高了 annotated 计数，真实逻辑其实没反标

用 +typdelays 跑 min::max 风格的 SDF typ 位为空 → 静默退回库默认值
